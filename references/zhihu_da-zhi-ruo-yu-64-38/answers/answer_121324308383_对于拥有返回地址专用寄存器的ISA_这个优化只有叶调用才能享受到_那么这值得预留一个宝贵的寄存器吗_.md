# 对于拥有返回地址专用寄存器的ISA，这个优化只有叶调用才能享受到，那么这值得预留一个宝贵的寄存器吗?

- 类型：回答
- 问题：对于拥有返回地址专用寄存器的ISA，这个优化只有叶调用才能享受到，那么这值得预留一个宝贵的寄存器吗?
- 原文：[知乎回答](https://www.zhihu.com/question/13934258384/answer/121324308383)

在指令集和ABI设计中，我们最好避免某条指令固定写到某个特定的寄存器中。这会扰乱编译器的寄存器分配算法，导致整体寄存器的利用率不高。

例如X86的MUL指令，将结果固定写到EDX和EAX。这样就不得不让编译强行腾空掉DX和AX，可能会引入更多的spill指令。

同理，对于Call-Return指令Pair来说，我们最好不要约束CALL指令固定写到一个特定的Return Address寄存器。例如，ARM指令集的BL将返回地址固定写到到X30(return address)，带来的问题就是ra这个通用的GPR就被锁定了。导致ABI中特殊功能的寄存器利用率都不太高。这对RISCV也适用。

riscv的架构寄存器使用频率统计

所以，编译器往往单独剔除RA/LR寄存器，不当作通用寄存器使用。这样RA/LR的函数调用序列往往是：

```text
CALL foo -> RA
PUSH RA -> [stack frame]
...
POP [stack frame] -> RA
RET RA
```

在Recursive Function或者连续函数调用的[Tail Call](https://link.zhihu.com/?target=https%3A//en.wikipedia.org/wiki/Tail_call)中，编译器往往执行尾调用优化。Tail Call Optimization不用在Caller侧记录callee的信息，从而大幅减少记录的状态。Return address也可以被省略。因此，除了叶子函数的场景以外，如果返回地址是固定的（嵌套调用）,返回地址可以不用压栈，可以直接通过goto来完成返回。

但是在大部分Pass-Through场景下，Caller-Callee为了维护ABI的共同约定，制造了大量的无效压栈操作。这些操作本来是可以通过track动态信息并消除的。

[Exploiting dead value information](https://link.zhihu.com/?target=https%3A//ieeexplore.ieee.org/document/645804/)这篇论文提供了一种动态消除压栈操作的做法，可以值得参考。
