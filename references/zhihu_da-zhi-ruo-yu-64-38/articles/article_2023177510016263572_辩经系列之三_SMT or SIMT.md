# 辩经系列之三：SMT or SIMT

- 类型：文章
- 原文：[知乎文章](https://zhuanlan.zhihu.com/p/2023177510016263572)

上一篇《[辩经系列之一：NPU or GPGPU](https://zhuanlan.zhihu.com/p/2022779284499039419)》，文言文的梗，玩到那里也就差不多了。
 这一篇，不玩虚的，直接上技术干货。
 我们来聊一个更本质、也更容易被讲歪的问题：

## **AI 计算，到底该押 SMT，还是押 SIMT？**

![image](https://pic2.zhimg.com/v2-1431f587b8d86a6d23c519136feb66a1_1440w.jpg)

先说一句不太谦虚的话：**这个问题，我还真有资格聊。**

为什么？

因为我不是在 PPT 上设计处理器，也不是在论文里设计处理器。
 我是在菊厂，真刀真枪做过一颗 **32核SMT4 的乱序多线程处理器，已经量产商用**。这东西不是画几张框图、跑几个模型就算结束，它是从指令集、微架构、CA Model、RTL、验证、FPGA、Emulator，踩 EC，一路磕到流片，再从回片、点亮、跑业务、最后走到商业部署。回片那天，一键点亮，复杂的几百线程业务直接跑通。到今天还在正常运行，已经部署商用。说句俗一点的话，这玩意儿给人的内啡肽，确实比发几篇 ISCA 更直接。

所以这一篇，不是体系结构课后习题答案，也不是读了几篇 paper 后的观后感。
 这一篇要讲的，是**真正能落到工程里、能扛住 timing、验证、功耗、面积和商业交付反复拷打的多线程处理器经验**。

第一代 SMT4 已经落地，第二代 SMT8 正在路上。
 所以这次也不怕把干货说出来。因为这种活，不是你听懂了就能做，也不是你看明白了，回去拉三个人就能成。要做这种东西，得有人愿意押大资源、押长周期、押高风险。愿意这么押的人，本来就不多。要是最后回来的是一块砖，不是一颗芯片，那可真要考虑提桶跑路了。

![image](https://pic4.zhimg.com/v2-372e4793d7146a4eac5faa3a45c6b217_1440w.jpg)

牛吹完了，开始讲理。我的立场先摆在前面：

**我认为在很多 AI 计算场景里，SMT 大于 SIMT。**

不是因为 SIMT 没价值，也不是因为 GPU 不成功；而是因为随着 workload 越来越真实，很多原来被“海量线程吞吐神话”盖住的问题，正在一个个重新浮出水面。

## 一、你们老爱拿 SIMD 去打 SIMT，可真正该上台的，其实是 SMT-SIMD vs SIMT

什么叫 **SIMT**？

这个问题，很多人一张嘴就要开始作法：仿佛 SIMT 是 GPU 神山上天降的紫气，和人间的 SIMD 早已恩断义绝。可 NVIDIA 自己在 PTX ISA 里写得一点也不玄：**SIMT “akin to SIMD”**，也就是“在性质上类似 SIMD”，因为本质上仍然是“一条指令控制多个处理单元”；真正的关键差异在于，**SIMD 把宽度暴露给软件，而 SIMT 让软件看到的是单线程的执行与分支语义**。CUDA Programming Guide 也说得很清楚：warp 以 SIMT 方式执行，同一 warp 内线程执行同样的 kernel code，但每个线程可以走不同的分支路径。([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/archive/8.0/parallel-thread-execution/index.html))

这里我们要定义一个概念，在GPGPU中，SIMT执行模型的每个warp是轮询多线程，也就是**FMT执行模型**。也就是线程调度基本上是一个QoS Round Robin模型。这样的调度是硬件最好实现的。

![image](https://pic3.zhimg.com/v2-681391c3080cb30360e448c9df89b132_1440w.jpg)

GPGPU-SM

这话翻成大白话是什么意思？
意思是，SIMT 不是从天外飞来的新物种，它并没有逃离“宽执行体”这个祖坟。它只是把原来赤裸裸摊在软件面前的“向量宽度”，裹上一层 thread 的长衫，再告诉程序员：“你别怕，你写的还是单线程。”这就像什么？像老宅子翻新，梁还是那根梁，柱还是那根柱，只不过外立面贴了新砖，门口换了铜环，于是有人就开始喊“这不是四合院，这是当代东方美学”。可你推开门一看，院子还在那儿，影壁也还在那儿。([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/archive/8.0/parallel-thread-execution/index.html))

所以，拿纯 SIMD去和 SIMT 对打，很多时候像什么？
像拿一把青龙偃月刀去比一支骑兵连，说谁更像近代战争。
像把弓箭拿去和火枪兵编制对比，然后一本正经地得出结论：火枪赢了弓箭，所以组织形态优于数据通路。
这不是论战，这是跑题。题目都出错了，答案当然越写越偏。

因为真正应该和 SIMT 对比的，不是裸奔的 SIMD，而是 **SMT-SIMD**。

SIMT 解决的是什么问题？
是**很多线程如何共享一套宽机器**。
SMT-SIMD 解决的又是什么问题？
是**一颗宽机器如何同时在 ILP、TLP、DLP 之间动态吃饭**。

你也许会问：
“你这是不是偷换概念？是不是把什么都往 SMT 上贴标签？”
不急，先别扣帽子。帽子这东西戴在脑袋上是装饰，扣在别人头上就是偷懒。

## 二、Silly, it is not just the memory latency

AI 处理器最怕什么？
算力不够吗？未必。很多时候，真正先露出牙齿的，不是算力，而是**访存时延**。算力像一群闲站在码头上的壮汉，胳膊练得比船锚还粗，结果船还没靠岸，货也没下舱，大家只能在岸边互相展示肱二头肌。不是不猛，是猛得没处使。NV 官方自己就写得很明白：一旦操作数落在片外内存，延迟通常就是**几百个时钟周期**；为了遮住这种延迟，需要足够多的 warps 持续给 warp scheduler 喂活。([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/cuda-c-programming-guide/))

那怎么办？
很多人张口就是一句祖传名言：
**那就多线程啊。线程够多，自然把 latency 藏住。**

这话对不对？
对。
但问题也恰恰在这里：**它太对了，所以太粗了。**

粗在哪里？
粗在它把“隐藏访存时延”这件事，想得像双十一仓库堵车：既然堵了，那就再雇三百个快递员。至于仓库门口只有一条巷子，装货口只有两个，货架还得绕远路，分拣区和打包区还互相打架——这些统统不管。仿佛只要人够多，包裹就会自己飞出去。可 NVIDIA 的 Nsight 文档讲得比鸡汤诚实得多：每个 scheduler 维护一池 warps，只有**eligible warps** 才能被发射；如果一个周期里没有 eligible warp，issue slot 就会被跳过，这正是“latency 没被 hide 掉”的明牌证据。换句话说，线程多不是目的，**持续有能发的线程**才是目的。([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/nsight-compute/ProfilingGuide/index.html))

![image](https://pica.zhimg.com/v2-4dc51a391bdf3556a03796f541a849c4_1440w.jpg)

于是问题来了：
隐藏时延，真的只是“把更多 load 无脑撒出去”吗？
当然不是。
如果只是“人海战术”就能解决问题，那 GPU 论文的半壁江山都可以改行写旅游游记了。

先看一个很扎心的事实。SC’14 那篇 `Managing DRAM Latency Divergence in Irregular GPGPU Applications` 一开篇就说：现代 GPU 的 memory controller 为了追求高带宽，会激进地重排请求，常常把**来自不同 warps 的请求交织在一起**。结果呢？带宽也许更好看了，但同一个 warp 内部的请求完成时间会出现更高方差，时延发散加重，最后拖累整体执行。你把人都赶上路，不代表大家会一起到；有的人先到，有的人晚到，队伍反而被自己拉扯散了。([用户计算机科学网站](https://link.zhihu.com/?target=https%3A//users.cs.utah.edu/~rajeev/pubs/sc14.pdf))

![image](https://pica.zhimg.com/v2-a8f33dc57238abbbfa438a830bc142de_1440w.jpg)

再看 MARS。它讲得更直白：多个数据流一高度交织，原本单个流内部自带的 locality 会被打碎，row-buffer reuse 会下降，内存效率反而变差。它的应对方式并不神秘，甚至很像老镖头的常识：既然乱序交织把路感走没了，那就在足够大的 lookahead 窗口里，把请求按 row-buffer 地址重新排一排，把 locality 再捡回来。作者报告说，靠“把 locality 捡回来”这一件事，就能让若干 memory-intensive microbenchmarks 的 memory efficiency 提升约 11%。这说明什么？说明访存不是菜市场抢鸡蛋，不是谁人多谁赢；访存更像送镖，镖师少的时候，镖车不但要出门，还得讲路线，讲先后，讲哪条路桥没塌。([arXiv](https://link.zhihu.com/?target=https%3A//arxiv.org/pdf/1808.03518%3Futm_source%3Dchatgpt.com))

`Dynamic Warp Subdivision` 这种经典工作，干脆就承认：当 branch divergence 或 memory divergence 出现时，一个 warp 不是非得绑死成一坨，可以被切成更细的可调度单元，让一部分先走、一部分后走。为什么要这么干？因为大家已经心知肚明：整齐划一有时是美德，有时却是拖油瓶。如果大车队过桥太慢，就把车拆成两股。桥是那座桥，车还是那堆车，但组织方式变了，效率就不一样。([ACM Digital Library](https://link.zhihu.com/?target=https%3A//dl.acm.org/doi/pdf/10.1145/1815961.1815992%3Futm_source%3Dchatgpt.com)) `Predictive Warp Scheduling` 这一类工作更进一步，直接提出：有些 warps 眼瞅着就要触发长时延操作，那就别一股脑都往前推，应该**预测谁会造成长时延，再决定谁先发、谁后发**。这说明什么？说明 GPU 世界自己都已经承认：调度不只是谁 ready 谁上，还包括谁现在上最划算。这已经不是单纯的 thread-level overbooking，而是在往请求组织学习华子IPD流程了。([ACM Digital Library](https://link.zhihu.com/?target=https%3A//dl.acm.org/doi/pdf/10.1145/3453688.3461525%3Futm_source%3Dchatgpt.com))

那么，SMT能有什么不同吗？
因为 SMT 的第一步，不是先把 所有线程全赶上街，再从人山人海里碰碰运气看能不能把 latency 淹掉。
SMT 更像一个会排车队的老镖头：先**在ROB里面把一个线程的多个** load 做出来。这样出来的 load，天然带着程序局部性，带着更强的 producer-consumer 关系，带着更清晰的先后语义。然后再通过 OoO、LIQ、LHQ、 MSHR、NoC、LLC 、MATA/HHA 这些结构，把它们组织成真正有秩序的 **MLP**。一个像先编队再出兵，一个像先出兵再捡队形；一个像水渠引流，一个像涨潮漫灌。前者不一定场面最热闹，但往往更知道水该往哪儿流。这里我说的是一种架构倾向和工程判断。

有人会反问：
“你是不是把 SMT 想得太美了？多线程共享资源，彼此踩脚不是家常便饭吗？”
当然会踩。哪有酒席永远不碰杯，哪有镖局永远不抢道。

![image](https://pic4.zhimg.com/v2-200ed270f259039768330f199d81ddc9_1440w.jpg)

可经典 SMT 研究同样给出了一个常被忽略的反例：Lo 等人分析数据库 workload 时发现，线程之间的 memory-system competition 并不总是坏事，其中一部分是**左脚踩右脚直线螺旋起飞**的，也就是线程共享数据带来 cache-line reuse，反而有利于性能；他们还报告，在高度 memory-intensive 的 OLTP 负载上，模拟的 SMT 处理器相对于资源相近的基线 superscalar，instruction throughput 能到约 3 倍。

所以**隐藏访存时延，不是比谁更会“无脑并行”；而是比谁更会“有序并行”。**
SMT 擅长的是：先把车队排好，再一起发。
SIMT 擅长的是：先把人都叫来，在一个不大的窗口里做 coalesce，再看看会不会堵。

## 三、阿姆达尔定律从来不讲情面，最后赢的人，往往是串行部分没烂掉的人

我前两篇文章谈 AI 处理器，张口就是 GEMM，闭口还是 GEMM。
仿佛天下武功练到最后，只剩一招：**力大砖飞**。
矩阵乘一快，万事大吉；张量核一响，诸邪退散。
听上去很豪迈，像武侠小说里“我有一剑，可开天门”。
可现实呢？现实常常更像官场小说：前门的将军再威风，后院的账房先生真要罢工，整个衙门照样瘫。

为什么这么说？
因为你把 GEMM 做快了，世界并不会自动太平。
恰恰相反，原来被掩在主菜后面的那几碟“小凉菜”——softmax、reduce、sampling、同步、epilogue、decode attention——会开始一盘盘端上主桌，而且越端越理直气壮。

近两年的 LLM 推理论文已经把窗户纸捅破了：高效推理综述明确把 **大模型规模、attention 的二次复杂度、autoregressive decoding 的串行方式**，列为 LLM 推理低效的几个核心根源。也就是说，AI 从来就不是一块纯平的并行大草原，它天生拖着一条串行尾巴；只是前几年大家都忙着给大平原铺高速，暂时没空理那条尾巴而已。 ([arXiv](https://link.zhihu.com/?target=https%3A//arxiv.org/abs/2404.14294))

那这条尾巴现在到底有多长？
先看 softmax。

有人会问：
**softmax 真有那么重要吗？不就是 attention 里顺手做一下归一化吗？**
问得好。问题就在这个“顺手”二字上。

UniAttn 直接说，**softmax operation is a primary bottleneck for LLM inference**，也就是 softmax 已经成了 LLM 推理里的主要瓶颈之一。ConSmax 更不客气，它几乎是在明着批评业界的注意力分配：大家把绝大多数精力都砸在矩阵乘上，却忽略了 softmax 本身的并行性差、同步重、难硬化这些老毛病，于是它专门设计一种替代 softmax 的硬件友好归一化方法，目标就是把 maximum searching 和 denominator summation 这两个“拖后腿的老同事”一脚踢开。更扎心的是，SoftmAP 对 Llama2-7B 在 A100 上做了表征，结果发现：**softmax 的运行时间占比会随着序列长度上升，在长序列下最高能到 38%，而相关工作里也提到它可能超过整体时延的 30%**。你看，softmax 不是什么“边角料”，它更像戏班子里一直站在幕后的鼓师。台上唱念做打一旦都练利索了，观众突然发现：哎，这鼓点怎么成了整台戏最卡人的地方。 ([arXiv](https://link.zhihu.com/?target=https%3A//arxiv.org/html/2502.00439v1))

如果说 softmax 还是attention 体系里的老麻烦，那 sampling 的崛起，就有点像衙门里原本给人倒茶的书吏，忽然有一天坐上了正堂。SIMPLE 这篇 2025 年的论文写得很直白：随着 tensor parallelism、pipeline parallelism 以及 data plane 上的 attention/GEMM、KV cache 一侧被不断优化，**sampling 这个把 logits 变成 token 的 decision plane，开始变成新的 bottleneck**。作者甚至把这个问题点得很透：sampling 既不能像 attention/GEMM 那样随着 TP 横向膨胀，也不能像前面那些 stage 那样很好地在 PP 里摊平，所以随着 GPU 越来越快，它在 iteration time 里的占比反而会上升，最后卡在 pipeline 的末端，像车队里最慢那辆拖拉机，把整个车队的平均速度都拖下去。这个比喻不是我现编的，是系统本身就在这么运作：前面的路越修越宽，最后那个收费站就越显眼。 ([arXiv](https://link.zhihu.com/?target=https%3A//arxiv.org/abs/2512.00719%3Futm_source%3Dchatgpt.com))

所以这说明什么？
说明**阿姆达尔定律没死，它只是换了件 AI 的外套。**

阿姆达尔定律：

![image](https://pic3.zhimg.com/v2-24406cc21dedd450cd4cf0a617d511b8_1440w.jpg)

很多人一听阿姆达尔定律，脑子里还是老教科书：一部分可并行，一部分不可并行，于是总加速比受限。
可到 AI 这里，它的脸更狡猾，也更像现代人：
前几年它藏在 attention 后面，后来藏在 softmax 后面，再后来又从 sampling、decode、同步、尾部控制里探出头来。它不是消失了，它只是在换藏身之处。

你把大块的并行部分推平了，
剩下那点串行、半串行、倒三角收敛的数据流，就会从角落里站起来，拍拍你的肩膀说：
“前面辛苦了。现在轮到我卡你脖子了。”

而这，恰恰是 SMT 特别对味的地方。

![image](https://picx.zhimg.com/v2-d64d212f83289b8e91880e53d65e78f9_1440w.jpg)

为什么？
因为 SMT 的资源不是一锤子焊死的，它更像一位会看场面挪桌子的掌柜。
客人多的时候，大家平分桌椅；
客人少的时候，剩下那几桌可以立刻并桌、让菜、扩位。
并行度高时，多线程可以平分 issue、端口、ROB、寄存器窗口；
并行度塌下去时，活着的线程又能独占更多资源，把剩下的串行活、归约活、尾部活狠狠干完。
它不是死板地给每个人焊死一把椅子，而是知道什么时候该分桌，什么时候该拼桌，什么时候干脆把整面屏风挪开。

反过来看 SIMT，它当然也能跑这类 workload，但它的直觉往往更像什么？
更像一个先把三十二把椅子焊死在地上的酒楼老板，然后要求客人“请优雅地坐满”。
人多时当然好看，整整齐齐，像阅兵；
可一旦进入 reduce、sampling、尾部控制这些“人越来越少”的阶段，空椅子就开始比人还显眼。
这不是说 SIMT 没法做，而是说它在结构直觉上，更偏向于**先把宽度和队形固定下来，再想办法别浪费 lane**；
而 SMT 则更像是**先接受“并行度会变”这个现实，再让资源跟着现实挪位置**。
前者像焊死了座椅的戏台，后者像可以移动隔断的酒楼。
戏台适合大戏齐唱，酒楼更适合散席之后收尾。
问题在于，大模型推理这门生意，往往是“前面大戏，后面收尾”，而不是从头到尾都在齐唱。

SHADOW 这篇 MICRO 2025 的工作，就在做一件很有意思的事：把 OoO thread 和 InO thread 放进同一个非对称 SMT core 里，运行时动态平衡 ILP 和 TLP。作者的出发点也很朴素：很多 memory-bound workload，尤其是稀疏、访存不规则、ILP/TLP 会来回摆动的那类负载，传统 OoO 核在某些阶段 ILP 挖不出来，资源就会闲着；纯 InO 多线程又容易在别的阶段吃不满深 ILP。于是 SHADOW 的办法不是二选一，而是让 OoO 和 InO 线程在同一个 core 里同时存在、动态偷活、按场景分账。它报告的结果也很醒目：在九类 benchmark 上，最高可达 3.16× 提升，平均约 1.33×，而面积和功耗开销都只有大约 1%。这说明什么？说明大家已经越来越不满足于“单一范式一统天下”，而是在认真重新思考一件事：不同并行度阶段下，资源到底该怎么动态分账。 ([自由研究小组](https://link.zhihu.com/?target=https%3A//liberty.princeton.edu/Publications/micro25_shadow.pdf))

这件事很重要。
因为它意味着，学界开始承认一个工业界其实早就痛彻心扉的事实：

**瓶颈不是静态的，并行性也不是静态的**
一个 workload 里，前半段可能最吃 DLP，
中段可能最怕 memory wall，
尾部可能最卡串行决策与归约。
你要是拿一把永远不变形的锤子去敲它，敲到最后，不是锤子卷刃，就是钉子歪头。
而 SMT 的美，不在于“线程多”三个字，而在于它是动态做了资源调整。

这也是我在华子做的SMT4核爆打In-Order FMT8 八线程的竞品核心逻辑。

## 四、SMT 为什么总和乱序、投机绑在一起？因为它们本就是一家人

有人说：
**SMT 太复杂，OoO 太耗电，投机太冒险，回滚开销大。**

那我问你一个更要命的问题：

这点开销和洪水巨兽相比，功耗占比多少？**我的回答是0.05%**

为什么？这些投机的模块不占面积和功耗吗？RAT、ROB、RS、LSQ、fetch、replay、flush、rollback 这一大串家谱？我的回答是：

### 投机不是原罪。错猜才是税，猜中就是功耗为0的白嫖生意

先把最容易被扣帽子的地方讲清楚。

**投机不是免费午餐。**
分支预测、错误路径执行、错误唤醒、错误发射，这些东西当然会烧电，也当然会制造浪费。这个结论不是常识层面的“我猜如此”，而是有实打实研究的。Parikh 等人的功耗论文讲得很明白：更高精度的分支预测虽然可能让预测器本身更复杂，但如果它显著减少 wrong-path instructions、缩短运行时间，那么处理器的总体能耗反而会下降；他们报告的结果里，相比最差方案，最优方向预测器可以把整体能耗拉低大约 **10%**。([cs.virginia.edu](https://link.zhihu.com/?target=https%3A//www.cs.virginia.edu/~skadron/Papers/bpred_power_hpca02.pdf%3Futm_source%3Dchatgpt.com))

这说明什么？
说明投机不是“乱花钱”，而是“看命中率做生意”。
错猜，是税；
猜中，是白嫖。
你不能因为做生意要交税，就宣布做生意是原罪。那不是谨慎，那是怕账本。

**在高准确率、可回滚的前提下，投机是在用少量风险，换取大量收益。**

一个处理器里面，如果有flush兜底了，原本那些到处拉满 stall 信号的保守电路，就有了谈判空间。流水可以更深一点，仲裁可以更大胆一点，发射可以更多供给一点。是因为机器突然变聪明了，
而是因为它终于被允许“边走边看”，而不是“看明白了再挪脚”。

毕竟，投机执行也是并行度解放的有效手段。

这时候你可能还会反问：

**那你这不就是 CPU 老路重走吗？GPU 世界不是已经证明“静态排班 + 海量线程”也能走得很好吗？**

当然走得好，而且走得很成功。CPU那一套投机方法，在90%猜对的概率上反复横跳。最近value predication也是小心翼翼，才勉强落到芯片上。

但是AI workloads的猜，可以做到99%。如果我能99%的时间白嫖，何乐而不为呢？

更有意思的是，连一向以吞吐优先、纪律严明著称的 GPU 阵营，最近都开始往这边偷看。2023 年的 SOCGPU，题目就写得很坦白：`Simple Out-of-Order Core for GPGPUs`。作者不是在玩文字游戏，他们真做了一个轻量级 OoO 机制，而且刻意避免了传统 CPU 式的大开销：**不做寄存器重命名，不用传统 scoreboard，而是靠一个小 instruction buffer 和 tiny dependence matrix 去跟踪依赖。**结果呢？在 Tesla V100-like 的模型上，某些机器学习程序最高加速 **2.3×**，综合平均约 **1.38×**，同时能耗下降 **6.5%**，面积开销只有 **2.4%**。这说明什么？说明连 GPU 这片一向主张“多线程把时延淹掉”的地界，也开始承认：**完全依赖静态排班、完全依赖 in-order 忍耐，并不是唯一答案。**

真正更有杀气的，是 **TURBULENCE**。
这篇工作的切入点非常漂亮，甚至可以说有点毒辣。它没有满足于“在现有 GPU 上缝一点轻量 OoO 逻辑”，它直接追问了一个更本质的问题：

**为什么 OoO 在 GPU 上显得贵？**
**到底是 OoO 这件事本身贵，还是你沿用了 CPU 那套表达依赖的方式，所以它才贵？**

TURBULENCE 的思路就是修水渠。它提出：传统 OoO 的很多复杂度，来自 rename logic、寄存器编号追踪，以及围绕这些结构搭起来的大量配套硬件。所以它干脆从 **ISA 本身**下手，不再让指令按寄存器号引用操作数，而是引入一种**按指令距离（inter-instruction distance）引用操作数**的方式，再配一套对应的微架构，去实现一种**复杂度更可控的 GPU 乱序执行**。他们把这套东西明确称为：**very low-cost out-of-order execution on GPUs**。([past.date-conference.com](https://link.zhihu.com/?target=https%3A//past.date-conference.com/proceedings-archive/2023/DATA/1031.pdf%3Futm_source%3Dchatgpt.com))

这件事的意义，已经不只是“又有一篇 OoO-GPU 论文”这么简单了。
如果“海量线程 + 静态排班 + in-order 忍耐”真的是终极答案，那么 GPU 世界就没有必要花这么多心思去研究 SOCGPU、TURBULENCE 这一类东西。既然已经有人认真地做、认真地评估、认真地证明它们值得，那就说明现实 workload 里，确实还有一块肉，纯靠“线程多”是吃不干净的。那块肉，就是**thread 内部的独立性、动态可提取的 ILP、以及更灵活的运行时调度空间。**

这一点，和 SMT 的直觉本来就是同路的。SMT 从第一天起讲的就是：别只盯着单线程，也别只迷信线程多，而是要把**线程级并行和指令级并行一起池化**。

## 五、SMT 最大的问题是前端？对通用程序是。对 AI 内核，不是

我并不回避 SMT 的短板。
SMT 的老毛病，确实在前端：取指带宽、预测表互扰、decode/rename 压力、issue queue 拥塞。这一点在通用 CPU 世界里早就不是什么秘密。El-Moursy 那篇讲 SMT front-end policy 的论文，开宗明义就在说：SMT 会把 issue queue 这类本就敏感的结构压得更紧，既容易碰 timing，又容易多烧电，所以前端策略必须仔细设计。([csl.cornell.edu](https://link.zhihu.com/?target=https%3A//www.csl.cornell.edu/~albonesi/research/papers/hpca03_1.pdf))

可问题来了：

**AI 内核，真有那么强的前端压力吗？**

这点为什么在 AI 上是有收益的？ 因为很多 AI kernel 不是充满花枝乱颤控制流的SPEC INT。它们里头有大量规整循环、重复模式、相似 load/use 节奏、可预测的资源竞争。

所以这里真正该问的，不是“SMT 前端难不难”，而是：

**对什么程序难？对哪类压力最难？**

如果你的程序热代码像野草一样乱长，分支像胡同一样乱拐，那 SMT 的前端当然难受。
可如果你的 kernel 本来就是规整循环、固定阶段、热区很窄，那么 SMT 的前端问题虽然还在，却未必是最疼的那一刀。真正更疼的，常常在后端：某些流水很长，某些功能单元容易扎堆，load/store 和算子混在一起。

**如果单条浮点/特殊函数流水本来就很长，你为什么一定要用 32 线程那种“海量备胎”去遮？为什么不能用 4 到 8 个 SMT 线程，加一个更积极的 OoO/LSQ/端口共享体系来遮？**

很多人下意识会把这个问题回答成一句口号：
“因为 GPU 就是这么干的。”
可“它一直这么干”从来不是“它必须这么干”的同义词。
这就像春运大厅里人满为患，你不能因为大家都在排队，就得出“排队是交通系统的最高美学”。排队有时候只是办法，不是答案；warp 多有时候只是补药，不是仙丹。CUDA 文档自己其实都留了后门：需要多少 warps 来 hide latency，**取决于 kernel 的 ILP**。这句话翻成白话，就是：如果单个线程内部本来就还能挖独立性，那你对“备胎 warp”的需求就没那么刚性。([docs.nvidia.com](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/cuda-c-programming-guide/))

而这恰恰是 SMT 有味道的地方。

为什么？
因为 SMT 允许你把不同线程、不同阶段、不同指令型态，塞进同一台机器的不同角落里，让它们在更细粒度上**动态分账**。
大家都在做 softmax，不代表大家会在同一拍都挤到 exp 上；
有人这拍在做 两读口的max，
有人在做 一写口的exp，
有人在做 load，
有人在等 store buffer 松口，
有人寄存器读口压力大一点，
有人 ALU 占用更偏，
有人更吃端口，
有人更吃寄存器。

![image](https://pica.zhimg.com/v2-84785689c0fdff08521cc54cad3034fc_1440w.jpg)

这时候，异构 ALU、Regfile读写端口、ROB 窗口、issue slot 之间的互补利用，恰恰是 SMT 的长处。它更像一个会看场面的掌柜：这桌客人酒来了，就先上凉菜；那桌催汤，就先腾锅；谁现在占灶台最合算，谁就先占。
SIMT 呢？SIMT 更像一整支大车队过桥。队形当然整齐，纪律当然严明，可一旦这一拍全队都看上同一个收费站，队形再美，也还是堵。你可以 coalesce、可以 regroup、可以多挂 warps，但本质上还是在用更多队伍，去替代更灵活的核内再分配。

**softmax 这种东西，最能暴露谁是会过日子的架构。**
因为它不是一个“从头到尾都在同一种功能单元上爆冲”的活。它有时更吃 max/reduce，有时更吃 exp，有时更吃 load/store，有时寄存器和端口的压力会突然抬头。这个时候，如果你像 SIMT 那样强行把很多资源按线程/warp 粗粒度地 partition 死，灵活性就会被自己先砍掉一截；而 SMT 的强项恰恰在于，它从一开始就不把“资源该怎么分”当成圣旨，而是当成**运行时问题**。谁现在更该占 ALU，谁更该占读口，谁更该吃 issue slot，小到一个仲裁，都可以动态分账。

这时候，前面几章讲过的那句话，就又该拿出来了：

**SMT 的灵魂，从来不是“一个核能跑几个线程”，而是“把核内资源做成池子，然后允许线程在池子里分账”。**

和架构状态强绑定、又怕时序炸裂的，优先 **partition**。
比如 ROB、RAT、部分 rename/tag 状态。因为这类东西像收银台，不像仓库；收银台一共享，抢道、互相拖累、timing 炸裂很快就全来了。

容易因为资源争抢引出死锁、验证又很难兜底的，也优先 **partition**。
不是因为 shared 不优雅，而是因为 tape-out 之前，优雅没有过片重要。

时延短、吞吐快、每线程行为模式差异大的，通常更适合 **partition**。
尤其预测相关结构，不同线程路径一旦相互污染，坏起来比家族群转谣言还快。

反过来，时延长、容量大、面积贵、天然适合摊薄的，就更偏向 **shared**。
这类东西更像仓库，不像收银台。仓库共享通常值，收银台共享容易打架。

这套原则，说穿了没有什么玄学：

**时序紧的，用 partition 买平安；**
**面积贵的，用 shared 买性价比。**

所以我一直觉得，SMT 真正有意思的地方，不在于“一个核能跑几个线程”这种海报口号，而在于：

**有了 SMT 以后，你终于可以对核内每一个模块，细粒度地定义它究竟该是 partitioned，还是 shared。**

这才是架构师真正该玩的游戏。
不是喊口号，
不是比谁缩写更时髦，
而是真正分田地，算细账

## 六、控制流这件事，SIMT 从来没有宣传册上那么优雅

SIMT 的宣传图总爱画得很美。
一群线程肩并肩，像阅兵，像鱼群，像一排排整齐的仪仗兵。可一到分支，画风立刻就变了：
“大家先别动，我看看谁往左拐，谁往右拐；没轮到你的，先把嘴闭上。”

这不是刻薄，是 NVIDIA 自己写在手册里的现实。CUDA Programming Guide 明说了：warp 里的线程按 SIMT 方式执行；一旦线程走不同控制流路径，就会发生 **warp divergence**，没走当前路径的线程会被 **mask off**，而这种分歧会直接影响利用率。更进一步，官方还提醒：为了获得高效率，同一 warp 内线程最好遵循相同控制流。换句话说，SIMT 的美，从来都带着一个隐藏前提：**大家最好别分家。** ([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/cuda-c-programming-guide/%3Futm_source%3Dchatgpt.com))

所以第一个问题来了：
**SIMT 到底有没有控制流问题？**
当然有。
而且不是“偶尔有点小麻烦”，而是**模型里就写着这门麻烦**。你可以把 SIMT 想成一支方阵：在平原上整整齐齐，非常好看；可一旦遇到岔路口，就得先把队伍拆开，再一拨一拨过。不是不能过，是过得没宣传册上那么优雅。CUDA 和 PTX 文档都指出，在较早架构里，一个 warp 共享程序计数器和 active mask；当线程落在不同执行状态或分歧区域时，线程间协作都会变得更脆弱，甚至会引出死锁风险。 ([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/parallel-thread-execution/%3Futm_source%3Dchatgpt.com))

经典的 GPU 分歧处理，本质上在干什么？
不是“让不同路径同时优雅地向前走”，而是**把不同路径串行化处理**。HPCA 2013 那篇 `The Dual-Path Execution Model for Efficient GPU Control Flow` 说得很白：在传统 SIMT 模型里，分歧后通常一次只执行一个 path，其他 path 上的线程被 mask 掉，执行是被部分串行化的；作者之所以提出 dual-path，本身就是因为他们认为传统做法没有最大化可用并行性。也就是说，分歧不是被消灭了，而是被包装成了“轮流上场”。 ([lph.ece.utexas.edu](https://link.zhihu.com/?target=https%3A//lph.ece.utexas.edu/merez/uploads/MattanErez/hpca2013_dpe.pdf%3Futm_source%3Dchatgpt.com))

再往前走一步，事情就更不像宣传册了。

现代 NVIDIA GPU 的控制流，已经不是老式教科书里那种“隐形 reconvergence stack”一句话能讲完的。那篇 2024 年的论文通过微基准和逆向分析发现，后 Volta 时代的控制流管理用了 **BSSY / BSYNC** 这样的指令对：**BSSY** 初始化一个 Bx 寄存器，设置 reconvergence point；**BSYNC** 在指定位置读取这个 reconvergence mask，把相关线程重新汇合。论文还指出，后 Volta 时代为了避免 pre-Volta 下的某些 SIMT-induced deadlock，控制流约束已经被大幅改写，程序员暴露出来的语义也跟以前不一样了。连 GPU 厂商自己都知道，这套控制流疼痛不能靠“大家继续齐步走”糊过去，必须加专门的控制流硬件与指令去兜。

**如果 SIMT 真是控制流圣杯，为什么大家还在不停给它打补丁？**

如果一种组织方式真是完美圣杯，它就不该反复长出旁门。可 NVIDIA 自己的 CUDA Binary Utilities 把这些“旁门”列得清清楚楚：**R2UR、S2UR、REDUX、UF2FP、UIADD3、ULDC**，全是 **Uniform Datapath Instructions**。其中，**REDUX** 是把向量寄存器归约到 uniform register，**UF2FP** 更是白纸黑字写着：**Uniform FP32 Down-convert and Pack**。这意味着什么？意味着连 SIMT 自己都知道：**不是所有状态都值得按“每线程一份、齐步走”来背着跑。** ([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/archive//12.0.1/cuda-binary-utilities/index.html%3Futm_source%3Dchatgpt.com))

这件事放到 AI 上，就更明显了。
8-bit、16-bit、量化、反量化、格式转换、pack、unpack，到处乱飞。你要是把所有低精度状态都硬塞进统一的 per-thread 抽象里，再靠外围硬件打补丁，那很多时候就是在拿复杂度给自己找麻烦。既然 GPU ISA 已经公开暴露出 uniform reduction、uniform pack、uniform datapath，这恰恰说明硬件设计者也很清楚：
有些值天然就是 **uniform** 的；
有些结果天然适合走 **标量捷径**；
有些 pack / down-convert 活，根本不值得让每个线程都背着一份 32-bit 私有抽象去演。 ([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/archive//12.0.1/cuda-binary-utilities/index.html%3Futm_source%3Dchatgpt.com))

**SMT-SIMD 不是没有标量，而是从一开始就把标量当正规军。**
因为它决定了这台机器在控制流变坏的时候，不会一下子从高吞吐机器跌成全员罚站。SIMT 一旦遇到严重分歧，本质上是在一支大部队里不断 mask 掉一批人、再拉回一批人；而 SMT-SIMD 的味道完全不同：它本来就有自己的 **标量 lane**，而且这个标量 lane 不是“uniform 小旁门”，更不是摆设，而是一个可以**乱序执行、独立调度、真干活**的正式执行面。这个标量的lane实际上可以做到一个4发射的OOO乱序多线程小CPU。支持4个不同divert PC并发执行。

向量 lane 负责大开大合，标量 lane 负责控制、谓词、地址、尾部、零碎活。最妙的是，这个标量 lane 本身还是 OoO 的，所以哪怕向量部分一时吃不上力，机器也不会立刻陷入“宽机器空转”的尴尬；最差的退化形态，不是整排 lane 一起陪绑，而是**退化成很多并行的标量线程**。这不是“小修小补”，这是退化路径的哲学差异：前者是“缩而不死，退而不崩”，后者更像“一分歧就让一部分人先闭嘴旁观”。这段是架构判断，但它和前面的证据链是连着的：既然 SIMT 自己都要专门长出 uniform datapath，就说明控制和统一状态本来就是一门单独的活。 ([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/archive//12.0.1/cuda-binary-utilities/index.html%3Futm_source%3Dchatgpt.com))

所以反过来看，为什么 SMT-SIMD 在很多 AI 场景里会更顺手？
因为它不装。
该 pack 的，显式 pack；
该 unpack 的，显式 unpack；
该标量控制的，交给标量 lane；
该向量吞吐的，交给向量通路；
该退化成并行标量线程的时候，也不至于把整排宽执行体一起拖下水。
它更像一个会过日子的掌柜：算盘归账房，搬货归伙计，刀工归厨子，点火归灶头。谁擅长什么，就让谁干什么。SIMT 的强项当然还在——统一线程语义、组织大规模吞吐很方便——但在控制流分歧、uniform 值、归约结果、低精度 pack/unpack 这些地方，它越来越像一件大袍子里偷偷缝了很多暗袋。暗袋当然有用，但暗袋的存在本身就说明：**这袍子并不是所有场合都那么合身。** ([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cuda/cuda-c-programming-guide/%3Futm_source%3Dchatgpt.com))

复杂度一直都在那里，看是谁兜住了

## 九、未来真正有生命力的 AI 处理器，更像 SMT-(CUBE+SIMD) 的多线程 CPU 形态

所以今天这场辩经，我真正想讲的，不是“GPU 已死，CPU 当立”这种低级口号。
我的答案一点也不时髦，甚至有点不讨喜：

**未来真正有生命力的 AI 处理器，不该是纯粹的 SIMT 神教。**
它更可能是一种 **SMT-(CUBE+SIMD)** 的多线程 CPU 形。CUBE依然是第一公民。

注意，我说的不是“CPU 复辟”。
不是把今天的 AI 芯片重新做成老式 superscalar，再拿几本教科书来给它开光。
我说的是：**把 CPU 真正值钱的骨头、GPU 真正值钱的骨头、NPU 真正值钱的骨头，重新装成一具新身体。**

CPU 真正值钱的是什么？
不是 ISA 祖宗牌位，也不是“通用”二字的情怀税。
CPU 最值钱的，是**动态调度、乱序执行、可回滚、会分账、会退化、会在不规则场景里继续挖独立性**。这不是我在替 CPU 招魂，连 GPU 阵营自己都已经开始往这个方向松动：SOCGPU 用不做寄存器重命名的轻量 OoO 机制去挖 thread 内部的 ILP；TURBULENCE 更进一步，干脆从 ISA 下手，用 distance-based ISA 来把 GPU 上的 OoO 做得更便宜。两篇工作的共同潜台词都很明确：**问题的本体，不是线程还不够多，而是运行时还有没有独立性可挖。**([UPCommons](https://link.zhihu.com/?target=https%3A//upcommons.upc.edu/bitstreams/485b8c5d-b2e7-4621-8aff-bfc920dddabb/download%3Futm_source%3Dchatgpt.com))

GPU 真正值钱的是什么？
不是“线程多”这三个字本身，而是**对大规模吞吐、宽执行体、层次化分块与海量并行组织的工程经验**。
NVIDIA 的 CUTLASS 其实已经把这种思维写进了模板库：一个 GEMM kernel 被拆成 **collective mainloop** 和 **collective epilogue**，主循环做 tile 上的 MMA，尾声单独处理 beta·C、缩放、融合后处理。FlashAttention 则更进一步，把 attention 直接写成 **IO-aware** 的 tiled algorithm，核心目标不是“算术多快”，而是减少 HBM 和片上 SRAM 之间的数据搬运。你看，这说明真正成熟的 AI 内核，本来就不是“纯算子”，而是“算子 + 分块 + 搬运 + 尾部”的整体。([NVIDIA Docs](https://link.zhihu.com/?target=https%3A//docs.nvidia.com/cutlass/latest/media/docs/cpp/gemm_api_3x.html%3Futm_source%3Dchatgpt.com))

NPU / CUBE 真正值钱的又是什么？
不是“矩阵单元”这个词本身，而是**在规则密集计算上的DSA定制电路压路机能力**。
它的意义从来不是“什么都能干”，而是在矩阵主战场上狠狠干穿。
所以我脑子里那台未来机器，不该是一尊“矩阵神像”，而应该是一台会分工的机器：
前面有**标量脑子**，
中间有**做大了的 SIMD 筋骨**，
核心有**CUBE 重炮**。
三者不是并排坐着开会，而是活在同一个 OoO/SMT 核里，由同一套调度和资源分账逻辑来组织。

这里最关键的一点，不是“有标量、有向量、有矩阵”，谁都能画三块框图。
真正关键的是：**标量 lane 必须是正式执行面，而且最好是乱序的。**
为什么？因为它决定了这台机器在逆风时怎么退化。
如果你的向量/矩阵世界一旦遇到控制流、尾部、格式转换、pack/unpack、gather/scatter、少量不规则地址，就只能让整排宽执行体陪着一起发呆，那这台机器本质上还是“顺风猛、逆风脆”。
而如果你的标量 lane 自己就是一条能独立调度、能乱序、能接住零碎活的正式通路，那么最坏的退化形态就不会是“全员罚站”，而是**退化成很多并行的标量线程**。

因为这套身体结构，最符合今天 AI 负载真正的地形：

并行度高的时候，它能铺开。
矩阵面狠狠干，向量面喂数、搬块、做局部变换，标量面管控制和编排。

并行度塌下去的时候，它又能收回来。
reduce、softmax、sampling、尾部、地址和轻量控制，不会逼着整排宽执行体一起陪绑。

遇到 latency，它不只会“多挂几个候补 warp”，而是会先在线程内挖 ILP，再在线程间找 TLP，再用 OoO 和 LSQ 把独立性一层一层抠出来。

遇到控制流，它不会把所有问题都包装成 active mask 和 reconvergence 的后台痛苦，而是让标量 lane 去接住本来就该由标量干的活。

遇到低精度、uniform、pack/unpack，它也不会硬把一切都塞回 per-thread 的私有抽象里，而是按部就班把AVX512这样的SIMD指令用好。

![image](https://pic2.zhimg.com/v2-03708a34d0baa90996f8fc35bd8a62bb_1440w.jpg)

而写到这里，全篇其实也该真正落回到那个最不浪漫、却最决定成败的问题上了：
 如果未来这台机器，真的要让标量、向量、矩阵三套执行面活在同一间院子里，
 那它们靠什么互相喂数？
 靠什么共享局部数据？
 靠什么既不把带宽烧穿，又不把时序炸掉？

也就是说，哲学讲完了，战争地图也画完了，
 接下来就轮到城门口那道最硬的数学题了：

**当 向量和矢量 要共享一块大 SRAM 时，这个 超宽的crossbar，到底该怎么设计？**
