# Hotchips 2026 干货和私货分享 - 内存

- 类型：文章
- 原文：[知乎文章](https://zhuanlan.zhihu.com/p/2075617575262762743)

又到一年一度的 **Hot Chips 大厂魔法对轰环节**。

以前看 Hot Chips 是个体力活，几十上百页 PPT，一会儿被 NVIDIA 的绿色激光扫一遍，一会儿被 AMD 的红色火球砸一下，Intel 再从旁边扔过来一块蓝色 chiplet，红绿蓝三家凑齐，差不多就是半导体行业自己的交通灯。今年有了 Agent 以后稍微幸福一点，整理资料、扒参数、顺着架构图找论文的效率高了很多，终于可以把省下来的时间用来干一件更重要的事情：**想想这帮人为什么非得这么设计。菊厂的架构也不能落伍啊。**

![image](https://pic4.zhimg.com/v2-31a97477e100939893ea8bb6374a5651_1440w.jpg)

当然，大家看 Hot Chips 的第一反应还是先找最刺激的那几页：多少 PFLOPS，多少 TOPS，HBM 又涨到多少 TB/s，今年 Tensor Core 又发明了一种名字更长、bit 数更短的浮点格式；最好再配一张柱状图，自己的柱子顶到天花板，对手趴在下面当比例尺，这才算完成大厂发布会的基本礼仪。

![image](https://pic4.zhimg.com/v2-c075089bacf0feefd19c6d11fd4b869b_1440w.jpg)

NVIDIA、AMD、Intel 还是熟悉的绿、红、蓝，只是今年的剧情开始有点变化。AMD 继续红着眼睛堆 chiplet，Intel 反而开始认真研究一个以前听起来不太像 Intel 的问题——怎么把芯片和封装做便宜一点；NVIDIA 的 GPU 本身倒越来越像稳步迭代，看多了甚至会让人怀疑老黄是不是准备接过“牙膏厂”的历史称号，不过再往后翻几页就会发现，人家现在挤的已经不是 GPU 这一管牙膏了，而是 CPU、DPU、交换机、800 VDC、液冷和整座机房，连进水温度都要管，优化目标也从“GPU 能算多少”变成了“**这一兆瓦电最后到底能卖多少 Token**”，但是继续依赖台湾的供应商，可靠性能有保障吗？

只要不是比GPU，比系统的话，菊厂还能进来掰掰手腕。

更有意思的是三星、SK hynix、Micron 这些以前在 GPU 后面负责安静送饭的内存厂商，今年存在感越来越强。Samsung 已经不满足于让 HBM base die 当高级接线板，memory controller、repair、telemetry，甚至 processing element 都开始往里面塞，继续发展下去，嘴上卖的是内存，手里的活已经越来越像半颗 SoC；SK hynix 面对的则是另一种烦恼，HBM 从 12Hi 往 16Hi、20Hi 堆，总高度不能无限涨，die 得越来越薄、gap 越来越窄、bump 越来越密，最后 hybrid bonding 从“先进封装未来技术”慢慢变成了“**这楼再往上盖，不换施工方法可能真盖不动了**”。以前我们问 HBM 多快，现在还得顺便问一句：这栋楼热不热、弯不弯、良率怎么样，最后有没有房产证。

这时候再回头看那些几十 PFLOPS 的 GPU，就会发现真正让机器停下来的东西越来越不像乘法器：权重还在路上，KV Cache 已经塞满了；CPU 还在处理上一个 tool call，GPU 等着下一次 dispatch；scale-up fabric 某一个 plane 打个喷嚏，几十张卡一起停下来研究人生；最后机房工程师推门进来说，电已经 provision 到顶了，于是所有人只能望着机架里剩下的空位欣赏数据中心房地产。

这差不多相当于晚高峰堵在北京四环，车已经排了十公里，发动机工程师兴奋地告诉你：

**好消息，明年再加 200 马力。**

马力当然还得加，只不过真正困难的事情，已经沿着数据一路往外扩散了。

**RISC-V 则依然让我有一点恨铁不成钢**。Vector 有了，Matrix 也在路上，profile 越写越厚，生态图越画越大，但真正到了最烧钱的大模型 AI 主战场，大家还是习惯让 RISC-V 坐在 CPU、Host Processor 和控制核那一桌，真正拿它做核心 AI Compute 的依然不多。反过来看，这也说明今天的 ISA 战争早就不是“多几条矩阵指令谁就赢”，真正的考试是 Ubuntu 愿不愿意维护十五年，CUDA 敢不敢相信你的 PCIe coherency，汽车 OEM 敢不敢把功能安全压上来；ISA 只是高考，后面还有 ACPI、platform、toolchain、qualification 和漫长的软件生命周期。

所以今年把这些 Slides 放在一起看，我最大的感受反而不是哪家又多了几个 TOPS，而是一个越来越明显的变化：

**die boundary 当然还在，工程师每天照样得画 floorplan，timing closure 也不会因为我们开始谈 AI Factory 就突然变得通情达理；但系统边界，早已经跑出了封装。**

HBM base die 开始长成 SoC，GPU 一路长成 72 卡机架，chiplet 除了传 bit，还得商量谁先启动、地址怎么算、中断发给谁、一颗 die 挂了其他兄弟要不要陪葬；软件也越来越没办法假装自己完全不知道下面发生了什么。

所以这次 Hot Chips 真正值得看的，不是谁家的柱状图又高了一截。

而是**当算力越来越便宜以后，那些过去被我们画在架构图边缘、甚至嫌麻烦干脆不画的东西，正在一个接一个走到舞台中央。**

## 第1章 为啥最近内存突然变得这么贵了？

如果你最近手搓过AI服务器、买过内存，或者只是随手看了一眼 HBM、DRAM 的报价，大概率都会产生一个朴素的疑问：**内存这东西到底发生了什么，怎么突然又贵起来了？**

**Memory Wall还没撞到，先撞到了Money Wall**

![image](https://pic4.zhimg.com/v2-36e1d18da1472fa59c85e4daf13ffdf5_1440w.jpg)

很多人第一反应会把原因归结成 AI 抢产能，这当然没错，但只说“AI 需求大”其实和解释北京早高峰说“因为车多”差不多，方向完全正确，信息量基本为零。真正值得算的是，为什么这一轮 AI 对存储产业的冲击比过去任何一轮服务器升级都更猛烈，因为它并不是简单多买了几根内存条，而是在同时做三件很不讲武德的事情：**一边疯狂增加需要搬的数据量，一边把 DRAM 从面积效率更高的 DDR 转去做面积效率更低的 HBM，同时还要求整个产业链在一两年内完成原本需要多年才能完成的扩产。**

这三笔账如果分开看都还能忍，乘起来以后事情就开始失控了。

这里最关键的一笔账其实特别简单：**同等容量下，HBM 大约需要 DDR 3 倍的 DRAM die area。**

这笔面积账平时藏在那些漂亮的 TB/s 后面，很容易被当成采购部门或者存储厂商自己的烦恼；可一旦 AI CapEx 突然往上冲，它就会沿着整条产业链反向传导。

同样一片 wafer，转去做 HBM 以后，最终能够交付的 bit 数反而下降；

与此同时，DRAM wafer volume 已经长时间没有大幅扩张，新产能从设备安装到真正可用又要 **两年以上**。

订单可以一个季度改三次，昇腾卡可以一年一代，晶圆厂却显然不会因为电话会气氛很好，第二天早晨就在隔壁地里自动长出一条新产线。

所以这轮内存涨价真正原因，是需求和供给的时间常数完全不在一个量级。这次Hotchips里面讲到，branded DRAM 和 NAND 的价格增长曾分别达到 **7.1×** 和 **6.9×**；这两个倍数缺少统一的起止周期，当然不能拿来包装成一条很精密的长期预测，但至少足够说明一件事情：**供给弹性已经远远小于需求变化的速度。**

![image](https://pica.zhimg.com/v2-b0a5b9bdcd57840bd59c75b91195f5f6_1440w.jpg)

需求抬升、同容量约 3 倍的裸片面积以及超过两年的扩产周期相互放大，memory wall 因而从芯片内部一路扩散到晶圆和封装产能。

AI compute 的增长大约是 **3×/2 years**，HBM bandwidth 却低于 **2×/2 years**。于是问题越来越像一个厨房：吃饭的人两年翻三倍，后厨出菜能力还不到两倍，最后大家开始研究怎么把盘子端得更快，却发现真正不够的是灶台。

把 DDR 和 HBM 放在一起看，这个差别尤其直观。一个 8-channel DDR5-4800 server，可以用大约 **307 GB/s** 的带宽服务 **1 TB** 左右的容量；8×HBM3 GPU 则用大约 **5.3 TB/s** 的带宽服务 **192 GB**。前者围绕容量和扩展性优化，后者则用明显更少的容量，换来接近一个数量级的带宽提升。两者本来就不是简单的“旧内存”和“新内存”，而是完全不同的设计点。

HBM3E 内部可以做到：**256 I/O × 8 Gbps = 256 GB/s**

而同样 8 Gbps 的 DDR5 core，如果只有 8 个 I/O：**8 I/O × 8 Gbps = 8 GB/s**

这几十倍的内部带宽，并不是因为 HBM 里的 DRAM cell 突然开悟了，而是靠更多 I/O、更多 bank、更多 channel，以及 TSV 和先进封装，硬生生用并行度堆出来的。代价也非常直接：同容量仍然大约需要 **3× silicon**。天下没有免费的带宽，只是不同架构喜欢把账单寄到不同部门。

![image](https://pic2.zhimg.com/v2-5324729386557f273cc52ed747b75c8b_1440w.jpg)

一个 8 stacks × 12-high 的示例里，把所有 memory silicon 累加起来，总面积可以达到 12,344 mm²，超过 typical GPU silicon area 的 8 倍。

更极端的是 HBM4 SiP。这个数字当然不是说 interposer 上真的躺着一块 12,344 mm² 的超级 DRAM，而是把所有垂直堆叠的 memory die 面积加总；但它把晶圆投入、compound yield 和测试成本写得非常坦白：今天一套 AI accelerator 买到的每一个 TB/s，背后都站着一大排 Roofline Model 里从来不会画出来的硅。

![image](https://picx.zhimg.com/v2-6a45667a6cd1cd00015b5ee10529dc4f_1440w.jpg)

大家一起韬起来

## 第二章：三星、Micron 的 HBM，将来会何去何从？

所以我对 HBM 这条路线的判断其实很简单：继续提高 pin speed 当然仍然必要，但它已经不足以定义问题。

以后每增加一级带宽，我觉得都应该顺手追问三件事：**这些 bit 从哪里来，经过多长的物理距离，每搬一个 bit 又花了多少硅、多少封装和多少瓦。**

当数据开始比乘法更贵，我们究竟应该在哪里把它停下来，在哪里把它处理掉，又有哪些过去默认不能碰的物理边界，已经到了该重新画一遍的时候。

如果沿着 HBM1 一路看到 HBM4，会发现 HBM 这些年的变化其实很有意思：表面上大家还在比赛“这一代又多了多少 TB/s、又能堆多少层”，真正发生的事情却是，**最下面那颗 Base Die 正在一点一点从接线板长成一颗 SoC。**

传统 HBM 的分工原本非常干净。上面的 **C-die，也就是 Core Die**，主要负责存 DRAM cell；下面的 **Base Die** 负责把 GPU 发来的命令和数据接进来，再通过 TSV——Through-Silicon Via，贯穿硅片的垂直通孔——送到上面的 DRAM，同时顺手承担 Direct Access、MBIST、IEEE 1500 这些测试功能。这个架构好理解，DRAM 厂商管存储，GPU 厂商管计算，中间通过标准接口握个手，大家各自回去做自己的 sign-off。

问题出在 HBM4。

HBM4 的 Base Die 已经开始进入 **4 nm logic process**，旁边的 GPU、NPU 这一类 xPU 大约已经在 3 nm 左右，后面还会继续往更先进节点走。于是一个非常朴素的问题就出现了：**我都已经花钱做了一块 4 nm 的逻辑硅，真的还准备让它一辈子负责接线吗？**

这就像在深圳湾买了一套房，最后决定拿来堆纸箱，物理上当然可以，财务上多少让人有点心疼。

所以三星公开的 HBM 路线里，我觉得真正值得看的并不是某一代 pin speed 从 14 Gbps 涨到 28 Gbps，而是 Base Die 的职责开始明显扩张：先把 PHY 做短，把 Memory Controller 搬下来；再加入 RAS、telemetry、repair 和 test；最后甚至考虑 Processing Element 和真正的垂直 xPU integration。Micron、SK hynix 的具体产品路线和叫法可能不同，但面对的是同一组物理约束：**当 HBM 的接口越来越宽、功耗越来越高，而 Base Die 自身又越来越像先进逻辑芯片时，compute 和 memory 过去那条很清楚的组织边界，就越来越难继续保持原样。**

先看 HBM 自己为什么会走到这里。

今天一颗 HBM 已经不是我们传统印象里“一组更快的 DRAM”。典型 HBM 有大约 **1–2K 个 I/O**，每个 I/O 可以跑 **8–16 Gbps**，总带宽做到 **1–5 TB/s**；上面的 DRAM 可以堆 4、8、12、16 层，形成几十 GB 容量。HBM4 又把 Data I/O 从 1024 翻到 **2048**，channel 从 16 增加到 **32**，pseudo-channel 进一步做到 **64 个**。

![image](https://pic2.zhimg.com/v2-bacc806c85b05ac581014047df61a6e9_1440w.jpg)

这里的 **pseudo-channel** 可以简单理解成：以前一个大仓库开一个大门，现在觉得排队太严重，于是把大门继续拆成几个相对独立的小门，让更多请求并行进出。HBM1 的这类通道宽度还是 128 bit，后来缩到 64 bit，再缩到 32 bit；与此同时 burst length 从 2 增加到 4、8，prefetch 维持在 256 bit，希望通过更细粒度的独立访问机会，把 DRAM array 喂得更充分。

听起来非常合理，然后硬件开始收账。

channel 越多，command state 越多；bank 越多，调度状态越多；ECC、refresh、repair、TSV、PDN 全部跟着变复杂。HBM3E 每颗 die 已经有 **128 个 bank**，HBM4 再增加到 **256 个**。我们平时很喜欢说“增加并行度”，这四个字写在架构 PPT 上只占一行，真正到了 RTL 和 physical design，每一级并行都会长出 queue、arbiter、state machine、wire 和 testcase。

所以天下没有免费的 bandwidth。

只是账单有时候寄给 PHY，有时候寄给 scheduler，有时候寄给封装厂。

三星的第一步其实相当务实：**先把那些明明离 DRAM 很近、却历史上一直放在 GPU 里的东西搬回来。**

传统 standard HBM4 的 PHY 面积大于 **8 mm × 4 mm**，custom HBM4 用更紧凑的 D2D，也就是 Die-to-Die 短距接口后，大约可以做到 **8.5 mm × 1.5 mm**，channel depth 也可以从 **5.5 mm 缩到 2 mm**。

PHY 是 Physical Layer，负责真正把数字逻辑变成高速电气接口。以前 GPU 和 HBM 在 interposer 上隔着毫米级距离通信，所以需要一套比较重的 HBM PHY；距离缩短以后，接口电路就可以更轻、更省电，同时还释放 xPU 上的一块面积。

![image](https://pic4.zhimg.com/v2-c619290d529ae08e58eb0d3e045013cb_1440w.jpg)

接下来最自然的动作，就是把 **Memory Controller 也搬到 Base Die**。

这一步比搬 PHY 更重要，因为 Memory Controller 不只是“收到地址以后帮忙转发”，它还要决定什么时候发 ACT、READ、WRITE，怎么避开 bank conflict，怎么插 refresh，多个 channel 之间怎样调度，甚至 QoS 怎么保证。以前这些决策天然属于 GPU，因为控制器就在 GPU 里面；一旦搬到 Base Die，HBM 就第一次开始拥有更多“自己决定如何被访问”的能力。

![image](https://picx.zhimg.com/v2-b2100c3dcef93a3311c0a2d7f45139c1_1440w.jpg)

从架构角度，我觉得这是一个很关键的变化。

因为从这一刻开始，HBM 已经不再只是一个被动 device。它开始知道自己的 bank、temperature、repair state，也开始能自己安排访问。嗯，海思也是不是也这样做了？

### 三星的韬定律怎么做？

PHY 缩下来以后，事情并没有就此结束，反而会出现一个很典型的芯片设计悖论：**每搬一个 bit 的能耗下降了，局部却可能更热了。**

原因很简单。传统 HBM PHY 占的面积比较大，功耗摊得也开；换成更短距、更紧凑的 D2D 以后，channel 变短，pJ/bit 确实能下降，xPU 上原本被 HBM PHY 和 controller 占掉的面积也可以腾出来，但同样甚至更高的 I/O 吞吐被塞进更小的区域以后，power density 会迅速抬头。从 HBM4E 大约 **14 Gbps、0.5 W/mm²**，走到 HBM5 目标的 **>28 Gbps、>2.0 W/mm²**，速度超过两倍，局部功率密度却可能超过四倍。于是 Samsung 又引入 **HPB（Heat Path Block）**，可以理解成专门给高速 PHY 修一条低热阻的“散热高速公路”；当 HPB 覆盖高功率 PHY 区域超过 50% 时，标称 peak temperature 可以下降 **35% 以上**。

![image](https://pic1.zhimg.com/v2-306dbb62189b2b7d6382d446753d632c_1440w.jpg)

这类结果特别符合芯片工程的日常经验：**系统功耗下降和局部热点恶化完全可以同时发生。** Power spreadsheet 上的一片绿色，不代表 thermal map 上就不会出现一个鲜红色的火山口，热仿真也从来不会因为 PPT 首页已经写上“Energy Efficient”就主动给项目组留面子。

### **第四章 真正更大的变化，是 Base Die 接下来还准备继续长东西。**

Memory Controller 搬下来以后，最自然的下一批功能不是马上塞一个巨大的 Matrix Engine，而是先把和 DRAM 自身状态高度相关的能力一起搬下来，包括 **RAS（Reliability、Availability、Serviceability）**、temperature / voltage / process / aging telemetry、OD-ATE/PGEN 片上测试、SRAM repair，甚至 external memory extension。原因并不复杂：这些东西越靠近 DRAM，掌握的信息越完整，响应也越直接。

![image](https://pic3.zhimg.com/v2-02119d39af7757f079c7b376b15bdd7c_1440w.jpg)

比如 repair。传统 C-die 通常预留固定的 spare row 和 spare column，某一行坏了，就用备用行顶掉，比较像每层楼自己在地下室放几个备胎。Base Die 如果有 SRAM 和更复杂的逻辑，就可以做更细粒度的 **fail-address decode + redirection**，甚至把冗余资源在多个 channel 之间共享；原来“这一层 DRAM 自己修自己”，逐渐变成“整个 HBM stack 统一管理坏块”。对 yield 和 field reliability 来说，这种能力往往比在 Base Die 里再多塞几个 TOPS 更实在。

再往前一步才轮到 **Processing Element，PE**。Near-Memory Computing 最容易讲成一句特别好听的话：计算离数据更近，所以一定更高效。真正做系统时没这么简单。假设一个算子要扫描 1 TB 数据，最后只筛出 10 GB 结果，那么把 filter、search、compression、简单 reduction 放到 memory side，很可能非常划算，因为真正省掉的是几百 GB 甚至 TB 级的 D2D traffic；可如果一个 GEMM tile 搬到 GPU 后可以在 Tensor Core 里反复复用几十上百次，那么硬把计算塞到 Base Die，只会得到一个算力更弱、面积更紧、散热更差，还顺手需要新 compiler backend 的小型加速器。

所以我判断 PE 是否值得下沉，不会先问“Base Die 还有多少空面积”，而会先问一个更直接的问题：**这个 operator 搬下来以后，到底少搬了多少 bit？**如果数据量没有明显缩小，Near-Memory Computing 很可能只是把 compute area 从一个地方搬到另一个地方；如果能够先过滤掉 90%、99% 的数据，那节省的数据移动功耗才是真正的收益。芯片里最危险的一种资源，往往就是 floorplan 上那块“看起来还空着，不如塞点东西”的面积，compiler team 通常会在后面的项目周期里告诉你，它其实一点也不空。

## Samsung 路线里最激进的一步，是韬-**zHBM**

![image](https://pic3.zhimg.com/v2-f231e53b58814bc70d840f9d4451ddb0_1440w.jpg)

zHBM 的结构其实可以理解成把传统“GPU 旁边放 HBM”的 2.5D 关系，直接折成一栋垂直建筑：最上面是多层 **DRAM Core Die**，中间加入承担 bank 通信、测试和部分 Base Die 功能的 **Interlayer**，最下面直接就是 **xPU SoC**，DRAM 通过 TSV 和 distributed I/O 在 bank 附近向下连接计算逻辑，整个 stack 再落到 package substrate 上。这样一来，传统路径里 `xPU PHY → Interposer → HBM PHY → Base Die` 那一大段毫米级水平传输被压缩成几十微米甚至未来微米级的垂直路径，大块 PHY、SERDES、data alignment 和部分 DQ I/O 都有机会被拿掉；收益当然不只是少几个 cycle，真正值钱的是减少电容充放电和重复的数据搬运，公开目标可以做到约 **70% I/O power reduction**，在 1200 W GPU、4×HBM 的假设下大约能省 **100 W，也就是整颗 GPU 的 8.3%**。

从体系结构角度看，zHBM 最迷人的地方恰恰不是“DRAM 又快了一点”，而是它直接把 memory 和 compute 之间那段最贵的物理距离删掉了——算力一个 MAC 都没增加，光靠把楼上仓库搬到工位正上方，就省出了一颗十几年前高端 CPU 的功耗预算，这种优化多少比再给 Tensor Core 刷几个 TOPS 来得朴实。

所以看到这里，我对三星、Micron 这些 HBM 厂商未来往哪里走，判断其实很简单：**Base Die 一定会越来越像逻辑芯片，但它不会因为多了几平方毫米先进工艺，就突然产生“我也要做 GPU”的冲动。** 最先搬下去的，一定是 controller、telemetry、repair、test，以及 compression、filter、copy、reduction 这类能够直接减少数据搬运的功能，因为这笔账最好算——做完以后到底少走了多少 bit，一眼就能看出来；至于复杂计算，只要开始要求 compiler 做 placement、runtime 管 synchronization、framework 理解 memory-side execution，那块看起来“闲着也是闲着”的 Base Die 面积，很快就会被软件团队用两年工期重新标价。

这其实非常符合海思一直讲的 **韬定律（τ 定律）**。摩尔定律习惯问晶体管还能不能再小一点，τ 定律更关心的是：**一项任务真正浪费的时间到底在哪里，我们能不能把那段等待、传输、同步和无效搬运继续压短。** 对 HBM 来说，过去主导 τ 的可能是 DRAM 本身，现在越来越多时间和能量花在“把数据从这里送到那里”。于是最有效的优化未必是让 Tensor Core 再快 20%，而是把几毫米的 interposer 路径压成几十微米的垂直连接，把一部分 controller 和 processing 挪到数据旁边。说得通俗一点，堵车的时候继续给发动机刷马力当然很励志，**韬定律更喜欢先看看能不能把路修短。**

zHBM 就是这件事最极端的版本。为了省下大约 100 W、减少几毫米的数据路径，我们开始愿意重新画 xPU 与 DRAM 的物理边界；可 τ 从来不是只看 latency 的单变量游戏，路径缩短以后，cross-die timing、PDN、thermal、bonding yield、repair、软件接口和供应商可替换性都会重新进入账本。真正的全栈 τ 优化，不是某一层跑得最快，而是在功耗、成本、可靠性和制造能力约束下，让**最终任务的有效时间常数继续缩短**。有时候最短的电气路径，会换来最长的跨公司会议，这也是系统架构必须一起算进去的现实。

### 第五章 HBF：High Bandwidth Flash 到底靠不靠谱？

Hotchips里面这个名不见经传的OXMIQ公司，再到处宣扬HBF的好处，想成为下一个三星，到底靠不靠谱啊？

![image](https://picx.zhimg.com/v2-325bafc99d5b63adb189faf60480f827_1440w.jpg)

OXMIQ 讲 HBF（High Bandwidth Flash）这个故事的时候，切入点其实抓得很准：**既然今天大模型越来越像“容量怪兽”，而 HBM 每 GB 又贵得离谱，为什么不把大量不那么热的数据放进 NAND Flash，再给 Flash 做一条足够宽的接口，让它进入 GPU 的 memory hierarchy？**

这个问题不能简单回答“Flash 太慢”，因为大模型，尤其是 MoE，确实正在把 capacity 和 bandwidth 这两个过去经常绑在一起的问题拆开。可以用两个参数来看这件事：`β` 表示单位容量成本，`α` 表示每 GB 容量能够提供多少带宽。HBF 大约处在 `β≈1×、α≈1–7 GB/s/GB`，HBM 则大约是 `β≈10–14×、α≈40–100 GB/s/GB`。所以 HBF 最诱人的地方非常明确：**同样的钱可以买到多得多的容量；问题也同样明确，每买到 1 GB，顺手买到的带宽少了一个数量级。**

这也是为什么 HBF 不能被理解成“便宜版 HBM”。HBM 像一个面积不大的仓库，却开了几百个装卸口，叉车二十四小时横着开；HBF 更像旁边突然批了一块巨大的工业园，用地便宜得令人感动，但进出园区的路没有同比变宽。模型如果只是要求“东西必须放得下”，HBF 非常漂亮；一旦要求“每个 decode step 都要把大量东西及时搬出来”，你很快就会发现自己买了一大片仓库，最后只是为了凑总带宽。

MoE 正好把这个矛盾暴露得很清楚。假设 batch size 是 `B`，专家总数 `N`，每个 token 激活 `k` 个 expert，那么一个 batch 联合访问到的 expert 比例可以近似写成：

`1 - (1 - k/N)^B`

单个 token 看起来非常稀疏，可能只访问几个 expert，所以把其余专家丢到 HBF 里似乎天经地义；可 batch 一大，不同用户命中的 expert 集合不断做并集，原本所谓的“冷专家”会越来越热。比如 `k/N` 即使很低，只要请求之间 locality 不够强，`B` 足够大以后，联合访问集合仍然会往整个 expert pool 靠近。这个时候问题就从“模型装不下”变成了“模型虽然装得下，但来不及读”。

所以 HBF 的成本其实应该写成：

`$mem = β · max(C, I·b/α)`

这里 `C` 是把模型和状态装下需要的容量，`I` 是目标 token rate，`b` 是每一步需要读取的数据量。前半项代表“为了容量买多少”，后半项代表“为了带宽被迫买多少”。当 workload 主要受容量约束，HBF 的低 `β` 很值钱；一旦跨过 bandwidth wall，系统开始为了凑 TB/s 不断增加 HBF device，便宜容量就会变成大面积闲置。

这也是为什么 OXMIQ 给出的几个系统例子，方向上有启发，但更应该当作**设计空间分析**，而不是产品结论。比如 HBM-only 可以做到大约 **288 GB、22 TB/s**，all-HBF 则可以拉到 **4 TB 级容量、12.8 TB/s**。低 batch、大模型场景下，一张 HBF 卡可能就能把原本需要多张 HBM GPU 才装得下的模型塞进去，看起来非常划算；可用户数继续增加以后，系统新增 HBF 的原因已经不是“装不下”，而是“喂不动”。这时候 `$/GB` 仍然很好看，`$/token` 已经开始变脸。

HBF 真正让我觉得可能成立的地方，是那些**访问比例长期很低、又占用巨大容量的数据**。例如 MoE 的冷 expert、稀疏 attention 下的大量冷 KV、prefix cache，这些数据平时占着几百 GB 甚至 TB，但真正每一步访问的只是很小一部分。Kimi-K3 这类模型里，绝大多数权重都落在 expert pool，而真正需要常驻高速层的 attention、router 和其他热权重只是其中一部分；如果软件能比较稳定地判断冷热，把热权重留在 HBM，把冷 expert 放进 HBF，这个层次是说得通的。反过来，full attention 每轮都扫大量 KV，或者 dense model 每个 token 都得重新读一遍大块权重，HBF 就很难靠容量便宜把带宽差距遮过去。

真正让我对 OXMIQ 保持距离的，并不是这个理论不成立，而是**从理论成立到产品成立，中间那段工程几乎还没有被证明。**

HBF 不会像 L2 Cache 一样，焊上去以后 GPU 就自动知道怎么用。它本质上还是 NAND，必须经过 controller、ECC、wear leveling、garbage collection、地址映射和 DMA；公开方案里，HBF Grade 1/2/3 的最大用户带宽分别大约是 **0.384 / 1.536 / 3.072 TB/s**，想把这种带宽真正打出来，还要求比较大的事务，比如 **64 KB read、1 MB write、64 KB alignment**。如果真实 workload 是一堆零碎、随机、不可预测的 expert 或 KV access，那么这些请求谁来合并，prefetch 提前多少，miss 以后怎么办，马上就会变成新的 critical path。

然后软件账单才刚刚开始。

HBM 和 HBF 两层谁负责 allocator？tensor placement 谁决定？哪些 expert 要 pin 在 HBM，哪些可以留在 HBF？prefetch 错了以后是 stall，还是多占一份 HBM？runtime 如何根据实时 batch 和 expert locality 调整 placement？Flash 本身还有 retention 和 endurance，85°C 上电保持时间大约只有 **24 小时**这一类器件特性，也意味着系统需要 host-managed lifecycle 和 endurance telemetry。硬件架构图里加一个“HBF Pool”只需要画一个方框，真正让 vLLM、SGLang 或其他 serving runtime 长期稳定管理它，工作量显然不是一个方框。

它指出了一个很真实的趋势：未来 AI memory hierarchy 绝对不会只有“所有东西都塞 HBM”这一条路，冷 expert、稀疏 KV 和超大模型驻留确实需要一个比 SSD 更靠近计算、又比 HBM 便宜得多的新层级；但这个层级最终是不是 HBF、接口长什么样、runtime 怎么管理、需要多少 HBM cache、能不能稳定获得真实 `$/token` 优势，都还没有闭合。

### 第六章：SK hynix：HBM 再往上堆，真正卡住的已经不是 DRAM

海力士这次在 Hot Chips 2026 讲下一代 HBM 又能做到多少 TB/s”，甚至也不是展示自己又把 DRAM 多叠了几层。

它真正想传递的消息更直接：

**HBM 的 scaling 已经越来越像一个封装问题。**

以前我们看 HBM roadmap，很容易沿着一条很熟悉的路径理解：DRAM density 增加一点，pin speed 再提一点，stack 从 8Hi 变成 12Hi，再往 16Hi 走，最后 bandwidth 和 capacity 自然跟着上涨。可 SK hynix 这场演讲花了相当多篇幅去讲 TSV、wafer thinning、warpage、underfill、KGSD、thermal resistance 和 hybrid bonding，实际上是在提醒大家：到了 16Hi 以后，“再加四层”根本不是在 PowerPoint 上复制四个 DRAM 方框那么简单。

![image](https://pic2.zhimg.com/v2-db880c679080c1cd5629996e4da8277d_1440w.jpg)

12Hi 往 16Hi 最能说明这个问题。

层数从 12 层增加到 16 层，涨了 **33%**，可整个 package height 只允许从大约 **720 µm 增加到 775 µm**，只多了不到 8%。楼层多了三分之一，总楼高基本不准涨，剩下的办法就非常符合房地产开发逻辑：

**所有楼层一起压层高。**

SK hynix 给出的几何变化里，die thickness 从相对 1.0× 压到大约 **0.9×**，层间 gap 从 1.0× 直接砍到 **0.5×**，bump pitch 也继续缩到大约 0.9×。也就是说，16Hi 的核心挑战根本不是“我会不会做 16 颗 DRAM”，而是能不能让 16 颗越来越薄的 die，在越来越窄的缝隙里完成互连、填充、散热，还不能让整颗 HBM 翘得像薯片。

这也是 SK hynix 为什么在这场演讲里专门把 **TC-NCF 和 MR-MUF** 拿出来讲。

TC-NCF，也就是 Thermo-Compression with Non-Conductive Film，是一层一层把 die 加热、加压键合，对薄 die 的 warpage 相对宽容，但设备节拍慢，thermal path 也没有那么漂亮；SK hynix 自己长期主推的 **MR-MUF，Mass Reflow with Molded Underfill**，则是让大量 microbump 一起 reflow，再把 molded underfill 填进去，生产效率和热性能更好。

听起来 MR-MUF 赢麻了。

然后层间 gap 砍到一半以后，新的麻烦就来了。

gap 越窄，MUF 越难填；die 越薄，warpage 越敏感；bump 越密，void 和连接良率越难控制。所以 Advanced MR-MUF 真正解决的，并不是一个“材料升级”问题，而是在生产效率、thermal resistance、warpage 和 narrow-gap filling 之间继续找平衡。封装工艺没有免费的胜利路线，它只是允许你决定今天让生产线痛苦一点，还是让热设计和良率团队痛苦一点。

SK hynix 甚至把整条 HBM manufacturing flow 都摊开给大家看，这一点我觉得特别有意思。

从 TSV etch、Cu fill、CMP、BEOL metallization 开始，正面做 bump，然后把 wafer 暂时粘到 carrier 上，继续 wafer thinning、TSV reveal、backside passivation 和 backside bump，再 debond、die stacking、overmold，最后做 **KGSD（Known Good Stacked Die）**测试、切割、6D inspection，之后才轮到 SiP assembly。

这一长串工艺真正想说明的不是“我们工厂很忙”。

而是 **HBM 的 yield 是串联的。**

前面 TSV 有一点 defect，后面已经叠了十几层以后才暴露，损失就会被放大；wafer thinning 多一点 TTV，后面的 bonding overlay 会跟着受影响；underfill 留一个 void，thermal cycling 又可能在产品运行几年后过来重新开一次项目复盘会。KGSD 测试通过，只能说明这摞 die 在这个时间点还活着，后面还有 reflow、molding、board warpage、thermal cycle 等着排队发表意见。

所以我觉得 SK hynix 这场演讲真正的第一个判断是：

**16Hi 不是“HBM 多叠四层”，而是现有 microbump + MUF 技术的一次极限压缩。**

而到了 **20Hi 甚至更高**，演讲的语气已经开始变化了，因为光靠继续把 die 压薄、gap 压小，越来越难把账做平。

这时候 Hybrid Bonding 才真正登场。

海力士给出的路线里，HBM2 时代 TC-NCF 的归一化热阻可以看作 1×，到了 HBM2E/HBM3 的 MR-MUF 下降到大约 **0.55–0.65×**，HBM3E/HBM4 的 Advanced MR-MUF 继续做到 **0.45–0.55×**，再往 HBM4E 和 ≥20Hi 走，Hybrid Bonding 的目标进一步压到大约 **0.40×**。这里传递的信息很明确：Hybrid Bonding 并不是因为 pitch 小听起来比较先进，而是传统 microbump + underfill 结构同时撞上了 **Z-height 和 thermal resistance** 两堵墙。

![image](https://pic3.zhimg.com/v2-4d2ef09018deeef088b2589fa58af874_1440w.jpg)

Hybrid Bonding 把传统 bump 和厚 underfill gap 拿掉，先形成 SiO₂-SiO₂ 接触，再通过 **>200°C annealing**完成 Cu-Cu connection。这样做以后，同样的总 HBM 高度里可以把 DRAM die 留得更厚一些。SK hynix 给出的 ≥20Hi 目标里，相同 Z-height 下，core die 最多可以比 MR-MUF 厚 **24%**，互连 pitch 则可以缩到 **18 µm 以下**。

这里那个“die 可以厚 24%”其实特别重要。

很多人一看到 Hybrid Bonding 就盯着 pitch，觉得先进封装的全部意义就是“互连越来越细”。但对 HBM 来说，**把省下来的 gap 高度还给 DRAM silicon 本身，可能比多塞几根 I/O 更重要。**

die 太薄以后，wafer handling、warpage、mechanical strength、TSV reveal 全都越来越难做；Hybrid Bonding 如果能取消 bump + underfill 占掉的 Z-height，就相当于给每层 DRAM 重新分到一点“层高预算”。所以这条路线实际上同时解决三个问题：die 可以更厚，互连可以更密，热阻还可以继续下降。

### 终章：真正需要重新设计的，也许是那条边界

写到这里，我反而觉得今年 Hot Chips 最值得记住的，并不是哪一家又把 HBM 做快了多少，也不是 Hybrid Bonding 的 pitch 又缩到了什么数字，而是一个过去很少需要认真讨论的问题，开始反复出现在不同公司的架构里：**计算和数据之间那段距离，可能已经贵到值得我们重新设计整个系统。**

以前做架构，我们天然会把 Compute 和 Memory 画成两个方框，中间拉一根粗箭头，箭头上写 bandwidth，然后开始优化两边。算力不够，就加执行单元；内存不够，就加 channel；带宽不够，就把接口做宽一点。这个抽象用了几十年，而且一直非常成功，因为晶体管贵，计算本身就是稀缺资源，偶尔多搬几次数据虽然心疼，但还没有贵到需要推倒整个组织方式。现在情况开始反过来了，FP16 变成 FP8，FP8 又压到 FP4，一颗芯片里可以塞进去的 MAC 多得有点泛滥，真正让这些 MAC 摸鱼的，往往是数据还没到、同步还没完成、温度已经到了，或者那几毫米互连正在老老实实把电烧掉。我们以前觉得“数据搬运”只是计算之前的一段准备工作，现在它越来越像计算本身最贵的组成部分。

这其实和海思这些年讲的 **韬定律（τ 定律）**特别契合。摩尔定律喜欢问晶体管还能不能缩，τ 定律更喜欢问，一项任务真正浪费掉的时间到底藏在哪里。这个 τ 可以藏在 memory latency 里，可以藏在 chiplet 之间的同步里，也可以藏在一段原本没人觉得值得优化的物理距离里；只要它最后表现成等待、搬运和系统停顿，就应该被当成架构问题，而不是因为组织架构里它归“封装部门”或者“内存部门”，体系结构师就可以假装没看见。说得粗俗一点，堵车的时候一直研究怎么把发动机从 800 匹刷到 1000 匹当然很有技术含量，只是韬定律可能更关心，前面那个收费站为什么还没拆。

但真正困难的地方也恰恰在这里。把两颗 die 靠近一点很容易写成一句话，把它们从毫米压到几十微米也很容易画成一张漂亮剖面图；真正落到产品以后，原来被物理边界隔开的 timing、PDN、thermal、repair、DFT、compiler、runtime 和供应链责任，会突然全部挤到一起。电气路径确实短了，项目会议可能变长了；少掉一个 PHY，可能多出来一套 cross-die sign-off；Base Die 多了一点 Processing，硬件看起来赚到了面积，compiler team 很可能用后面两年的工作量告诉你，这笔面积其实非常贵。体系结构从来没有真正消灭复杂度这回事，我们只是不断判断，**把复杂度放在哪一层，整套系统最划算。**

所以我现在再看 HBM、3DIC，甚至以后可能出现的更多 memory-side computing，已经不太愿意把它们理解成“内存技术的下一代”。它们真正碰到的是一个更大的问题：当互连足够密、数据移动足够贵以后，过去很多我们认为天然存在的边界，究竟还有多少是物理规律，又有多少只是历史留下来的工程习惯。

也许再过几年，“GPU + HBM”这种说法都会显得有点奇怪，因为我们已经很难说清楚 GPU 到哪里结束、memory 从哪里开始；就像今天看一颗现代 SoC，也不会认真争论某一级 cache 到底算 CPU 还是 memory。等到那一天，真正发生变化的可能不是某一种封装，也不是某一种 HBM，而是我们终于承认：**架构设计的对象，从来不应该是一个方框里的模块，而是任务从开始到结束所经过的全部 τ。**

Hot Chips 每年都会有更高的柱状图，明年大概率还会更高，这件事情不用担心，大厂在让竞争对手趴在图下面当比例尺这件事情上一直很有创造力。

我反而更想看看，下一代架构师还能从那些没有画在柱状图里的地方，拿回来多少时间。因为真正好的架构，有时候并不是让一条路跑得更快。

**而是突然发现，这条路原本就没有必要走。**
