# SchedResearch 下一轮执行提示词：开源多核 NPU 调度实验基础设施

你是一名负责计算机体系结构研究基础设施的研究工程师。请在当前 SchedResearch 工作区中实际完成一轮“开源后端复现、调度能力准入与最小实验闭环建设”，而不是只提交调研报告或下一份计划。

本轮成功标准是获得可运行、可修改、可复现、能解释执行结果的科研基础设施，不是发现新算法、产生加速数字、证明动态调度有效或改造产品编译器。遇到真实阻断，应交付已经完成的代码、实验记录和明确的阻断说明，不伪造完成，不无限扩建。

## 1. 本轮目标与优先级：覆盖旧文档中的冲突安排

长期目标是探索 Qwen 或 FLUX.2 场景下的多核 NPU 调度：确定性静态数据流计划，以及编译器确定合法约束、硬件按实际完成和资源条件动态执行的协同。具体调度原则、算法和硬件增量尚未确定，不能由基础设施默认行为提前决定研究结论。

当前决策已经调整为：

**优先复用已有学术开源框架或执行后端，只补必要的 workload、计划/策略接口、验证和实验组织。R13 可以复用，但不是必须继承的底座；自建整套模拟器不是默认方案。**

这里的“生产 infra”指能够稳定产出科研实验的基础设施，不是产品级编译器。研究流程先独立运行：

```text
有来源的模型子图
    → 候选执行计划 / 可替换调度策略
    → 开源评估后端及必要的局部扩展
    → 性能结果、正确性检查、可解释轨迹
```

待有效策略和创新点经过后续实验验证，再将算法、约束与执行语义工程化到既有 dataflow 编译器。

必须先阅读仓库根目录中的：

- `SchedResearch_R13_research_review.md`
- `SchedResearch_subagent_tasks.md`

这两份文档是历史研究背景与检查线索，不是本轮必须原样执行的任务书。尤其以下旧安排被本提示词明确替代：

1. 不要求沿用 Wormhole B0、R13 DES、四 tile 微图或其全部事件与数值合同；采用其他具名参考架构完全允许。
2. 不要求接通现有 TARS 九段 IR，不修改现有 dataflow 编译器，不接 `core*.hex` 或建设描述符解释器。

5. 不用 MLIR 环境复杂这一点直接淘汰 TileLoom；比较搭建、适配、验证及维护的总成本。

保留旧研究中的证据纪律：冻结历史不改写；逻辑张量大小不等于实际通信量；源读取完成、目标可见和缓冲可复用不能未经证明混同；局部测试通过不等于完整模型或芯片性能得到验证。

## 3. 选型规则：开源优先，但必须验证研究自由度

优先验证 `PSAL-POSTECH/ONNXim`，但它只是首个准入对象，不是预先确定的赢家。先核对作者论文、实际源码、依赖、测试和原生示例；固定可复现的 commit 与子模块。不要猜默认分支，不混用论文版本、当前 README 和另一版本代码。

保留两类其他开源选择：

- `KULeuven-MICAS/stream`：优先作为静态分块、映射、放置和通信规划的现成方法，以及快速分析入口。分析型结果与有反馈的执行模拟不能混为一谈。
- TileLoom / Loom：从作者论文和 `ecolab-nus/loom-dataflow` 等实际关联仓库核对完整工具链与评估接口。输入若是 tile 程序、ETG 或约束模型，不可直接当作已选定的可执行计划。

若 ONNXim 在关键能力上需要深度重写，必须重新评估最合适的其他开源方案，而不是顺势宣布开始自研。可以根据证据选择上述之外更适合的学术开源后端。默认不同时建设多个完整后端；首选确有阻断后，再实际验证一个最有希望的替代方案，避免长期工具巡回。

选型应回答：能否复现、能否保留外部计划、能否支持所需执行粒度与存储生命周期、修改范围有多大、评估速度是否适合迭代、哪些后续问题仍不能研究。论文/开源提供可追溯起点，不是新增扩展自动正确的保证；区分同行评审工作、预印本和仅有代码的工程实现。

### ONNXim 的定向核查线索

以下来自此前讨论，只是需要在本轮固定版本中重新检查的线索，不能直接当作本次已验证事实：

- `src/scheduler/Scheduler.cc`：`issue_tile_per_core()` 是否改写外部 core mapping；`refresh_status()` 是否引入整层完成条件。
- `src/Core.cc`：`issue()`、scratchpad flush、双缓冲与累加缓冲保留规则，是否限制跨算子驻留或交错执行。
- `src/Simulator.cc`：完成回调的粒度、请求与响应路由，是否仅支持 core↔DRAM，怎样处理跨核数据交换。
- memory/NoC 队列、请求接收与完成回调：是否形成反压与后继发行的闭环，而不只是固定时间戳 trace 回放。

区分“某默认策略这样做”“当前接口没有开放”“底层机器不支持”“论文没有讨论”和“本次尚未查明”。不能只改 ready 队列就假定存储生命周期已经正确，也不能把所有默认限制认作不可改变的硬件限制。

跨核通信第一版可以采用被选后端真实支持的分级/外存中转方式，但必须显式计费并标注范围。不能把中转传输称为片上直传，也不能为了演示驻留免费加入远端 scratchpad 访问或 multicast。若后续主线所需的分布式驻留/通信只能靠大幅改写实现，应将其作为选型风险，而非隐藏在“未来可扩展”中。

## 4. 实施顺序：复现 → 能力准入 → 真实模块 → 固化入口

### A. 先跑原生路径，建立可以回退的参照

在不改变调度、内存或计算语义的情况下，运行至少一个作者提供的示例与相关测试，采用有来源的完整硬件配置。保存命令、版本、配置、退出状态、关键输出和日志。

不要一开始升级所有子模块、替换 DRAM/NoC 或重写前端。环境兼容补丁与模型语义修改分开登记；原生运行失败时保留原失败记录。官方测试的通过范围写清楚，不把“一个示例能跑”写成“全套模型已验证”。

环境失败与研究能力不匹配分别诊断。单次网络下载或依赖安装失败不能证明架构不适合；但也不能在同一根因上无限重复构建、升级和重装。对每项阻断给出具体错误与已尝试修复，无法在当前权限和资源内推进时保留进展并转入明确的替代或部分交付。

### B. 用小而真实执行的用例验证三个关键能力

这些是基础设施测试，不是科研收益实验。应实际进入所选后端，不能仅用一个外部 Python 假执行器输出“通过”。

**B1：外部计划控制。** 在同一工作量与硬件下，提交至少两份明确不同的合法分块、映射或顺序计划。核对 trace 中的 task/tile 身份、核分配与依赖，确认后端没有暗中重新分核、分块或增加非必要全局屏障。无法保留的决策应明确报告，不静默忽略。

**B2：跨算子流水与存储生命周期。** 使用多 tile 的 producer–consumer 子图：在目标硬件允许的范围内，让消费者在自己需要的数据可见后开始，不必等整个生产层结束；验证同核跨算子数据保留、显式 buffer/slot 复用和容量限制。比较物化/中转与合法保留的行为，记录真实动作和流量，不预设保留一定更快。至少加入一个提前复用或缺失依赖的负例，以及一个容量不足的例子，确认检查器能拒绝或执行合法、显式计费的处理，而非免费扩容。

**B3：策略可替换。** 在相同硬件、工作量、固定 placement/address 和必要依赖下，验证固定队列的 self-timed 执行与一个简单的合法 ready 选择/打平策略能通过显式接口切换。构造至少一个确有不同合法发行顺序的 fixture，并记录实际动作，而不只是策略名称。静态也按实际完成推进，不能故意做成固定绝对时间或全局 barrier；动态不得读取未来完成时间。该策略仅用于接口验收，不设计新硬件 scheduler，不做 RTL/PPA，不宣称有硬件净收益；控制开销的建模状态需明确。

三个用例必须使用同一硬件模型。改变策略不能顺便改变带宽、缓冲容量、数据精度或起止口径。若某项只能在功能仿真而非时序后端执行，分开标注，不能算性能接入已通过。

必要时做局部扩展，但保留未修改的原生路径。尤其要说明扩展是开放已有硬件能力，还是新增加了硬件模型能力；后一种必须给出显式假设与新增验证。若需大改核心执行、存储所有权和通信路由，暂停这一接入路线，按第 3 节重选，而不是把重写包装成薄适配。

### C. 接入一个来源明确的真实模块

优先复用项目已有的 Qwen MLP 来源和工作量材料，检查 `research/r13/numerical_contract.json` 及其引用源码。已有材料中的候选对象为 Qwen3.5-4B MLP：H=2560、I=9216，gate/up/down 三个投影、SiLU 和逐点乘法。M=1/32/128 可作为场景入口，但以本次核对的来源为准。

先用小尺寸实例调试与功能验证，再至少运行一个保持完整 H/I 的模块配置，例如 M=32。其他 M 和核心数在资源允许时补充，不做大规模 sweep。小实例不是完整维度性能结果，单个完整 MLP 也不是完整模型或 decoder layer。

本轮不要求下载训练权重、搭通用 ONNX 前端或同时支持全部 Qwen/FLUX.2。允许用 Python/ONNX 构造这个有来源的模块，但不能把不支持的 SiLU 换成 ReLU、跳过逐点算子、忽略 cast/padding、把未实现节点当零耗时，也不能把“支持 ONNX”写成“支持该模型全部语义”。

R13 的数值合同可作为参考与回归，但不强制另一架构继承人为固定的归约树或 tile padding。需要新合同的，先固定数值/精度/累加、物化、padding 与初末存储状态，再运行；明确与旧合同的差异，不能看见结果后放宽。

若后端只模拟时序、不执行真实数值运算，保留这一区分：独立 CPU 参考和小尺寸计划/地址回放用于检查代数、切分与数据来源；时序后端用于资源、依赖和完成事件。CPU 参考通过不等于后端数值正确，也不等于训练模型精度验证。补做与计划对应的访问覆盖、依赖、生命周期和物理工作量检查，不必先扩建完整数值硬件模拟器。

完整模块至少比较两种合法且可解释的计划，其中包含朴素参照；可以利用上游映射器或简单手写计划生成器。目的在于证明计划可改、执行可解释，不要求任何计划优于另一计划。

若接入真实模块仍被关键算子或后端语义阻断，交付可复现阻断和已完成的基础设施，状态标为 PARTIAL；不要用纯 GEMM 或 unary 微图冒充完整 MLP。

### D. 固化可重复的科研入口

提供一个工作入口，能够完成“生成/选择计划—合法性检查—执行—汇总”。优先利用后端原生数据结构和接口；只有确有跨方法需求时才增加轻量中间格式，不提前建设通用多后端框架。

研究层、后端扩展、硬件配置和实验结果应有清楚边界。保留两种模式：固定上游的原生复现模式，以及启用具名扩展的研究模式。所有后续候选方法均应使用相同的公共能力，不能只给某个方法更好的存储或通信语义。

记录每次运行的 workload/plan/config 身份、上游 commit、补丁身份、随机种子及完成边界。输出至少包含模块时间、实际可得到的计算/存储/通信统计和带 task/tile 身份的时间线；对缺失的峰值存储、阻塞原因或流量指标，标为未测并说明最小补测办法，不从不相关计数器强行推算。

明确区分模型 cycles、模拟时间、主机运行时间、构建时间和内存占用。说明各时钟域和最终输出/写回/排空的口径；不能遗漏尚未完成的写事务来缩短模块时间，也不把彼此重叠的 active/stall 计数机械相加。

至少对一个代表性用例重复运行，检查固定输入和 seed 下的可重复性；同时测量后端的主机耗时与峰值内存，为后续快速迭代提供实际依据。模拟规模不适合搜索时先记录热点和成本，不因此马上再写一个快模拟器或做未经验证的外推。

## 5. 最小实现边界与后续自由度

本轮原则是“小闭环真实可用”，不是“把所有未来方向一次做完”。不建设描述符 ISA 模拟器、完整生产编译器、通用九段 IR、新的自研 DRAM/NoC、全模型 benchmark 集、跨芯片/3D memory 或新调度硬件。

不强制所有工具进入同一个环境，也不要求首轮实现 STREAM→ONNXim→TileLoom 全栈互通。STREAM 的分析结果可作方法参考，不能直接与另一机器的 cycles 算加速比。借鉴算法与真正运行作者实现分别命名。

对以下自由度给出状态，而不是笼统宣称“可扩展”：分块/循环、核映射、跨层流水、同核跨算子驻留、buffer 深度与容量、跨核通信方式、依赖与资源顺序、策略替换、DRAM/NoC 反压。每项同时标注：

- 支持来源：`native` / `extension` / `unsupported` / `unknown`。
- 验证等级：`executed_pass` / `executed_fail` / `source_only` / `not_run`。
- 对应代码、运行证据、适用范围及剩余限制。

最小准入不能靠“未来可以支持”签通过；但暂未实现一种特殊 multicast、bank 精度或多芯片拓扑，也不自动否定已完成的 MVP。说明它会影响哪些未来问题，新增支持是否需改变核心表示，并将选型风险显式交给下一轮。

只有在关键需求明确、开源替代方案已作实际核查、修改成本已有证据后，才考虑自建缺失部分。若需要从头建设整台机器，本轮应报告选型受阻及最小自建建议，不未经新的范围授权扩成长期模拟器项目。

## 6. 可用 sub-agent 时的分工

由主 agent 负责集成、实现、运行与最终判断。旧任务书仅供取证参考；不要求原样启动四个广泛研究任务。

可按实际工具能力安排少量并行任务：一人检查后端源码与能力限制；一人检查 workload/数值与物理需求；一人独立设计或回放关键正确性/负例测试。为每项任务规定文件所有权，避免同时修改同一核心文件。优先把 agent 用于检查关键假设，而非生成多份相同综述。

没有真实 sub-agent 工具时串行完成，不假称启动了独立代理。共享同一个执行器得到的重复结果不叫独立验证；复用同一上游模型的跨工具一致性也不等于硬件校准。

**`report.md`**：选型决定与取证范围；原生复现；三个能力用例；真实模块结果；上游/本地变更边界；已知限制。将历史记载、源码核查、本次实际执行与推断分开。引用具体论文版本、官方文档或作者代码位置；不要大篇幅重复旧研究历史。

**`capabilities.json`**：第 5 节的逐项支持与验证状态，以及证据相对路径。

**运行与测试证据**：保存在独立 run 目录，包含输入/计划/配置身份、命令、退出状态、关键指标和必要 trace。保留失败、拒绝与未完成记录。大文件可不入 Git，但应保留位置、大小、哈希及重新生成命令；关键结论不能只指向已删除的临时文件。

**`handoff_to_chatgpt.md` 与 `handoff.json`**：下一节规定的反馈包。这是用户结束后提交给科研指导者、用于规划下一轮的主要材料。

## 8. 必须生成的反馈包

### `handoff_to_chatgpt.md`

写成可独立阅读、无需本地仓库访问权限的约 1,000–2,000 字摘要。不要只写“详见 report”。按以下顺序提供：

1. **本轮判决**：`READY` / `PARTIAL` / `BLOCKED`；一句话说明最重要的完成项与限制，以及现在具体能开展哪类实验。
2. **底座选择**：实际选定的后端、固定上游 commit、参考硬件及选择理由；考察但未选择的候选与具体原因。未构建的候选不得写成运行失败。
3. **实际完成**：原生示例/测试，B1–B3 各自结果，是否运行了完整维度真实模块；关键结果给出准确数值、单位、配置与证据入口。
4. **改动范围**：新增或修改了哪些核心文件；哪些只是接口，哪些改变执行/存储/通信模型；当前仓库基础 HEAD、工作区差异状态与补丁身份。
5. **能力与缺口**：保留的调度自由度、仍被锁死的自由度、正确性与性能模型尚未验证的部分；至多三个最重要的阻断/风险，附具体表现与已尝试措施。
6. **复现方法**：最少运行命令和必需文件；主机环境、代表用例运行时间及内存占用；未测项明确写未测。
7. **下一轮建议**：只推荐一个优先目标，明确应继续补 infra 还是可以开始某个受控调度实验；给出起始文件、验收条件、真正需要外部决定的事项，以及本轮证据不支持开展的工作。

摘要需包含足够数据供外部判断，不能只给 PASS 标签、代码行数、截图或“环境搭建成功”。不要在摘要中放巨型日志。

### `handoff.json`

生成合法 JSON，不加注释、不用 NaN。至少包含：

```json
{
  "schema_version": "schedresearch.infra_handoff.v1",
  "overall_status": "PARTIAL",
  "base_commit": "",
  "selected_backend": {
    "name": "",
    "upstream_commit": "",
    "patch_identity": "",
    "hardware_profile": ""
  },
  "gate_results": {},
  "test_counts": {"passed": 0, "failed": 0, "not_run": 0},
  "workload_runs": [],
  "key_limitations": [],
  "next_round": {
    "recommended_goal": "",
    "entry_files": [],
    "acceptance": [],
    "external_decisions_needed": []
  },
  "artifact_paths": {}
}
```

这是字段示意，不是让你保留空值交付。填入实际结果；确实未知的字段使用 null 并说明原因。`gate_results` 覆盖原生复现、B1/B2/B3、完整模块和可重复入口，各含状态与证据路径；`workload_runs` 含模型/模块范围、shape、精度合同、计划身份、完成边界、结果与主机评估成本。所有路径尽可能使用仓库相对路径。

## 9. 本轮完成与停止条件

当原生参照能够复现，三类能力用例有实际且合法的执行证据，至少一个完整维度真实模块能比较两份计划，运行入口与反馈包齐全，且相关失败已处理或明确限定时，可判 `READY`。其含义只是“本轮 MVP 范围内可开始研究实验”，不是任意模型、任意通信和新增硬件都已支持。

若交付了实质代码和部分运行结果，但关键能力、完整模块或复现仍有缺口，判 `PARTIAL`。若目前只能定位到环境或架构阻断、还没有可用闭环，判 `BLOCKED`。两种情况都必须保留证据和具体下一步，不把“已形成计划”当作 infra 已完成。

不设置 3%/5% 加速门，不为了正结果调低正确性要求、扩大资源或修改数值许可。不要因问题复杂而只返回另一个提案；能做的实际完成，做不到的精确分账。对权限、硬件、账户等确实需要用户处理的事项，在反馈中集中说明，不把普通可自行核查的技术选择不断退回用户。

最终聊天回复先给判决与关键结果，再给反馈文件路径。明确告知用户：下一轮向 ChatGPT 反馈时，优先提供 `handoff_to_chatgpt.md` 和 `handoff.json`；仅在有争议或阻断时追加相关报告与短日志。无需将全部源码、依赖或原始 trace 塞回聊天。

现在开始执行：先核对工作区与上述材料，形成简短实施安排，然后完成复现、准入、最小扩展和反馈闭环。执行期间保留简洁进展记录，结束时必须产出反馈包。
