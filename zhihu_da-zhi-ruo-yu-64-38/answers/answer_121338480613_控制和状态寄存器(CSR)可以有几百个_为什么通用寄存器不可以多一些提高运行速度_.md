# 控制和状态寄存器（CSR）可以有几百个，为什么通用寄存器不可以多一些提高运行速度？

- 类型：回答
- 问题：控制和状态寄存器（CSR）可以有几百个，为什么通用寄存器不可以多一些提高运行速度？
- 原文：[知乎回答](https://www.zhihu.com/question/502805718/answer/121338480613)

这是个好问题。以前在x86/ARM的思维框架下，高赞回答的理由是合理的：

1. 寄存器编码空间不足
2. Context Switch需要保存更多的上下文
3. ABI中Caller-Callee的额外状态保存
4. 增加了寄存器重命名的复杂度，RF alias table或者SMAP的复杂度。

但是，如果我们跳出既有的思维定势，上面的四点都是可以通过技术手段变通的。

1. 在变长指令编码的设计下，通用寄存器的编码不再是限制条件。
2. 如果我们提供一种kill指令，可以deallocate架构寄存器，那么被kill的指令不必要保存上下文
3. ABI中通过寄存器bitmask获取活着的寄存器状态，并动态压栈
4. 寄存器重命名改造成register cache或者某种层次化的寄存器结构

通过巧妙的设计，我们也许可以证明将通用寄存器增加到64个，说不定会带来可观的性能提升。

至少对于SPECINT 2017的某几个子项，例如525.x264, 531.deepsjeng, 548.exchange等子项，对寄存器个数的需求还是挺高的。编译器unroll一下核心循环，并静态的把指令流排一下流水，就会带来10%~50%的性能提升，降低了10%~20%的load store个数。

提升架构寄存器的个数，对于微架构的收益主要在于：

1. 降低了load/store的spill操作，降低了LSU的压力，降低了内存地址检查的压力
2. 提升了编译器排流水的能力，尽可能让多个迭代的指令塞满流水线
3. 让微架构更关注不同寄存器的reuse distance，使能更好的层次化寄存器重命名
4. Early release & Lazy Allocation
