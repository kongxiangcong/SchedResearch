# DeepSeek V4 预览版本上线并同步开源，哪些亮点值得关注？

- 类型：回答
- 问题：DeepSeek V4 预览版本上线并同步开源，哪些亮点值得关注？
- 原文：[知乎回答](https://www.zhihu.com/question/2030963929510310856/answer/2031020927979406721)

在美帝高墙之下，中国模型没有停；在制程重压之下，国产算力没有退；

在看似狭窄的路上，仍有人把路一寸一寸凿出来。

不因外界称誉而轻飘，不因外界讥诽而退缩。DS模型是否用昇腾芯片训练出来？这个不重要，重要的在于，在不容易的地方，仍有人继续往前走。

它们背后，是制程，是存储，是互联，是超节点，是编译器，是算子库，是训练系统，是推理框架，是低精度数值，是通信调度，是一代又一代工程师在看不见的地方，把一条路一点一点修出来。

## 一、百万长卷：模型不是在读书，而是在驯服记忆

DS V4大模型最像什么？像一位不眠不休的书吏。

能作文，能写码，能推理，能查表，能读论文，也能替人类在深夜里继续加班。它手中有万卷书，眼前有千头绪。可是，它也有自己的痛苦。

书太长。记忆太重。

每写一句话，都要回头翻一遍前文；每做一个判断，都要从海量上下文中重新寻找线索。若上下文只有几千 token，这尚可忍受；若上下文进入百万 token，传统注意力机制便像一个被迫逐页翻书的老吏，气喘吁吁，汗流浃背。

这就是长上下文模型的第一重难题：

**不是模型不能看长文，而是不能用蛮力看长文。**

让一个模型读百万 token，若仍然每一步都把所有历史 token 拉出来相互对照，那就像让一个人每写一句批注，都从《永乐大典》第一页翻起。道理上可行，工程上荒唐。

DeepSeek V4采用的混合注意力思路，可以用一句话概括：

**近处看原文，远处看索引。**

近处的信息，必须细。因为最近几句话、最近几段代码、最近几轮对话，往往决定当前输出的精确性。这里不能只看摘要，必须保留原文，就像案头常备最近几页文稿。

远处的信息，则不必全部逐字摊开。可以压缩，可以索引，可以筛选，可以先看提要，再查原文。CSA 像给巨著做索引卡，HCA 像把远处文献压成翰林院摘要。模型先问：此刻我最该看哪几张卡？再决定是否回到原文。

这才像真正的读书人。新手读书，一页一页硬啃。高手读书，先看目录，再查索引，近处精读，远处通览；要论证时回到原文，要把握大势时看提纲。

长上下文模型也一样。

百万 token 的时代，不是让模型变成一个更勤奋的苦力，而是让它学会更聪明地组织记忆。

这背后折射出的硬件问题也非常尖锐。注意力不再只是两个规整的矩阵乘。它会变成压缩、筛选、top-k、gather/scatter、KV cache 重排、局部窗口、远端摘要、动态索引的混合工作负载。

DS V4的训练，使用了Muon优化器。它像先把车轮校正，把车轴摆直，把队形排齐，然后再发力。不是所有人各推各的，而是让更新方向更有结构，更少内耗。这背后也有一个深意：未来大模型训练不会只靠更大 batch、更大算力、更长时间硬堆。优化器会越来越懂矩阵结构，越来越利用参数本身的几何性质。

## 二、MoE 与昇腾 950 超节点：为 DeepSeek V4 而生的系统底座

DeepSeek V4 的 MoE，不是“小打小闹”的 MoE。

它不是几十个专家点缀一下，而是真正把专家系统做成了模型主干：**V4-Pro 有 384 个 routed experts，另有 1 个 shared expert；V4-Flash 有 256 个 routed experts，另有 1 个 shared expert；每个 token 都会从 routed experts 中激活 6 个专家。**

这意味着什么？

**V4 Pro 384的专家数和昇腾384超节点这么巧合地耦合在一起了。有没有可能模型就是在一起开始和菊场就这样设计的呢？**

每一个 token 进入模型之后，都不是沿着一条固定流水线往前走，而是像一枚高速数据包，先被路由器判断，再被送往数百个专家中的少数几个。算完之后，还要把结果带回原处合并。

通讯？路由器？交换机？这不是华为一直遥遥领先的传统艺能吗？

这就像一座大城里有数百个专科医院。

每个病人进城后，不是所有医院都看一遍，而是分诊台迅速判断：该去心内科、骨科、神经科，还是影像中心。真正考验城市能力的，不只是医院数量多，而是分诊准不准、转运快不快、道路堵不堵、检查结果能不能及时汇总。

MoE 也是如此。

专家多，只是第一层能力。

真正难的是：**token 能不能快速找到该去的专家，专家能不能及时吃到数据，算完之后能不能低延迟合流。**

如果没有一张足够强的系统网络，384 个专家就不只是能力，也是压力。专家越多，路由越复杂；激活越稀疏，访存越离散；上下文越长，KV cache 越沉；并发越高，dispatch 与 combine 越容易成为瓶颈。

所以，MoE 的问题，不是“有没有专家”。

而是“数百个专家能不能像一个整体一样响应”。

这正是昇腾超节点的用武之地。

单卡像一座高楼，算力可以很强；但 DeepSeek V4 这样的 MoE 长文本模型，需要的不是一座孤楼，而是一座低时延联通的大城。专家分布在不同计算单元上，token 要在城中穿行，KV cache 像城市档案库，Vector 负责分诊、归约、softmax、量化这些细活，Cube 负责专家 GEMM 这些重活。若道路窄、调度慢、档案远、转运多，再强的 Cube 也会等数据。

昇腾超节点要做的，就是把这些“楼”连成“城”。

不是把卡简单堆起来，而是用大带宽、低时延、强 Scale Up 的互联，把多卡组织成一个统一计算体，让专家并行不再被单机边界绑住，让 token dispatch 不再一跨卡就变慢，让 KV cache 不再成为调度的锁链。

这也是为什么华为宣布基于 Ascend 950 AI 芯片的昇腾超节点将全面支持 DeepSeek V4。

DeepSeek V4-Pro 的 384 个 routed experts，很像一座有 384 个专科中心的超级医院群；V4-Flash 的 256 个 routed experts，则像一座更轻、更快、更适合高并发的区域医疗网络。每个 token 激活 6 个专家，相当于每个病例会被送到 6 个最相关的专科会诊。会诊质量取决于专家水平，但会诊速度取决于城市系统。

![image](data:image/svg+xml;utf8,<svg xmlns='http://www.w3.org/2000/svg' width='1672' height='941'></svg>)

超节点，就是把这些专科中心、转运道路、档案系统和会诊平台连成一张低时延网络。

没有这张网，专家越多，越可能排队；模型越大，越可能堵车；上下文越长，越可能被档案拖慢。这时候，如果仍按传统集群思路处理，多卡之间像一座座孤岛，token 每跨一次卡都像过一次关，KV cache 每远取一次都像绕一段路，dispatch 和 combine 每等待一次，Cube 就多空转一拍。

峰值算力再高，也会被路上的等待吃掉。昇腾超节点要解决的，就是这个“路”的问题。

第一，它需要大规模 expert parallelism。

MoE 低时延推理，不能把太多 expert 塞在同一个计算单元里排队。专家要铺开，token 要能快速到达。专家铺得越开，单个 token 的等待越少，decode 阶段越容易压低 TPOT。但专家一铺开，通信就变成生命线。所以，超节点必须提供高带宽、低时延、强 Scale Up 的互联能力，让 expert 不再被单机边界绑死，让 token dispatch 不至于一出本地就慢下来。

第二，它需要把 all-to-all 从“沉重通信”变成“系统内动作”。

MoE 的 dispatch 和 combine，本质上就是反复交换 token。若每一步都按普通 all-to-all 去做，就会出现通信开销高、动态 shape 多、CPU-NPU 同步频繁、计算和通信串行等问题。适合 MoE 的系统，必须把这些环节融合起来：路由元数据少走弯路，hidden state 尽量压缩后再发，通信和 expert 计算尽量流水重叠，dispatch 与 combine 尽量减少中间落地。这不是“优化一个 kernel”。这是把 MoE 当成系统级算子重新设计。

第三，它需要分布式 KV cache 的高效访问。

长文本推理最怕什么？不是模型不会读，而是记忆太重。DeepSeek V4 这种长上下文模型，一边要保留大规模 KV cache，一边还要做 MoE 路由。如果 KV cache 被牢牢绑在某一小块本地资源上，调度就会被数据位置牵着走。哪里有 cache，计算就不得不往哪里挤；哪里通信慢，TPOT 就被哪里拖住。

超节点的价值，是把多卡资源组织成更大的共享空间，让 KV cache 的访问不再成为调度的锁链。它要让系统从“计算追着数据跑”，逐渐变成“数据和计算在统一平面里协同调度”。

第四，它需要低精度、稀疏访存、Vector 与 Cube 协同。

MoE expert 的主计算是矩阵乘，Cube 要吃得饱；router、top-k、softmax、归约、量化、反量化、dispatch、combine，又大量依赖 Vector 与访存路径。如果 Vector 做完路由，还要绕很远把数据交给 Cube；Cube 算完又要绕回来做后处理，那么低时延就会被片上搬运吞掉。因此，Vector 与 Cube 之间的 Memory 共享、低精度原生支持、稀疏访存优化，并不是锦上添花，而是 MoE 推理能否真正跑顺的底层条件。

**这就是为什么昇腾超节点适合 DeepSeek V4。**

专家要铺开，通信要够近；token 要分发，路径要够宽；KV cache 要巨大，访问要够顺；Cube 要高效，数据要及时送到；低精度要省，数值路径要稳。

昇腾超节点要做的，就是把这张图铺成路、架成桥、织成网，让万千 expert 各归其位，让海量 token 往来有序，让国产算力真正接住国产模型的下一步。

## 三、mHC：残差高速路，不怕路多，怕无规矩

如果说混合注意力解决的是“书太长，怎么读”，那么 mHC 解决的是另一个更幽微的问题：

**层太深，信息怎么传？**

深度神经网络为何能堆很多层？靠的很大一部分，是残差连接。

普通残差连接很朴素：下一层，等于原来的输入，加上这一层加工后的结果。

它像写论文时保留原稿。每一轮修改都可以加入新内容，但底稿一直在。哪怕某一层没学好，原始信号还可以顺着直通车道往后走。

这条直通车道，就是 identity mapping。残差连接的厉害，不在于多加了一根线，而在于给深层网络保留了一条生命通道。它告诉模型：你可以加工信息，但不要轻易毁掉信息；你可以一层层塑形，但别把源头掐断。

那么问题来了一条残差通道这么有用，能不能多修几条？

这就是 Hyper-Connections，也就是 DeepSeek V4 HC算法的想法。普通残差像一条官道。所有信息沿着主路往后走。HC 则像把官道扩成驿路网络：有的路传军情，有的路运粮草，有的路走文书，有的路载商贾。多路并行，分流合流，信息自然更丰富。

路多了，若无交通规则，就不是繁荣，而是混乱。车马乱行，信使相撞，粮车堵路，军令迟滞。放在模型里，就是多条残差流之间的混合如果没有约束，信号可能被层层放大，也可能被层层削弱。

有些通道越灌越满，有些通道越来越干。最后不是信息流动，而是信息失控。这便是 HC 的隐忧。

mHC 的高明，不是把多车道拆掉，而是给多车道立规矩。它把残差流之间的混合矩阵约束成双随机矩阵。所谓双随机矩阵，说得直白一点，就是每一行之和为 1，每一列之和也为 1，且元素非负。

可以把它想成几只水桶。矩阵决定水从一个桶倒向另一个桶。双随机约束要求：每个桶倒出去的总量有数，每个桶接进来的总量也有数。水可以重新分配，但不能凭空暴涨，也不能莫名蒸发。

这便是 mHC 的妙处：**让信息可以流转，却不至泛滥；可以混合，却不至冲堤。**它不是保守。它是有边界的自由。

这也是很多大模型架构创新最容易被忽略的一点：表达能力不是越放纵越好。真正高级的表达能力，必须有稳定性的约束。没有边界的灵活，最后往往不是创造，而是崩坏。

DeepSeek-V4 使用了 **mHC：Manifold-Constrained Hyper-Connections**。其中，Sinkhorn-Knopp 迭代需要一个专门的融合算子，用于对局部矩阵进行归一化，使其逐步收敛为 doubly stochastic matrix，即行和、列和都接近 1 的矩阵。我们基于 昇腾**PTO 指令集的 Python 接口**，同样用 20 行左右的 Python 代码表达其核心计算逻辑，在几分钟内完成了昇腾平台上的 Sinkhorn 算子开发，并通过了 TileKernels 仓中的单元测试 test_sinkhorn.py。

**DSV4 mHC 用 Sinkhorn-Knopp 算法**，把普通矩阵反复校正成近似双随机矩阵。先按行归一化，再按列归一化；再按行，再按列；来回数轮，像排座位表，既要每排人数对，也要每列人数对。调几轮，秩序便出来了。

这件事很有象征意味。大模型越来越深，越来越宽，越来越复杂。过去我们只盯着 attention、FFN、MoE，仿佛发动机越大，车就越强。mHC 提醒我们：底盘同样重要。车开得越快，底盘越要稳。路修得越宽，护栏越要牢。模型越大，信息主干道越不能失控。

那么这个算法怎么在昇腾芯片上写出来呢？

Sinkhorn 迭代的数学公式非常简单。参考 TileKernels 单元测试中的 PyTorch 基线实现 `sinkhorn_normalize_ref`：

```text
def sinkhorn_normalize_ref(
    x: torch.Tensor,
    repeat: int = 10,
    eps: float = 1e-6
) -> torch.Tensor:
    x = x.softmax(-1) + eps
    x = x / (x.sum(-2, keepdim=True) + eps)

    for _ in range(repeat - 1):
        x = x / (x.sum(-1, keepdim=True) + eps)
        x = x / (x.sum(-2, keepdim=True) + eps)

    return x
```

这里的 `x` 是一个 3D 张量，shape 为：

```text
[batch, 4, 4]
```

其中，`4` 是 mHC 论文中选用的扩展系数，可以作为编译时常量处理；而 `batch` 与输入 token 数成正比，需要作为动态维度处理。

整个算法可以分为两个阶段：第一阶段，先对 `x` 按行执行 softmax；第二阶段，反复执行行归一化和列归一化，使局部矩阵的行和、列和逐步收敛到 1。换句话说，Sinkhorn-Knopp 做的事情非常直接：先把矩阵变成一个合理的概率分布，再不断校正行和列，直到它变成一个近似的 doubly stochastic matrix。

在 PTO 实现中，首先使用 `tload` 将一块 `[4, 4]` 数据从 HBM 读取到片上 buffer，然后在 buffer 上完成两个阶段的计算。这里的核心优势在于：PTO 可以直接用 Python 接口表达 tile 级计算逻辑，开发者不需要手写底层同步、搬运和访存细节，只需要围绕局部 tile 描述计算过程。

对于 shape 为 `[4, 4]` 的 mHC Sinkhorn 算子而言，核心逻辑非常短，基本可以直接对应 PyTorch 基线代码。把上述逻辑合在一起，Sinkhorn 核心算子用PTO写法就是：

```text
# stable softmax on rows
tile.row_max(mat_kk, scratch_kk, row_stat)
tile.row_expand_sub(mat_kk, row_stat, mat_kk)
tile.exp(mat_kk, mat_kk)

tile.row_sum(mat_kk, scratch_kk, row_stat)
tile.adds(row_stat, eps_h, row_stat)
tile.row_expand_div(mat_kk, row_stat, mat_kk)

# first column normalization
tile.col_sum(mat_kk, scratch_kk, col_stat)
tile.adds(col_stat, eps_h, col_stat)
tile.col_expand_div(mat_kk, col_stat, mat_kk)

# repeated row/column normalization
for _ in pto.range(c1, repeat_idx, c1):
    tile.row_sum(mat_kk, scratch_kk, row_stat)
    tile.adds(row_stat, eps_h, row_stat)
    tile.row_expand_div(mat_kk, row_stat, mat_kk)

    tile.col_sum(mat_kk, scratch_kk, col_stat)
    tile.adds(col_stat, eps_h, col_stat)
    tile.col_expand_div(mat_kk, col_stat, mat_kk)
```

这里可以看到，PTO 的表达方式非常接近算法本身，在昇腾950上你能够快速写出GPU相同的算子了，性能还很好。

论文里三行公式，PyTorch 里三十行代码，训练系统里三百个麻烦。

最后工程团队只留下一句话：

“这个东西训不起。”

所以真正重要的，是把新结构变成硬件友好的执行图。哪些数据留在片上？哪些操作融合？哪里用 Vector？哪里用 Cube？哪里需要同步？哪里可以双缓冲？哪里能隐藏访存？

这正是昇腾 PTO 可以发挥的地方。

它不只是让你“写出”一个 Sinkhorn，而是让你有机会把 Sinkhorn 写成一个真正适合昇腾硬件执行的 Sinkhorn。

## DeepSeek V4.1 ???

未来大模型创新会越来越快、越来越结构化。今天是 mHC，明天可能是新的流形约束，后天可能是新的稀疏残差拓扑，再后天可能是新的训练时动态路由机制。
