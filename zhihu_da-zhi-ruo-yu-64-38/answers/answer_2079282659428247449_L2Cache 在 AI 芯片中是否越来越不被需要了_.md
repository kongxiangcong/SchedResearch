# L2Cache 在 AI 芯片中是否越来越不被需要了？

- 类型：回答
- 问题：L2Cache 在 AI 芯片中是否越来越不被需要了？
- 原文：[知乎回答](https://www.zhihu.com/question/2077385092591367615/answer/2079282659428247449)

## L2 Cache 在 AI 芯片里真的要失业了吗？

![image](data:image/svg+xml;utf8,<svg xmlns='http://www.w3.org/2000/svg' width='1448' height='1086'></svg>)

如果只看今天最典型的小 Batch LLM Decode，给 L2 Cache 判一个“职业前景不佳”其实并不奇怪：一个几十甚至上百 GB 的模型，每生成一个 token 都要把大量权重从 HBM 重新扫过一遍，KV Cache 又随着上下文持续膨胀，而芯片上那个几十 MB 的 L2 面对这样的 working set，确实很容易陷入一种尴尬境地——数据刚刚被装进来，还没来得及享受几次 reuse，就已经被下一批 streaming traffic 顶了出去，于是你花了 SRAM 面积，做了 tag array、replacement、MSHR、writeback buffer，甚至还为了多个计算单元共享数据引入一致性和仲裁逻辑，最后发现最繁忙的功能居然是把数据从 HBM 搬进来，再很快把它赶出去。

从这个角度看，越来越多面向 AI 的 ASIC 或 NPU 弱化传统 L2，并不难理解。

但如果把这个观察继续外推成“AI 芯片越来越不需要 L2”，问题就来了，因为 NVIDIA 这些年干的事情恰恰相反：A100 把 L2 做到了 40MB，H100 继续做到 50MB，而且从 A100 开始还专门给软件提供 L2 residency control，让程序主动告诉硬件哪些数据值得留下。另一方面，TPU、Tenstorrent、Cerebras 这类架构确实长期没有照搬传统 GPU 式共享 L2，而是把大量 SRAM 分散到计算附近，通过 DMA、NoC 和编译器显式安排数据生命周期；甚至到了最近公开讨论的 Jalapeño，一边能够看到 L1 Cache 和 OoO 执行重新进入 AI Core，另一边又没有回到传统“所有 Core 背后挂一个大共享 L2”的老路，而是围绕 HBM slice、数据 placement、prefetch 和专用通信网络重新组织存储层次。

所以这件事情真正值得讨论的，从来都不只是 L2 这两个字。

![image](data:image/svg+xml;utf8,<svg xmlns='http://www.w3.org/2000/svg' width='1672' height='941'></svg>)

更准确的问题应该是：**AI 芯片里的数据局部性，究竟应该由硬件动态发现，还是由编译器提前安排？**

这才是 Cache 和 Scratchpad 背后真正的架构分界。

### L2 真正买的东西，从来都不只是命中率

很多人谈 L2 时，第一反应是“减少一次 HBM 访问”，这个理解当然没错，但还不够，因为真正让一个共享 L2 昂贵，同时也真正让它有价值的地方，在于它实际上承担了一整套围绕“不确定访问”建立起来的系统功能。

假设有几十个 SM 或 AI Core 同时对 HBM 发请求，如果它们完全直接穿透到内存系统，那么 NoC、memory controller 和 HBM interface 看到的不是几十条漂亮、连续、已经对齐的 DMA，而是大量不同时间到达、不同地址、不同粒度甚至部分重叠的 transaction；这时候 L2 首先可以通过 MSHR 和 request merge 把多个针对同一条 cache line 的 miss 合并掉，又可以通过 write combining 和 writeback buffering 把碎片化的小写操作重新组织起来，同时还能承担 atomics、跨 Core 数据共享以及一部分 coherence 汇合点的作用，于是 L2 的意义并不只是“这里恰好存着我要的数据”，它同时也是整个 memory system 的流量整形器。

如果只盯着 capacity，很容易得出一个看似合理但其实很奇怪的判断：50MB L2 连一个 70B 模型的零头都装不下，所以它没有意义。

这相当于说家里的冰箱装不下一整座沃尔玛，所以厨房不该有冰箱。

Cache 的价值从来都不要求把整个 working set 装进去，它真正关心的是 reuse distance：一个 cache line 从第一次被访问到下一次被访问，中间到底经过了多少其他数据，如果 reuse distance 能落在 Cache 容量覆盖的窗口里，这块 SRAM 就有意义；如果 workload 彻底变成单向 streaming，每块数据只碰一次，几十 MB L2 面对几十 GB 权重当然会被冲得像没存在过一样。

所以“小 Batch Decode 对 L2 不友好”这个判断本身没有问题。

问题在于 AI inference 已经远远不只是“小 Batch Decode”。

当 batch 和 concurrency 提高，同一块 weight tile 会在多个 sequence 之间产生 reuse；当 prefix sharing 出现，一部分 KV 又可能在多个 request 之间共享；MoE 引入动态 expert routing 以后，不同 token 会落到不同 expert，访问模式开始从规则矩阵乘变成带统计分布的稀疏访问；再加上 embedding、sampling、routing metadata、quantization/dequantization、reduction 和各种 framework glue kernel，一个完整 inference pipeline 的访存行为远没有“HBM 读进来，矩阵乘一下，再写出去”那么干净。

这也是为什么 GPU 很难彻底放弃共享 Cache。

NVIDIA 要面对的 workload 集合太大，编译器不可能在 kernel launch 之前精确知道每一个 cache line 的未来生命周期，于是 L2 本质上是在用晶体管购买一种东西：**软件看不到未来时，硬件仍然有机会把局部性捞回来。**

这就是 Cache 的保险价值。

保险的问题大家都知道——平时看着浪费，出事的时候又嫌买少了。

### NPU 为什么敢把这份保险退掉

AI 加速器真正特殊的地方，在于大量 Tensor workload 的未来其实没有那么神秘。

以一个最普通的 GEMM 为例，编译器在编译期就知道矩阵尺寸，也知道 CUBE 或 Tensor Core 每次消费多大的 tile，因此它完全可以提前决定 A、B 分别按照什么 layout 切块，哪几个 tile 被搬进本地 SRAM，在 Matrix Engine 中复用几次，什么时候下一块 DMA 可以启动，什么时候当前 buffer 已经没有消费者，可以安全覆盖；如果硬件还支持 double buffering，编译器甚至可以把 load、compute 和 store 在时间轴上排成流水，让下一块数据在上一块矩阵乘还没结束之前就已经开始搬。

在这种情况下，一个硬件自动管理的 Cache 反而会显得有些多余。

编译器明明已经知道这块数据将在 600 cycle 以后死亡，Cache 却还要为它分配 tag、选择 set 和 way、更新 replacement state，然后等未来某个时刻再通过 replacement policy“猜”它是不是没用了；更糟糕的是，两个本来被软件精确安排好、绝不会互相干扰的 tile，可能因为地址映射撞进同一个 set，在一个 perfectly tiled 的算法里制造出 conflict miss，这种事情在 CPU 上还能忍，在一个追求 cycle-level deterministic schedule 的 Tensor pipeline 里，多少有一点自己给自己找刺激。

于是 TPU、早期数据流 NPU、Tenstorrent 以及 Cerebras 这一类架构做出了另一种选择：SRAM 当然继续要，而且往往要得更多，只不过它不再伪装成一个“硬件会自动帮你管理一切”的 Cache，而是直接成为 Local SRAM、Unified Buffer、VMEM 或 Scratchpad，让软件明确知道数据放在哪里，再用 DMA 或 NoC 显式把它搬过去。用户给的讨论里其实已经点到了这个问题的核心：真正要区分的首先就是 L2 Cache 和 L2 Buffer，因为物理上都是 SRAM，体系结构上的含义却完全不同。

这种做法在 PPA 上的吸引力非常直接。

你可以少掉 tag lookup，可以弱化甚至彻底去掉 coherence，可以让 SRAM 几乎全部容量都存有效 payload，可以针对 Tensor tile 宽度设计 banking 和 port，也可以让访问延迟更加确定；更重要的是，一旦 NoC 支持 multicast，一个权重 tile 根本不需要像 CPU cache hierarchy 那样让多个 Core 分别 miss、分别 fill，而可以从源头一次搬运，然后在 fabric 上复制到多个消费者。

从数据流角度看，这当然很漂亮。

问题在于，架构从来没有免费午餐，尤其是芯片行业，免费午餐通常只存在于 PowerPoint 的左上角。

Cache 被删掉以后，局部性并没有被删掉，数据依赖也没有消失，DRAM latency 更没有因为产品经理不喜欢它就主动降低；原来由 hardware replacement、MSHR、prefetch、miss handling 和 coherence 承担的复杂度，现在只是换了一张工牌，去了 compiler team 上班。

于是编译器开始负责 tiling，负责 buffer allocation，负责 lifetime analysis，负责 double buffering，负责 DMA scheduling，负责 multicast，负责 spill，负责 bank conflict，负责 layout conversion，还要负责在 Compute、Memory 和 NoC 之间做 overlap。

只要 workload 足够规则，这笔账非常划算。

可一旦程序开始动态起来，事情马上就不一样了。

### 真正决定 L2 生死的，是“未来到底有多可预测”

假设编译器提前认为一个 activation buffer 在第 800 cycle 就可以释放，于是把下一块 tile 安排在那里，结果下游 Vector Engine 因为 bank conflict 或者前一个 reduction 延迟了 200 cycle，原本看上去非常漂亮的静态 lifetime 就会发生冲突；再比如 MoE 原本根据平均 expert load 做了 buffer sizing，某一批 token 却突然大量集中到几个热门 expert，或者 sequence length、batch、speculative decoding acceptance rate 在运行时发生变化，那么本来依靠 compile-time scheduling 排好的数据流，很快就会出现 bubble、spill 或重新同步。

传统 CPU 为什么会发展出 OoO、Cache 和 branch prediction，本质上并不是体系结构学家天生喜欢复杂，而是软件世界里有太多事情到运行时才知道。

第一代 NPU 能够把这些东西砍掉，是因为神经网络曾经真的非常规则：Conv、GEMM、固定 shape、静态 graph，大部分时间编译器知道接下来发生什么，于是让硬件猜未来就显得浪费。

今天的 workload 正在重新变得麻烦。

LLM 的 Attention 里 KV Cache 会持续增长，MoE 的 expert 访问取决于 token，continuous batching 会让不同 sequence 在不同时间进入和退出，agentic workload 又会把模型计算和各种动态控制流、tool calling、不同长度请求混在一起；于是曾经那种“编译器完全知道未来”的设计前提正在逐渐松动，存储层次自然也开始重新发生变化。

这恰恰也是 Jalapeño 值得关注的地方。

按照目前公开描述，它没有简单退回传统 GPU 模式，而是做了一件更有意思的事情：Core 内重新引入 L1 Cache 和 OoO，用硬件吸收局部范围内那些越来越难以静态预测的 latency 和 dependency，而在 Core 之外，却仍然通过 HBM slice、明确的数据放置、prefetch 和专用 collective network 去控制大规模数据移动。公开分析把它描述成 L1 + 分片 HBM 的极简层次，每个 Core 对本地 HBM slice 拥有更低延迟的访问，再通过专用网络完成跨 slice 通信，这背后的逻辑其实非常清楚：只要 weight、KV 以及 tensor-parallel communication 的拓扑在系统层面仍然可控，就没有必要为了这些巨大的 streaming 数据再维护一个传统意义上的大共享 L2。

这并不意味着 Jalapeño 证明了“L2 无用”。

它证明的是另一件事：**Cache 应该覆盖那些真正存在动态 reuse、动态依赖和不可预测 latency 的范围，而对于软件已经能够明确 placement 的数据，继续让一个通用 Cache 插在中间，有时候反而是在支付一份没有必要的保险费。**

这个思路其实比“Cache 对 Scratchpad”二选一高级得多。

因为现实系统里，不同数据根本不应该使用同一种管理方法。

几十 GB 的权重天然接近 streaming，尤其在低 Batch Decode 下，把它们反复塞进几十 MB 的 L2，意义非常有限；一个几 KB 或几十 KB 的 activation tile，却可能在 CUBE、Vector、Reduction 之间短时间高频复用，适合留在本地 SRAM；KV 的生命周期更长、容量更大，又和 request 强绑定，可能更适合通过 placement 保证 locality；至于 metadata、routing table、稀疏 index、stack、runtime state 这些东西，本身又非常像传统通用 workload，让 Cache 来处理反而省心。

如果硬要让所有数据都经过同一种 memory hierarchy，最终一定会有一类 workload 为另一类 workload 的设计假设买单。

### 所以 L2 会不会消失，最后其实是一道 PPA 题

L2 会不会在 AI 芯片里消失，我觉得最终并不是一个关于 Cache 容量、命中率甚至 HBM 带宽的问题，它更像是过去几十年体系结构里那条老问题在 AI 时代重新出现：**对于那些只有程序真正跑起来以后才知道的事情，我们究竟愿意花多少晶体管让硬件在运行时解决，又愿意把多少责任提前交给编译器。**

CPU 和 GPU 很长一段时间选择的是前一条路，因为 branch、load latency、memory alias、cache locality 这些事情本来就很难在编译期完全确定，于是 OoO、Cache、prefetch、speculation 一层层长出来，本质上都是拿面积和功耗去消化不确定性；早期 NPU 恰好遇到了一个非常特殊的窗口，Conv、GEMM、固定 shape 和静态 graph 让大量数据依赖提前变得可知，于是我们第一次有机会把很多原本属于硬件的工作搬给 compiler，用 tile、scratchpad、DMA 和 static schedule 换回非常漂亮的 PPA，而今天 MoE、continuous batching、长上下文、动态路由以及越来越复杂的 inference workload，又把这种确定性一点点拿走，所以 Cache、OoO 和 prefetch 重新回来并不奇怪，真正有意思的是它们不会简单按照 CPU 的老样子回来，而会只覆盖那些软件已经无法经济地提前决定的部分。

这也是我觉得 Jalapeño 这类架构真正值得看的地方：它没有在“GPU 还是 NPU”“Cache 还是 Scratchpad”之间选边站，而是在重新划分责任边界，局部 latency、dependency 和动态调度交给硬件，大尺度 tensor placement、HBM locality 和 collective communication 仍然尽量交给软件，于是未来 AI Core 的竞争很可能也不会是谁把 Cache 做得最大，或者谁把 Scratchpad 做得最干净，而是谁能够找到一条更好的分界线，让动态性留在硬件最擅长处理的尺度里，让确定性尽可能暴露给 compiler，同时又不把整个软件栈逼成一台巨大而脆弱的静态调度机器。

因此 L2 只是一个表象，真正需要回答的问题始终是：**哪些事情值得让硬件猜，哪些事情值得让软件提前知道。** 这条线一旦画错，代价最后都会从别的地方回来，可能是更大的 SRAM、更复杂的 DMA 和 barrier，也可能是更长的 NoC、更差的利用率、更难收敛的 compiler，甚至最终变成 floorplan、功耗和芯片成本；而一颗真正好的 AI 芯片，往往并不是把某一种机制做到极端，而是让每一种复杂度待在它最便宜的地方。
