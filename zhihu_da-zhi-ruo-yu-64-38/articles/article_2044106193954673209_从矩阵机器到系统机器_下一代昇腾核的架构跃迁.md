# 从矩阵机器到系统机器：下一代昇腾核的架构跃迁

- 类型：文章
- 原文：[知乎文章](https://zhuanlan.zhihu.com/p/2044106193954673209)

最近“韬定理”如火如荼，朋友圈里人人都在谈系统、谈封装、谈先进工艺之后的第三条路，听起来每个人都像刚从未来十年穿越回来。作为菊场一名朴素的牛马，仰望星空当然也要仰望，毕竟谁不想在技术史的长河里顺手捞一瓢水；但低头看一眼自己的工位，屏幕上还挂着一堆算子性能、客户问题、流水断点和 profiling 图，心里马上就踏实了：宏大叙事先让大佬们飞一会儿，咱还是先把昇腾这颗核里的水管、电线、阀门和红绿灯理明白。

![image](https://pic3.zhimg.com/v2-baada3031582543d1b09482dc85baf80_1440w.jpg)

昇腾 950 已经开始大规模进入客户现场，卡卖得多了，用户多了，模型多了，框架多了，问题自然也多了。过去有些问题藏在实验室里，像墙角一小片返潮，看着不严重；等客户真正把模型一批批搬上来，长序列、低 bit、推荐、广告、搜索、动态 mask、MoE、通信融合全都往上怼，才发现这不是返潮，这是楼上浴缸忘关了。我们最近的状态也很像救火队员，一边拎着水管冲进去，一边还得给业主解释：房子主体结构是可靠的，钢筋水泥都没问题，就是管线有点复杂，开关有点多，个别阀门藏得比较深，操作手册写得像绝地武士训练纲要。

昇腾这辆车，发动机其实很猛。CUBE 该有的爆发力是有的，Vector 也不是吃素的，搬运引擎、Fixpipe、各种格式转换和低精度能力，拆开看都挺能打。问题在于，它有点像一辆性能很好的手动挡赛车，离合、油门、档位、转速、路线全都给你了，理论上能开得飞快，实际上要开出 Speed of Light，驾驶员最好是天行者安纳金，闭着眼都能感受到原力在 L0A、L0B、L0C 和 UB 之间流动。普通人上去一脚油门，车没坏，路也没堵，就是突然发现自己还没挂对档，副驾驶的 CUBE 已经在催，后排的 Vector 还没系安全带，Scalar 正在翻说明书，Fixpipe 在旁边冷静地说：别急，量化参数还没配完。

这也是很多人吐槽 CUBE 和 VEC 分开的原因。单独看，每个单元都有自己的道理；合起来跑复杂模型，就会发现数据总在倒腾。CUBE 算完一块东西，Vector 马上要做 scale、mask、softmax、reduce；Vector 处理完，CUBE 又要接着算下一轮。算法图上是一条流畅的线，落到硬件里就变成了几段接力：这块数据先在哪，下一步谁用，要不要搬，要不要转格式，要不要等同步，要不要释放 buffer，要不要小心踩到另一个 pipe。写算子的人本来是来写数学的，写着写着就像在调度一个微型物流园区，叉车、仓库、闸口、传送带全要自己盯。

低精度也是一样。听起来很美，bit 少了，算力高了，带宽省了，模型成本降了，大家一起鼓掌。但真到芯片里跑，事情马上变得很现实：数据要打包解包，scale 要加载对齐，格式要转换，L0C 要搬出，Fixpipe 要接住，Vector 要做后处理，转置路径还要亲和。CUBE 在前面喊“我准备好了”，后面的数据流像早高峰地铁换乘，入口、扶梯、闸机、站台全在排队。低 bit 的峰值很性感，低 bit 的端到端很诚实。

950 把 SIMT 加进来以后，很多不规则场景终于不用再硬拧 SIMD 或折腾 Host 了，这一步方向当然是对的。动态 mask、离散访问、复杂控制流，这些东西迟早要在核内解决。但昇腾的 SIMT 又不是 GPU 那套土生土长、从小练到大的 SIMT，它更像是我们给一支原本纪律严明的方阵配了一支轻骑兵，能绕路、能侦察、能处理复杂地形，但马厩、粮草、指挥链和主力部队之间的协同还得继续补。于是很多算子就变成了混合作战：一段 SIMT，一段 SIMD，中间还要搬数据、对齐、同步、切 shape。能打，但累人；能赢，但每次赢完都想回去重构。

我们做 PTO 虚拟指令集，初心其实很朴素，甚至有点理想主义：底下这些 CUBE、Vector、MTE、Scalar、SIMT、Fixpipe，各有脾气，各有祖传接口，各有一套“你最好按我喜欢的姿势来”的使用说明。那能不能往上封一层，把这些异构单元包装成一组简单、统一、稳定的 Tile 操作？用户写的是我要搬一块数据、算一块矩阵、做一次重排、完成一次同步，至于底下到底是哪条 pipe、哪个 buffer、哪个 event、哪个奇怪的配置字段，最好别让人天天背口诀。结果做了一波以后，客户也很真诚地告诉我们：抽象很好，但是我还想要硬件底层。

这话听起来完全合理。毕竟大家做性能优化，谁都不想隔着一层毛玻璃看硬件。问题是，底层一给出去，事情马上开始变得玄学。参数多，约束多，组合多，亲和路径多，挂死姿势也多。你给他一个简单接口，他说不够透明；你把底层打开，他说怎么这么难用。最后我们夹在中间，像一个人格分裂的导游：上午给游客讲“大家放心，这是一条统一路线”，下午又偷偷补一句“但是这段山路要自己换挡，那个弯道要提前踩离合，前面还有个隐藏开关，没开可能直接熄火”。

PTO 想解决的是统一抽象，可现实里的硬件接口却像一座老城区。每条街都有名字，每个路口都有历史，每个单元都有自己的小规矩。比如原子操作这种东西，按理说应该是一个很清楚的系统能力：我要同步，我要交换信息，我要保证顺序，我要让多个核之间有一个可靠的握手机制。结果一看实现，标量有一套，向量有一套，MTE 又有一套，能力不完全一样，语义不完全一样，路径不完全一样，性能也不完全一样。你想做一个多核同步，先别急着写代码，先开一场科普会，解释清楚“你这个 atomic 到底是哪个 atomic”。

这件事表面上很好笑，往深了看其实很疼。它说明我们现在的硬件能力虽然丰富，但缺少一个统一的核内管理和调度语义。每个单元都在努力把自己的事情做好，可系统层面缺少一个能把这些能力收拢起来的共同语言。PTO 想往上抽象，客户又需要底层控制；底层一暴露，复杂度又反噬软件；软件接不住，就继续靠专家经验、靠文档补丁、靠群里答疑、靠一轮又一轮解释。

更深一层看，昇腾当前遇到的这些问题，表面上散落在 C/V 交互、低 bit、SIMT、DMA、Scalar、通信、DFX、TDP 各个方向，像一张到处贴便利贴的问题墙；真正的根子其实很集中，就是**核内的调度和管理问题**：现有核还是围绕固定流水和显式 buffer 管理来组织计算，缺少一个统一的数据流调度层。计算单元各自很强，交接成本却不低；片上存储层级很丰富，软件却要记住太多物理细节；低 bit 峰值上去了，scale、重排、搬出和 Vector 后处理没有被放进同一套调度；SIMT 有了处理不规则场景的能力，还没完全成为主路径；通信越来越像模型数据流的一部分，却仍然带着外部控制动作的影子。

### 如果有机会重构这个核，那它应该要解决什么问题

过去的 AI 核像一条高效的工业产线。原料规整，工序稳定，最重的工序是矩阵计算，硬件把这个工序做得足够快，整条产线自然有很高吞吐。

现在的模型更像一座繁忙城市。城市里仍然有主干道，也有越来越多的小路、岔路、临时管制和跨区调度。大矩阵乘还是主干道，但低 bit、稀疏 attention、MoE、动态 mask、长序列 KV、推荐离散访问、小算子融合、A-F 分离和多流通信都在增加“路口”和“换乘”。城市的通行效率不再只取决于最宽那条路，还取决于匝道是否堵、信号灯是否合理、快递能不能送到最后一公里、调度中心能不能看清全局。

这也是昇腾当前痛点开始集中爆发的原因。现有核擅长规则高密度计算，但复杂模型把大量非规则、非矩阵、非连续、非静态的工作推到前台。只要其中某一段没有跟上，矩阵阵列就会等数据，Vector 就会等搬运，SIMT 就会等资源，Scalar 就会等 cache，通信就会等 doorbell 或 CQE，端到端性能自然跑不满。

一个简单的性能表达式能说明问题：

```text
T_layer ≈ max(T_cube, T_vector, T_memory, T_comm)
          + T_reorder
          + T_scalar_control
          + T_sync
          + T_tail_latency
```

在规则大矩阵时代，`T_cube` 往往最大，其他项被掩盖。到了低 bit、稀疏和长序列时代，`T_cube` 下降，`T_reorder`、`T_memory`、`T_scalar_control`、`T_sync` 和 `T_tail_latency` 反而变得更显眼。继续只增加矩阵峰值，会让公式里的其他项更加刺眼。

未来昇腾核要优化的核心对象，应该从单个计算单元转向这条完整的数据流。

### 分离结构有历史合理性，但新模型把交接成本放大了

昇腾现在把 CUBE、Vector、搬运、Scalar 分得很清楚，这不是偶然，也不是当年没人想过统一。它背后有非常现实的物理约束。

CUBE 要吃极高带宽。矩阵乘不是一口一口吃饭，它更像灌水，L0A、L0B、L0C 必须稳定供数、稳定累加、稳定搬出。Vector 也一样，softmax、reduce、activation、quant/dequant、mask 处理都需要高带宽读写自己的工作区。如果强行做一块 CUBE 和 Vector 都能高频访问的大 SRAM，软件当然舒服，硬件马上难受：端口数、bank 冲突、crossbar、布线、面积、功耗、时序，每一项都会涨。

在工艺、面积和频率都受限的情况下，这种统一大 SRAM 很难落地。于是更现实的办法就是拆开。CUBE 有自己亲和的 L0A/L0B/L0C，Vector 有自己的 UB，搬运引擎负责在中间倒数据。路径窄一点、专一点、局部一点，硬件好收敛，矩阵阵列也更容易喂饱。对于规则 GEMM、BMM、卷积和标准 attention，这套方法很有效。数据流稳定，交接次数少，软件把流水排好，硬件就能按节拍往前冲。

所以 C/V 分离不是一个简单的历史包袱。它曾经是很工程、很克制的选择。它解决的是当时最关键的问题：在有限工艺条件下，把高带宽局部计算做出来，把峰值和能效先做稳。

麻烦出在模型变了。

过去 CUBE 和 Vector 偶尔交接，中间搬一次还能接受。现在复杂模型里，它们成了天天对接的上下游。Attention 里，CUBE 算完 QK，Vector 立刻要做 scale、mask、softmax、reduce，后面 CUBE 又要接 PV；低 bit GEMM 里，矩阵计算前后都有 scale、quant、dequant、layout 转换和搬出；推荐、稀疏和动态 mask 场景里，SIMT 生成索引或 mask，Vector 做特征处理，CUBE 再接矩阵计算，中间结果不断跨执行域流动。

算法看上去是一条连续的数据流，硬件里却要跨几个车间。CUBE 的结果在 L0C，Vector 想用要搬到 UB；Vector 处理完，CUBE 还要用，又得搬回 CUBE 能吃的位置。每次交接都带着搬运、同步、格式转换和 buffer 管理。过去这些开销藏在大矩阵后面，现在低 bit、稀疏、小算子和长序列把它们全照亮了。

这就是今天最痛的地方。分离结构当年帮我们把矩阵机器做成了，现在复杂模型又把分离结构的交接成本放大了。

未来的机会来自物理条件变化。二维平面上，统一高带宽 SRAM 太贵，逻辑和存储都挤在同一层，带宽靠横向布线、端口和 bank 去堆，越统一越难收。**3D 堆叠和韬定律打开了另一种可能**：存储可以更靠近计算，逻辑和 SRAM 可以在垂直方向重新组织，带宽不完全依赖长距离横线，CUBE、Vector、SIMT 访问同一类 Tile 数据的代价有机会下降。

这件事的关键不是把所有 buffer 粗暴合成一块大 SRAM。那样只会把端口、仲裁、冲突和时序问题重新搬回来。更合理的方向，是物理上仍然保留 bank、local buffer、专用 datapath 和分层 SRAM，架构语义上收敛成统一的 Tile Register。软件看到的是逻辑 Tile，硬件决定它放在 L0C、UB、某个 SRAM bank，还是通过旁路直接送给下一个执行单元。

这样既保留了 NPU 的专用高能效路径，也不再把物理分离原封不动地甩给软件。CUBE、Vector、SIMT 仍然可以有各自亲和的数据通路，但它们消费的是同一套 Tile 语义。中间结果不再靠“在哪一级 buffer”来表达身份，而靠 Tile 的逻辑名字、ready 状态、依赖关系和物理映射来管理。

当年的分离，是受限于核内超大带宽共享 SRAM太贵；今天的痛苦，是模型越来越需要 CUBE 和 Vector 像处理同一条数据流一样协同；未来的窗口，是 3D 堆叠可能让统一 Tile 数据对象重新变得可行。

下一代昇腾核要抓住这个窗口，把过去被物理约束拆开的单元，在架构语义上重新组织起来。

### 片上存储要从“手工仓库”走向“Tile 寄存器体系”

未来昇腾核应该把片上共享存储“Tile 寄存器化”。这个说法的重点不在“寄存器”这三个字，而在寄存器体系背后的能力：逻辑命名、物理映射、重命名、ready 状态、依赖追踪、生命周期管理和异常恢复。

在这样的体系里，软件声明的是逻辑 Tile：

```text
Tile q = load_tile(Q, layout_q);
Tile k = load_tile(K, layout_k);
Tile s = matmul(q, k);
Tile p = softmax(s, mask);
Tile v = load_tile(V, layout_v);
Tile o = matmul(p, v);
store_tile(O, o);
```

硬件内部仍然需要决定 q、k、s、p、v、o 分别落在哪块 SRAM、哪个 bank、是否需要进入矩阵阵列旁边的局部 buffer、是否可以直接旁路给 Vector、是否需要 spill 到更低层级。这些复杂性没有消失，只是从手工账本变成硬件和编译器共同管理的资源映射。

这样做的价值很直接。第一，软件不再把每一级 buffer 的生命周期写死，算子泛化性会好很多。第二，CUBE、Vector、SIMT 之间可以通过 Tile ready 状态自然衔接，减少显式同步。第三，异常发生时，硬件可以记录逻辑 Tile 到物理存储的映射，DFX 能看到真正的数据流状态。第四，未来硬件改变某一级 SRAM 容量或路径时，软件接口不需要跟着大改。

复杂模型里的很多等待，不再是软件排流水时能完全预知的等待。稀疏访问会让某些 Tile 的数据回来得比预期更晚，PageAttention 里的某个 page miss 会拖住一小段数据流，动态 mask 会让不同 Tile 的控制路径不一样，低 bit 场景里 scale 可能提前 ready 也可能被 layout 卡住，通信返回有远端时延，小 shape 下单个 block 可能根本填不满一个执行核。于是原来那种“我提前知道每一步要花多久，所以我把流水排得刚刚好”的假设开始失效。流水一旦失效，就会出现气泡：CUBE 有空但数据没来，Vector 有空但前序 Tile 没搬完，Memory Engine 有空但软件没把下一批请求提前发出去，旁边明明有已经 ready 的工作，却因为软件预排顺序还没走到它，只能跟着一起等。

这个时候，继续让软件手工重排流水，当然可以缓解一部分问题，但它会越来越吃力。因为动态性越强，软件越难在静态阶段把所有情况都排好；模型 shape 越多，模板越多；layout 越多，亲和路径越多；通信和稀疏越多，运行时的不确定性越多。软件能做的是给出一个大致合理的执行图，但执行过程中到底哪个 Tile 先 ready，哪个 Tile 被 memory 拖住，哪个 Tile 可以提前做后处理，哪个 Tile 的 scale 可以预取，这些信息只有硬件在运行时看得最清楚。既然信息在硬件手里，调度也应该有一部分回到硬件手里。

这里需要的不是把 AI 核做成一个通用 CPU，也不是在每条标量指令上复制 CPU 那套乱序窗口。AI 核的数据粒度更大，计算结构更规整，真正值得乱序的对象不是一条条普通指令，而是一块块有明确输入输出关系的 Tile。一个 Tile 可以代表一次矩阵块计算，一次低 bit 数据重排，一次 scale 对齐，一次 softmax/reduce，一次 gather 访问，或者一次通信等待。只要硬件能够知道这些 Tile 之间的依赖关系，知道每个 Tile 的输入是否 ready，知道对应执行后端是否空闲，知道内存顺序和异常边界，就可以在不破坏程序语义的前提下，把已经 ready 的 Tile 先发出去。

这就是 Tile 级乱序的本质：把过去由软件静态安排的“固定流水”，变成硬件在运行时根据 Tile ready 状态动态推进的“数据流调度”。

为了做到这一点，下一代核需要在前端建立一套围绕 Tile 的状态系统。逻辑 Tile 要能映射到物理 Tile 存储，这样软件看到的是稳定的数据对象，硬件可以在内部做重命名和复用；等待执行的 Tile 操作要进入一个队列，硬件根据输入 ready、资源 ready 和内存依赖来选择发射；Tile 的生产和消费关系要有明确记录，某个执行后端写回以后，依赖它的后续 Tile 可以被唤醒；内存访问要进入独立的建序结构，既允许不相关访问并行推进，又能在别名、越界和异常时保持可解释；已经发射的 Tile 要有提交状态，这样出错时能够知道哪个 Tile 在飞、哪个 Tile 已经完成、哪个 Tile 可以回滚或丢弃。

这套机制听起来像 CPU 乱序，但粒度完全不同。CPU 乱序关心的是几条加法、load、branch 之间的依赖；Tile 乱序关心的是一个 BMM tile、一个 reorder tile、一个 scale tile、一个 vector tile、一个 communication tile 之间的依赖。它不追求在极细粒度上榨干每一条标量指令，而是要在 AI 模型真正的执行粒度上，把大块等待重叠起来，把本来会空转的 CUBE、Vector、SIMT、Memory 和 Comm 填起来。

有了 Tile 级乱序以后，很多过去必须靠软件手工安排的事情，就可以交给硬件运行时处理。某个稀疏 load 还没回来，不相关的矩阵 Tile 可以继续发；某个通信 Tile 在等远端事件，本地已经 ready 的 Vector 后处理可以先做；低 bit 的 scale Tile 可以提前搬进来，不必等到 MMA 前一刻才发现 scale 没到；reorder Tile 可以插在 memory 和 compute 之间，尽量和上一块计算重叠；小算子不必作为一段单独流水硬插进去，而可以在资源空隙中被调度出去。这样做的结果不是让单个操作本身变快，而是让整条模型数据流少等一点。

复杂模型最怕的，往往不是某一个操作慢，而是很多小等待凑在一起。一次 page miss、一段 scale 对齐、一点通信静态时延、一次 descriptor 准备、一块小 tile 的尾巴，看起来都不大，叠在几十层、几百个算子、几千个 Tile 上，就会变成端到端性能里很厚的一层灰。Tile 级乱序的意义，就是让硬件不再傻等软件排好的下一步，而是在保证正确性的前提下主动找活干，把这些灰一点点擦掉。

### 低精度也需要增强核内控制和调度

量化这件事，最容易被讲成一个很简单的故事：FP16 换成 FP8，FP8 再压到 FP4，bit 少了，算力高了，带宽省了，模型自然就快了。这个说法听起来很顺，像把行李箱里的衣服用力压一压，空间立刻多出来一半；可真正到了大模型里，问题就没这么体面了，因为模型里那些数不是一堆可以随便压扁的衣服，它们有的很重要，有的不那么重要，有的值很小却影响结果，有的值很大却只是 outlier，有的 channel 对输出特别敏感，有的 channel 粗糙一点也还能忍。把它们统统塞进 4bit，难点从来不在于编码表怎么写，而在于这 4bit 到底还能不能保住原来那堆数里真正该保住的信息。

所以量化的第一性问题，其实是误差该怎么分配。一个 tensor 里，大多数值可能集中在很窄的范围内，少数值突然冲得很高；weight 相对稳定，activation 却会随着输入变化，动态范围更飘，也更容易冒出 outlier。一个粗 scale 看起来最适合硬件，因为数据和 scale 都简单，搬运也省事，可它会让一个 block 里少数大值把尺度拉大，剩下大量小值被压得没有分辨率；scale 切得太细，误差是下来了，scale 自己又变成了要存、要搬、要对齐、要参与计算的新负担。量化的难处就在这里，它像给一张照片压缩，压得太狠，细节糊了；压得太保守，文件还是大；真正好的压缩，不是平均地删信息，而是知道哪里该保真，哪里可以省。

很多量化方法，本质上都在围绕这个问题转。SmoothQuant 试图把 activation 里特别扎眼的 outlier 压力转移到 weight 上，让 activation 的分布变得更适合低精度；AWQ 观察到不是所有 weight 都一样重要，于是根据 activation 分布去保护那些更关键的 channel；MXFP、NVFP4 这类格式，则把这个思路放到硬件数据格式里，让一小组元素共享 scale，而不是让太大一片数据共用一个粗糙尺度。它们看起来是算法、格式、硬件三种不同语言，背后说的其实是同一句话：低 bit 太窄了，必须把动态范围先整理好，再交给硬件去算。

放到芯片里，这个问题会更现实。scale 选得再漂亮，也要有人把它搬进来；group 切得再精细，也要有人把 scale 和 packed data 对齐；数据压成 FP4/MXFP4 以后，片外存储变小了，片内却多了 unpack、reorder、scale align、acc convert、requant/dequant 这些动作。MMA 只是链路中间那一刀，真正决定端到端性能的，是这一刀前后的东西能不能接上。低 bit 最怕的情况，就是 CUBE 已经能高速算 FP4，前面 packed 数据还在慢慢解包，scale 还没对齐，后面累加结果还在等转换，Vector 和 Fixpipe 又接不住搬出的节奏，最后峰值表格很好看，模型实测像一辆发动机很猛但变速箱打滑的车。

一次低 bit 计算从数据流角度看，应该先从高精度数据的局部动态范围开始，决定 scale 的格式和粒度，再按 group 或 block 把数据量化成 packed low-bit 表达，随后这批 packed 数据和 scale 一起被搬到片上，在进入矩阵阵列之前完成必要的 unpack、布局重排和 scale 对齐，矩阵单元负责低 bit 乘法和高精度累加，累加结果再根据后续路径做格式转换、requant 或 dequant，最后按目标 layout 写回。这里每一步都可能成为瓶颈，每一步也都可能影响精度；把其中任何一步当成“算子里顺手补一下”的小动作，低 bit 的收益都会被打折。

未来昇腾核如果要真正把量化做好，就不能把 low-bit 看成 CUBE 新增的一个 dtype，而要把它看成一条带语义的数据流。一个 low-bit Tile 不能只写着 FP4 或 MXFP4，它还应该携带 packed layout、scale format、scale granularity、group size、accumulation type、valid mask、reorder policy 这些信息。硬件看到这些信息，才知道这块 Tile 不是普通矩阵，而是一块带着 scale、分组、布局和精度约束的量化数据；编译器看到这些信息，才有机会把 scale load、unpack、reorder、MMA、acc convert、requant/dequant 放进同一个调度图里，而不是让它们散落在不同 pipe、不同模板、不同特殊路径里。

scale 尤其不能再被当作一个临时参数。低 bit 场景里，scale 和数据一样重要，甚至很多时候比数据更麻烦。scale 要被 load，要被 cache，要被复用，要和数据 layout 对齐，要在转置和重排时跟着走。scale 提前到了，MMA 少等一拍；scale 和数据 layout 对齐，Vector 和 Fixpipe 少倒腾一次；scale 粒度设计合理，精度和带宽才有平衡。很多低 bit 路径跑不满，表面看是 CUBE 利用率低，仔细看是 scale 和数据流没有被一起设计。

unpack 和 reorder 也不能全靠软件手工拼路径。低 bit packed 数据为了省存储，通常不会天然长成计算阵列最喜欢的样子；模型 layout 为了适配 attention、KV cache、MoE 或推荐场景，也不会总是按硬件最舒服的方向排。每次都靠软件拆模板、补转置、挑特殊指令，低 bit 算子很快就会变成迷宫。更合理的方式，是让 Tile Memory Engine 在搬入时就尽量完成 unpack、reorder、padding 和 scale align，把后端真正要吃的 Tile 准备好，这样 CUBE 看到的是已经整理过的计算数据，而不是一堆需要前后端临时救火的半成品。

累加和再量化也需要统一语义。低 bit 乘法通常不能用低 bit 累加，结果要进入更高精度的累加域，然后根据下一步需求决定是保留高精度、转成 BF16/FP16，还是重新 quant 成低 bit 写回。如果每个算子各自写一套 acc convert、requant、dequant 路径，溢出行为、舍入方式、scale 使用和性能特征都会变得不一致，调试起来非常痛苦。未来应该把这些动作收敛成稳定的 Tile 原语，让软件表达清楚精度语义，让硬件选择高效路径。

## SIMT 是表达方式，后端应该收敛到 SMT-SIMD

未来模型里的不规则性会越来越多。推荐里的离散 embedding、稀疏 attention 里的 index 和 mask、FlexAttention 里的 score_mod、MoE 里的 token routing、长序列里的 page 和 KV 命中，都会不断把控制流、predicate、离散地址和小粒度访存塞进核内。程序员确实需要一种更自然的表达方式，可以像写 SIMT 一样描述“每个元素、每个 token、每个 lane 自己判断、自己算索引、自己决定是否参与”。

但这不代表硬件内部要再长出一套传统 GPU 式 SIMT 前端。

更合理的实现方式，是前端给程序员 SIMT 表达，后端落到一套统一的 SMT-SIMD 硬件上。程序员看到的是线程式、lane 式、predicate 式的表达；硬件内部执行的仍然是一套向量/SIMD 资源，只是通过多上下文交织、predicate mask、lane mask、寄存器重命名和调度，把不同控制路径下的工作压回同一套 SIMD datapath 里跑。

这条路并不奇怪，AMD 的 CDNA 和 XDNA 都能看到类似思想。CDNA 的软件模型里，程序员面对的是 wavefront 这样的并行执行抽象，底层真正干活的是 SIMD 单元，一个 CU 里有多个 SIMD pipeline 和 wavefront slot；XDNA 的 AI Engine 也是 tiled dataflow 架构，每个 tile 里有 vector processor、scalar processor 和本地存储，软件表达的是空间数据流和并行任务，硬件执行靠局部 vector/scalar 资源承接。它们都不是把“前端并行表达”和“后端物理执行”简单画等号，而是在二者之间做了一层翻译：上面给程序员足够自然的并行语义，下面用硬件最划算的 SIMD/VLIW/本地数据流去实现。

昇腾下一代核也应该往这个方向走。SIMT 不应该成为一条独立于 Vector/SIMD 的物理主路径，更不应该带来两套寄存器、两套调度、两套访存和两套性能模型。那样表面上增加了灵活性，实际上会让核内人格分裂更严重。更好的做法是，软件保留 SIMT 表达，硬件统一成 SMT-SIMD：规则密集的部分直接走 SIMD，带分支和 predicate 的部分用多上下文和 mask 在同一套 SIMD 后端上兜住，真正复杂、无法结构化的逻辑再由 SIMT 表达作为 fallback。

这个定位很重要。SIMT 不是未来核的主路径，主路径仍然是规则、密集、可向量化的数据流。CUBE 能吃的就给 CUBE，Vector/SIMD 能吃满的就给 Vector/SIMD，AGU、Index/MaskGen、Gather Engine 能接住的离散访存就交给专用数据通路。SIMT 表达只负责兜那些硬件专用结构暂时接不住的边角：特殊 score_mod、非常规 index、复杂分支、临时 fallback，以及一些动态 shape 下不好静态规整的控制逻辑。

这样做的好处是，程序员不用被迫在 SIMD 和 SIMT 两套世界之间来回切换。写法上可以用 SIMT 风格表达不规则逻辑，编译器和硬件再决定哪些部分收敛成普通 SIMD，哪些部分用 SMT 上下文交织，哪些部分走 gather/maskgen，哪些部分保留真正的 fallback。底层只有一套物理执行资源，一套 Tile 数据对象，一套寄存器和调度语义，CUBE、Vector、Memory Engine 和 SMT-SIMD 都围绕同一条 Tile 数据流协同。

### 搬运引擎要从固定 DMA，走向结构化 Gather-Scatter 系统

很多不规则访存，不能简单丢给 SIMT。

SIMT 确实能算地址，也能做 gather/scatter，但它做这件事的代价很高。每个 lane 都要重复执行地址计算，重复处理 index、offset、mask、边界和 layout 规则，最后只是为了得到一批本来就有结构的地址。这样写起来灵活，硬件执行起来却不划算：指令多，寄存器占用高，LD/ST 队列压力大，地址计算和 predicate 消耗了大量 issue 带宽，真正有价值的计算还没开始，SIMT 已经先被“算地址”和“小 load”拖住了。

问题的根子在于，这些访问看起来离散，但并不是完全随机。

PageAttention、SparseAttention、embedding lookup、KV cache、低 bit packed layout、scale layout、head/batch/sequence 展开，这些场景里的地址通常都有规律。它们可能不是简单的一维连续地址，却往往可以写成多维坐标到物理地址的映射：base 加若干个 stride，加 page offset，加 block offset，加 lane offset，再按 mask 过滤一部分无效位置。换句话说，它们不是没有规律，只是规律比传统 DMA 的 base + stride 更复杂。

如果把这种“有结构的离散访问”交给 SIMT，相当于让一群工人拿着计算器一户一户算门牌号；每个人都能算，结果也对，但效率很差。更合理的做法，是把门牌号生成规则交给一个专门的地址生成器，让它一次性展开一批地址，再由 gather/scatter 引擎去合并请求、过滤无效元素、处理跨页和重排返回数据。

所以这里真正要拆清楚的是三件事：地址怎么生成，哪些位置有效，请求怎么合并。

连续 DMA 把这三件事默认得太简单，SIMT 又把这三件事全交给程序去做。下一代核需要在两者中间放一组硬件：通用 AGU、Index/MaskGen 和 Gather Engine。

可以从一个简单的访存模型看这个问题。假设一次 tile 需要取 N 个元素，每个元素大小为 E 字节，理论有效数据量是：

```text
UsefulBytes = N × E
```

如果这些元素连续，硬件发出的总请求量接近 UsefulBytes，带宽利用率自然高。可如果这些元素分散在很多 cache line 或 page 里，真实搬运量会变成：

```text
TrafficBytes ≈ NumberOfTouchedLines × LineSize
```

真正的带宽效率就是：

```text
Efficiency = UsefulBytes / TrafficBytes
```

问题不在 HBM 峰值，而在 NumberOfTouchedLines 被离散访问放大了。一个 4KB 的有效数据，如果散落在很多 128B line 里，硬件实际搬的可能远不止 4KB。再叠加 TLB miss、请求队列开销、返回乱序和同步等待，端到端代价会继续放大。

这就是为什么小粒度访存不能只说“提高带宽”。峰值带宽解决的是主干道宽度，离散访问浪费的是每个包裹进出小区的成本。真正要优化的是访问集合本身：哪些地址可以合并，哪些 line 可以复用，哪些 page 可以提前走表，哪些元素根本无效不该发请求。

AGU 负责第一步，把结构化地址展开。很多所谓离散访问，其实有规律。PageAttention 里的 page/block 映射，SparseAttention 里的 block index，embedding lookup 里的 table base 和 offset，multi-head 场景里的 batch/head/sequence 坐标，都可以被描述成多维地址生成问题。AGU 不应该只会 base + stride，它要能处理多维 stride、分段 offset、page table、block table、tile 内坐标和循环展开，把“看起来散”的访问先规整成一组结构化地址流。

Index/MaskGen 负责第二步，把有效访问筛出来。长序列里不是每个 block 都有效，sparse attention 里不是每个 token 都参与，动态 mask 里不是每个位置都应该被取。与其让 Scalar 或 SIMT 一条条判断，不如让硬件根据 length、offset、index table、predicate 和 bit mask 生成 tile 级访问集合。这样后面的 gather 引擎拿到的就不是一堆原始循环，而是一组带有效位的访问描述。

Gather Engine 负责第三步，把访问集合变成高效请求。它要看地址之间的距离，能合并相邻请求，能把同一 cache line 内的多个元素合到一次访问里，能识别跨页边界，能提前发 page walk，能把返回数据按目标 layout 装回 Tile。它不是简单 load 单元，而是一个小型的“访问整理器”。

这三者连起来，访问路径应该长这样：

```text
Index/MaskGen 生成有效访问集合
        ↓
AGU 展开结构化地址
        ↓
Gather Engine 合并 line、处理跨页、重排返回数据
        ↓
Tile Memory Engine 交付后端可消费的 Tile
```

这里有一个关键边界：SIMT 仍然需要保留，但它应该兜底真正复杂的部分。比如用户自定义的特殊 score_mod、非常规 index 计算、不可预测分支、临时 fallback 路径，这些交给 SIMT 很合理。常见的 page lookup、block sparse、embedding gather、mask filtering，如果已经成为主流模型的稳定模式，就不该每次都让 SIMT 手工展开。能硬化成 AGU/Mask/Gather 的，就应该沉到硬件里；只有模式还不稳定、规则还没收敛的部分，才由 SIMT 接住。

未来的 AGU 不能只停留在简单的 base + stride。它应该支持更通用的结构化地址生成，例如用 16bit 系数和 48bit 地址计算一组多项式或仿射表达，把 tile 内坐标、head、batch、block、page、lane、group 等维度组合成物理地址。很多 tensor layout 本质上就是多维坐标映射，只要把映射规则交给 AGU，硬件就能用很少的控制信息生成一整片地址流，而不需要 SIMT lane 逐条重复计算。

比如一个 tile 内元素的地址可以抽象成：

```text
addr =
  base
+ i0 * stride0
+ i1 * stride1
+ i2 * stride2
+ page[index] * page_size
+ block_offset
+ lane_offset
```

这里的 `i0/i1/i2` 可能对应 batch、head、sequence 或 tile 内坐标，`page[index]` 可能来自 page table 或 block table，`lane_offset` 对应低 bit packed 数据里的位置。这个表达式看起来比普通 DMA 复杂，但它仍然是规则的、可硬件化的。

这比 SIMT 逐条发 load 更接近硬件应该做的事。SIMT 的价值在于处理真正复杂、不可预测、用户自定义的逻辑；对于已经稳定下来的 tensor layout、page layout、sparse block layout 和 low-bit packed layout，硬件应该沉淀出 AGU + Index/MaskGen + Gather-Scatter 的专用能力。SIMT 作为兜底可以保留，但不能让它长期承担结构化访存的主工作。

否则会出现很典型的浪费：明明每个元素地址都来自同一个 layout 公式，却让几十个 lane 各自跑一遍公式；明明相邻元素最后会落到同一条 cache line，却让它们以零散请求进入 memory；明明 mask 可以按 bitset 一次生成，却让每个 lane 自己判断有效性。结果是计算资源花在地址计算上，访存资源花在碎请求上，调度资源花在等待上，最后整个 gather/scatter 看起来能跑，性能却很难好。

所以未来昇腾核的小粒度访存能力，核心不是“让 SIMT 更会 gather/scatter”，而是要识别并硬化“结构化离散访问”。连续访问继续走 DMA fast path，结构化离散访问走 AGU + Index/MaskGen + Gather-Scatter，真正不可预测的访问再交给 SIMT 兜底。这样分层以后，硬件才不会把所有不连续访问都当随机访问处理，软件也不需要为了每一种 layout 手写一段地址计算逻辑。

大块连续搬运解决的是主干道，结构化 gather/scatter 解决的是城市路网，SIMT 负责那些导航地图上暂时没有标出来的小路。未来模型里，越来越多数据都落在中间这一档：不连续，但有结构；不适合传统 DMA，也不值得用 SIMT 硬算。AGU 把这类地址规则算出来，Gather-Scatter 把请求组织起来，Tile Memory Engine 再把结果整理成后端能直接消费的 Tile，这才是下一代核该有的小粒度访存路径。

### Scalar 要从“填表员”变成乱序控制核

复杂算子里，Scalar 经常是那个最不起眼、但最容易把整条流水卡住的角色。

它要读 tiling 参数，拷贝结构体字段，拼 descriptor，算 bitfield，算地址，发搬运，设同步，敲 doorbell，轮询状态，还要处理分支。说白了，它干的已经不是“配置一下加速器”这种轻活，而是在做一个小 CPU 的工作。

问题是，它干着 CPU 的活，却没有 CPU 的身板。

复杂模型里同时活跃的状态很多：base 地址、stride、shape、offset、loop counter、mask、descriptor 片段、实际序列长度、稀疏索引、通信状态、同步 token。它们不是简单的常量，也不是靠一组 uniform register 就能兜住的东西。很多状态会随着循环、分支、动态 shape 不断变化。寄存器不够，就只能 spill；一 spill，就打 Dcache；Dcache 一 miss，CUBE、Vector、MTE 都在旁边干等。

所以 ScalarBound 的本质，不是某几条 Scalar 指令慢，而是控制复杂度已经超过了现有顺序 Scalar 能承受的范围。

未来昇腾核里的 Scalar，应该升级成真正的块级控制核。它需要更多架构寄存器，给复杂 kernel 留出足够的活跃状态空间；也需要更接近乱序 CPU 的能力，能做分支预测、寄存器重命名、Load/Store 排队、乱序发射和有序提交。它不一定要做成大 CPU，但不能再只是一个顺序配置小核。

更多架构寄存器很关键。复杂控制流里，很多东西都是动态状态，不是固定常量。uniform register 可以放一些 loop invariant，但解决不了寄存器压力的根。真正能减少 spill、减少栈访问、减少 Dcache 压力的，是更多通用架构寄存器，以及更好的寄存器重命名和调度能力。

乱序能力也很关键。Scalar 在算地址、读参数、准备 descriptor、判断分支、发 TileOP 的过程中，有不少工作可以提前做，也有不少工作可以和 memory miss 重叠。如果还是强顺序执行，一个参数 miss 就可能把后面全堵住。乱序 Scalar 至少可以把不相关的准备工作先推进，不要让 CUBE 和 Vector 等它填表。

当然，Scalar 变强不是为了让它继续填更多表。搬运和计算接口也要收敛，descriptor 要支持 base + delta，常用配置要能缓存，底层字段不要一遍遍让软件重拼。Scalar 应该负责组织 Tile 数据流、做依赖管理、处理异常和动态控制，而不是天天给各个加速器抄配置单。

一句话，下一代核不能再把 Scalar 当小秘书用。它应该是块级调度的大脑。CUBE、Vector、SIMT、MTE 都很强，但没有一个足够强的乱序 Scalar 把它们组织起来，复杂模型还是会卡在控制、参数和动态调度上。

### 通讯指令和计算指令要站在同一个抽象层级上

未来模型里的通信，已经不能再当成计算旁边的一段外部流程。

MoE 的 token 要路由，A-F 分离里不同阶段要频繁交换数据，长序列推理里 KV 和 page 状态会跨单元流动，多流融合里通信和计算本来就想互相掩盖。过去通信更多像层间开销，放在算子外面处理也还能接受；现在通信越来越细、越来越频繁，几微秒的启动、等待、轮询和同步，放到几十层、上百次交互里，很快就会变成 token latency 里的硬开销。

现在很多通信动作的问题，是它们没有和计算站在同一个抽象层级上。计算这边已经在谈 Tile、依赖、ready、issue、commit，通信那边还像挂在外面的控制动作：doorbell 要特定通路敲，CQE 要轮询，Atomic 在不同单元上各有一套语义，通信 task 和计算 task 的 trace 很难自然连起来。硬件乱序流水线能看见 CUBE、Vector、Memory 的依赖，却看不清一次远端数据什么时候发出、什么时候可见、什么时候返回、哪个本地 Tile 正在等它。调度系统看不见通信，通算融合就只能靠软件猜时序。

下一代核里，通信指令应该和计算指令使用同一个抽象层级。一次远端 Tile 的 Push，一次本地 Tile 的 Pop，一次跨核 Scatter，一次 Broadcast，一次 Atomic exchange，本质上都应该是 Tile 数据流里的操作，和 TMMA、TVEC、TLOAD 一样进入统一的乱序流水线。它们有输入 Tile、输出 Tile、有依赖、有 ready 状态、有异常、有提交边界，也应该被同一个调度器看到。

这里要特别小心同步通信。同步通信如果直接占住 ROB，等待远端返回，就会把本来可以继续推进的本地计算一起卡住。ROB 里挂着一个等远端的通信操作，后面的本地 ready Tile 发不出去，CUBE、Vector、Memory 都可能因为一个远端事件停在原地。这种设计看起来语义简单，实际非常容易把通算融合做成通算互卡。

更合理的方式，是把通信改成异步的 Push/Pop 消息机制。

Push 负责把一个 Tile 或一段消息发出去，它进入乱序流水线时只需要完成本地建序、权限检查、地址或目的地解析、消息注入和必要的可见性语义，不应该一直占着 ROB 等远端消费。Pop 负责在本地消费一个已经到达或将要到达的消息，它可以表现为一个普通的 Tile 输入依赖：消息没到，这个 Pop 相关的 Tile 不 ready；消息到了，依赖被唤醒，后续计算继续走。这样远端时延不会变成 ROB 的硬阻塞，而是变成 Tile ready 图上的一个等待边。

在这个体系里，通信操作大致可以分成几类。Push 类操作负责把 Tile、token、index、KV 或中间结果送到远端；Pop 类操作负责从本地消息队列或远端通道取出可消费的数据；Broadcast、Scatter、Gather 是 Push/Pop 的批量和路由化表达；Atomic 负责跨核同步和小粒度信息交换；Doorbell 和 event 不再是某条特殊通路上的副作用，而是通信 Tile 的事件语义。它们都应该有统一的数据类型、内存语义、异常语义和 trace 语义。

这样做以后，通算融合会自然很多。一个 Tile 发起 Push 后，本地后续无关计算可以继续；另一个 Tile 需要远端数据时，通过 Pop 形成依赖；调度器知道哪些 Tile 等通信，哪些 Tile 只等本地数据，哪些通信可以提前发，哪些计算可以插空做。通信不再是算子外面的一段黑盒控制流，而是和计算一样被统一乱序流水线调度的数据流节点。

这也会倒逼 Atomic 语义收敛。现在如果标量、向量、MTE 各自有一套 atomic，通信和同步就很难做成统一系统。未来 Atomic 应该作为通信/同步 Tile 的一种语义，由统一的内存模型定义 acquire、release、exchange、add、compare-and-swap、message visible 等行为；底层走哪条物理通路，可以由硬件选择，但软件看到的是同一套语义。否则多核同步、生产者消费者队列、跨核 mailbox、远端事件唤醒都会继续散成几套解释体系。

最终目标很简单：通信和计算都进入同一张 Tile 数据流图。计算指令不再只是在本地算，通信指令也不再只是外部控制动作；它们都被 rename、issue、wakeup、commit 和 trace 机制管理。同步通信少用，避免卡住 ROB；异步 Push/Pop 成为主路径，让远端等待变成依赖图上的 ready 问题，而不是流水线里的全局堵点。只有这样，通算融合才不是软件手工掩盖时延，而是硬件真的能看见、能调度、能重叠。

### DFX/RAS 要回到 CPU 的调试框架里

现在写算子，很多时间不是在写算法，而是在和现场搏斗。

一个 kernel 跑不起来，最怕的不是报错，最怕的是它不说人话。它可能只是挂住，可能偶现，可能换个 shape 就死，可能单流没事、多流一开就踩内存，可能同步早了一拍，也可能某个搬运晚了一拍。你看得到一个很粗的错误码，看不到它到底停在哪条指令；你知道某个 pipe 不对劲，却不知道是哪一个 Tile 把后面全堵住；你怀疑是越界，但现场已经被后续 outstanding 请求冲掉了。最后大家只能加日志、打 dump、插 wait、减小 shape、关掉一半流水，再一点点把问题逼出来。

这种调试很耗人。很多时候，功能代码半天写完，调试要花几天；性能优化看起来是在追极限，实际大部分时间是在问“它为什么卡住”。更难受的是，这些问题往往不是一个人能看明白的，算子、编译器、runtime、硬件、驱动都要拉进来，一群人围着几段 trace 猜来猜去。说是软件开发，干起来像事故勘查；说是性能优化，日常更像修水管，哪里漏了先堵哪里，堵完还要祈祷别的地方别爆。

这里面很多痛苦，本来可以由硬件多承担一点。

如果核里有精确 PC，挂住时能停在明确位置，开发者至少知道从哪开始看；如果 Tile 有明确状态，能看到哪个 Tile ready、哪个 Tile 在等 memory、哪个 Tile 在等通信、哪个 Tile 已经提交，问题就不会变成一团雾；如果 Load/Store Queue 能保留访问 range，越界和踩内存就不用靠猜；如果通信 Push/Pop 有事件状态，远端没回、本地没发、CQE 没到就能区分清楚；如果异常现场能保住，调试就不用靠复现撞运气。

更进一步，如果未来核能接进 CPU 这套成熟调试框架，软件会轻松很多。perf 能采样热点，火焰图能看耗时分布，泳道图能看 CUBE、Vector、Memory、Comm 谁在跑谁在等，gdb 能停住、单步、看寄存器、看 Tile 状态。人类写 CPU 程序这么多年，已经积累了一整套 debug 方法：断点、单步、回溯、计数器、trace、core dump、符号表、调用栈。AI Core 没必要重新发明一套黑盒玄学，更没必要让每个算子开发者都从“如何猜一个异步加速器为什么挂住”开始修炼。

所以 DFX/RAS 不是最后补几个计数器，也不是出问题后多打印几行日志。它应该进入执行模型本身。Tile ROB 负责保存提交状态，Tile Rename Table 负责保存逻辑 Tile 到物理位置的映射，Load/Store Queue 负责记录内存访问顺序和范围，通信队列负责记录消息状态，task trace 把不同执行单元的事件串起来。硬件多记一点状态，多给一点可观测性，软件就少掉很多无效劳动。

这件事的价值很现实。硬件多做一点，软件就少熬几晚；硬件能精确停住，软件就不用靠插 wait 撞概率；硬件能把 trace 串起来，开发者就不用拉一堆人开会猜“谁等谁”；硬件能区分本地错误和远端错误，问题就不会在几个团队之间来回踢。算子开发最宝贵的时间应该花在数据流、tiling 和性能模型上，而不是花在复现一个偶现挂死上。

未来的 AI Core，应该像 CPU 一样能被调试、能被观察、能被中断、能被恢复。跑得快当然重要，但跑挂以后能讲清楚自己为什么挂，也同样重要。否则峰值再高，开发者也得天天在黑盒旁边烧香。真正成熟的下一代核，应该让人少猜一点，让工具多看一点，让问题早暴露一点，让软件开发从“破案”回到“工程”。

### 12. 持续功耗控制不能只靠降频，要进入调度本身

长序列、多模态和高并发推理，最容易把芯片推到一种很难受的状态：短时间 benchmark 很漂亮，CUBE、Vector、Memory、Comm 都能拉起来，曲线也很好看；可一旦连续跑几百毫秒、几秒，整板功耗撞到 TDP，power cap 触发，频率被压下来，TPOT 开始抖，客户看到的就不是峰值有多高，而是性能为什么一会儿快、一会儿慢。

芯片里其实有很多 power sensor，能看到不同区域、不同时间窗口里的功耗变化。问题不在于“能不能知道功耗高了”，而在于知道以后能做什么。如果硬件执行方式是完全静态拍好的流水，软件已经把 CUBE、Vector、Memory 的节奏排死了，运行中没有多少调度余地，那么功耗一旦顶到 TDP，最直接、也几乎唯一有效的手段就是降频。降频当然能降功耗，但它像一脚踩刹车，所有东西一起慢下来，矩阵慢，搬运慢，Vector 慢，延迟也跟着抖。

乱序动态调度给了另一种空间。既然 Tile 是运行时发射的，既然 CUBE、Vector、Memory、Comm 都要经过调度器排队，那么功耗控制就不一定只靠粗暴降频。功耗高的时候，可以先约束调度，稍微放慢 CUBE 的发射密度，拉开高功耗 Tile 的间隔，让 Vector 或 Memory 的工作插进来，把瞬时电流峰值摊平。很多时候系统并不需要把所有单元同一时刻拉满，尤其在通算融合和多流场景里，只要端到端数据流不断，CUBE 晚发几拍，可能比整核降频更划算。

这其实和 CPU 的思路很像。CPU 做功耗控制，不只是等到温度或功耗超了再降频，它还可以通过调度、发射、资源选择、指令节奏去控制瞬时功耗和 di/dt。乱序核天然有一个调度点，能决定这一拍发什么、下一拍缓什么、哪些高切换活动不要堆在一起。AI 核如果继续走静态流水，功耗控制就很难精细；如果走 Tile 级动态调度，power sensor 反馈就能进入调度策略，变成“少发一点、错开发一点、换个资源先发一点”，而不是只有“降频保命”这一招。

这里的关键不是让性能无损，也不是说调度约束可以替代 DVFS。真正的目标是给系统多几个旋钮。到了 TDP 附近，第一层可以做发射节流，比如限制 CUBE 连续发射窗口、降低某类高功耗 Tile 的并发度、把访存和 Vector 工作错开；第二层可以做资源配比，比如 Prefill 阶段保护 CUBE 和 HBM，Decode 阶段保护小粒度访存和通信，低 bit 阶段注意 Vector、Fixpipe 和重排；第三层再做分域 DVFS，必要时降低某个区域频率或电压；最后才是更粗粒度的整核或整卡降频。

这样做还有一个好处，就是对 di/dt 更友好。大矩阵 Tile 连续发射时，CUBE 阵列切换很猛，电流变化也猛；如果调度器能看到功耗传感器和发射队列，就可以把高功耗块打散，让电源和封装看到的瞬时冲击小一点。对长序列和高并发推理来说，这种“把峰摊平”的能力很重要，因为客户关心的不是某一瞬间冲得多高，而是长时间稳定跑在一个可预测的性能点上。

未来昇腾核的功耗控制，应该和 Tile 调度、DFX 统计、power sensor 反馈放在一起设计。每类 Tile 大概消耗多少功耗，哪个执行后端正在高负载，哪个区域接近 TDP，哪个阶段需要保护 latency，调度器都应该能看到一部分信息。这样 power control 不再只是电源管理模块在后面喊“超了，降频”，而是前端调度器在运行时就能调整发射节奏。

模型阶段也要被考虑进去。Prefill 吃矩阵和带宽，Decode 吃 KV、小粒度访存和通信，MoE 吃路由和 all-to-all，推荐吃 gather 和不规则控制流，低 bit 可能让重排、scale、Vector 后处理变成瓶颈。不同阶段的功耗热点不一样，调度策略也不该一样。静态流水只能按最坏情况保守设计；动态调度可以根据当前队列和 sensor 状态做更细的取舍。

所以持续功耗能力，不能只理解成“散热更强”或者“频率策略更保守”。未来核要把功耗控制做进调度里面。硬件多一点观测，多一点发射约束，多一点分域调节，就能让软件少面对那种最痛的情况：模型跑起来很好看，跑久了突然被 power cap 打一拳，然后所有性能分析都变成“它刚才到底为什么降频”。

最终目标不是永远不降频，而是降得更晚、更细、更可解释。能靠调度摊平的，就不要先降频；能压 CUBE 发射密度解决的，就不要把整个核拖慢；能错开高功耗 Tile 的，就不要让电流峰值硬撞上去。这样下一代昇腾核才能不只会短跑冲峰值，也能在真实业务里稳稳地跑长程。

### 结论

昇腾当前遇到的问题，已经不能简单归结为某个单元算力不够、某条通路带宽不够、某条指令还不完备。真要这么简单，大家早就把表格拉出来，哪个弱补哪个，年底再贴一张“全面提升”的胶片，问题就算闭环了。可惜架构这东西，从来不是 Excel 里把短板涂红就能解决的。

真正的矛盾来自模型形态变化之后，数据流变得更碎、更动态、更低精度、更依赖通信、更依赖小算子和不规则访存，而现有核仍然主要依赖显式 buffer、固定流水和软件手工编排来组织这些工作。于是我们就进入了一种很熟悉的状态：CUBE 说我已经很努力了，Vector 说你算完倒是把数据给我啊，MTE 说我也想搬但参数有点多，Scalar 说别吵我还在拼 descriptor，SIMT 说我能处理复杂场景但别指望我一夜之间变成 GPU，DFX 在角落里默默补一句：你们先跑，挂了以后记得别问我现场去哪了。

这当然是玩笑话，但玩笑背后就是现实。计算单元各自都不弱，弱在交接；片上存储不是不丰富，难在管理；低 bit 不是没有峰值，痛在全链路；SIMT 不是没有能力，缺在成为主路径；通信不是不能做，问题在于它越来越像模型数据流的一部分，却还带着外部控制动作的影子。过去靠专家手工把这些东西拧在一起，像老师傅开手动挡赛车，听发动机声音就知道该不该换挡；未来客户越来越多、模型越来越多、shape 越来越野，再指望每个算子都由绝地武士亲自调原力，显然不太现实。绝地武士也要休假，牛马也想准点下班。

因此，未来昇腾核的核心方向，应当从矩阵峰值转向复杂模型的数据流效率。这个方向包含几个关键判断：逻辑 Tile 要成为统一数据对象；片上存储要向 Tile Register 体系演进；CUBE、Vector、SIMT 要成为统一 Tile 的执行后端；搬运引擎要从固定 DMA 升级为消费者视角的 Tile Memory Engine；低 bit 要作为端到端数据流设计；SIMT 要成为不规则模型主路径；通信、Atomic、Doorbell、CQE 要进入 Tile 数据流；DFX/RAS 要基于 Tile 精确状态内建；功耗和资源配比要支持模型阶段动态调节。

如果说过去的昇腾核是一台高效的矩阵机器，未来昇腾核应该成为一台面向大模型的 Tile 数据流机器。它仍然要保留 NPU 的高能效矩阵能力，毕竟发动机不能丢；但它还要长出更好的变速箱、更顺的传动轴、更聪明的导航、更清晰的仪表盘，以及出问题以后能告诉你“刚才到底是谁在第几个路口压了线”的行车记录仪。块级乱序、统一数据承载、可编程重排、SIMT 并发、通信事件化和生产可观测能力，本质上都是为了让这台机器不再只会在理想赛道上跑 peak，而是能在真实道路上跑业务。

架构做到最后，最好的状态应该是：高手仍然有空间把性能压到 Speed of Light，普通工程师也能在不献祭周末的情况下写出靠谱代码；硬件底层足够强，软件抽象也接得住；客户想看底层时看得明白，不想看底层时也不用被迫考古。到那个时候，我们再讲 PTO、Tile、下一代核，就不用像推销一份复杂说明书，而可以更有底气地说：这不是包皮，也剪不掉，这是硬件真的开始理解数据流了。

这会是下一代昇腾核架构最重要的方向。至于我们这些菊场牛马，愿望也很简单：少解释几遍 atomic，少抢救几个挂死，多让模型自己跑满。真到那一天，哪怕韬定理继续在天上飞，我们在地上拧螺丝的人，也算终于把这辆车从“手动挡性能怪兽”，慢慢调成了一台普通人也敢开、高手还能飙的好车。
