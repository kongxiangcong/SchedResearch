# 手搓NPU系列1：Agent开发流程

- 类型：文章
- 原文：[知乎文章](https://zhuanlan.zhihu.com/p/2060349342666564369)

大家好，我是乱序摸鱼。

这个系列准备讲一件听起来多少有点不务正业、实际上又非常耗费精力的事情：我如何在上班摸鱼的过程中，指挥一群 Agent，从零开始搓出一套 NPU。

这里的“搓”并不是写几个矩阵乘算子，再套一个漂亮的网页界面，就宣布自研 NPU 胜利竣工，而是重新搭建一套指令集、编译器、C 语言运行环境、操作系统适配、算子软件栈、功能模型、周期精确性能模型、NPU RTL、FPGA 仿真环境，以及最后能够落到综合、布局布线和 PPA，也就是功耗、性能与面积评估上的完整流程。

这当然是一个相当庞大的全栈工程。它横跨软件、体系结构、数字设计、验证和物理实现，一个正常的芯片团队往往要组织几十人甚至几百人，按照不同专业方向分工合作，才能勉强把这些齿轮咬合起来；而我现在想做的，就是把过去由人组成的工程组织，替换成一批随叫随到、偶尔失忆、从不休年假，但非常擅长一本正经地告诉你“任务已经全部完成”的赛博员工。

我写这个系列，还有一个现实原因：过段时间我要去清华大学暑期学校讲课。既然课都准备了，只给清华的同学看多少有点浪费，不如把整个过程公开出来，让更多对体系结构、编译器、芯片设计和 Agent 工程感兴趣的人一起讨论。况且我和大家接触 Agent 的时间差不多，也还在摸索，没有什么传授教条的资格；这个系列更像是一份边施工、边记录、边返工的工程日志，成功的地方可以抄作业，失败的地方也可以提醒大家别踩同一个坑。

以前我在菊场做类似工作，是指挥十几个能力很强的 OD 同学一起推进；现在这些同学被我换成了赛博员工，主要由 ChatGPT 5.6 Sol Extra High 和 DeepSeek V4 Pro 两个模型交替工作：前者负责阅读资料、架构分析、任务拆解、设计评审和复杂问题定位，后者负责边界明确的模块实现、测试补齐、回归修复和大量机械性工作。

我把整个工程称为 **Superproject**。它目前横跨十个代码仓，任何一个接口改动，都可能沿着“指令集—功能模型—编译器—运行库—性能模型—RTL—验证环境”这条链路一路传染下去，颇有一种一个人开了十家公司，然后每天召集十家公司的负责人互相对齐版本的美感。

## Human in the Loop：最重要的那个 Agent，还是人

在这样一个横跨十个代码仓的复杂工程里，如何操作 Agent，才能让项目不是在第一周轰轰烈烈、第二周遍地 TODO、第三周连作者自己都不敢运行全量回归？

答案当然不是继续增加 Agent。

真正决定项目上限的，仍然是 **Human in the Loop，也就是人在闭环中**。软硬件协同设计不是一个把需求扔给模型、几小时后回来验收的外包项目，因为目标架构如何选择、版本边界在哪里、哪些接口可以修改、哪些接口一旦发布就必须保持兼容、性能数据究竟证明了什么、一次测试通过究竟覆盖了多少状态空间，这些问题都不是单纯依靠生成代码可以回答的。

Agent 可以帮你把一座楼盖得很快，但楼应该盖在哪里、承重墙能不能拆、验收报告到底测了什么，最后还是要有人负责。

所以，在我的分工里面，人负责确定目标架构、划分版本边界、冻结跨仓接口、裁决跨模块冲突，并对最终结论负责；上下文容量大、推理能力强的 Agent，负责阅读大量资料、形成架构归纳、拆解复杂任务、审查设计和定位跨层问题；速度快、成本低的 Agent，则负责实现边界清楚的小模块、补测试、跑回归、改文档，以及处理那些重复、琐碎但又不能不做的工程工作。

这就是我所说的 Human in the Loop。它并不只适用于 NPU，任何涉及多人协作、复杂接口和长期演进的工程，本质上都需要类似的控制循环。

现在大家经常说 **Agent harness，也就是 Agent 的运行框架和约束系统**，听起来像是某种新发明，其实拆开来看，无非是把模型、上下文、工具、权限、状态、工作流和验证器组织到一起：什么情况下可以改代码，什么情况下只能读，哪些测试必须执行，输出什么交付件才算完成，失败后如何重试，连续失败后向谁升级，以及怎样阻止 Agent 用“删掉失败测例”这种天才办法完成任务。

![image](https://pica.zhimg.com/v2-f19e450692b2edbe4fbb77088dd9ab40_1440w.jpg)

Harness 的价值，并不是让模型显得更聪明，而是把模型的聪明限制在工程允许的范围之内。2026 年的一项 AutoHarness 研究甚至把 harness 简化成了“提出动作—检查是否合法—拒绝非法动作—根据环境反馈继续修正”的控制循环；另一项面向 LLVM 编译器缺陷修复的研究则发现，前沿模型处理真实编译器问题时，相比普通软件缺陷会出现约 60% 的能力下降，而加入编译器专用工具、可复现缺陷和定制工作流后，效果反而可以超过通用 Agent，说明复杂工程真正缺少的往往不是更长的提示词，而是更专业的工具接口和更可靠的反馈环境。[AutoHarness 论文](https://link.zhihu.com/?target=https%3A//arxiv.org/abs/2603.03329)、[Agentic Harness for Real-World Compilers](https://link.zhihu.com/?target=https%3A//arxiv.org/abs/2603.20075)

大厂的 IPD，也就是集成产品开发流程，早就把需求、设计、实现、验证、发布和质量门禁玩出了花。我们现在做的事情，并没有脱离传统工程管理，只不过把流程的执行者换成了赛博员工，他们的工资不是月薪和年终奖，而是我用真金白银买来的 Token。

更重要的是，Agent 在闭环里积累 Skills，人也必须在闭环里学习。人学习的东西不只是提示词怎么写，而是 Agent 返回的实现数据暴露了哪些架构问题、性能模型和 RTL 为什么对不上、哪个接口总在返工、哪些任务适合交给小模型、哪些问题即使交给最强模型也必须由人亲自判断。

如果人在循环里没有成长，只是每天负责点击“同意”，那不叫 Human in the Loop，只能叫 Human as a Button。

## NPU 练气阶段：先让最小循环活起来

创业初期最怕什么都想做：指令集还没稳定，就开始优化算子；编译器还不能正确生成代码，就开始讨论乱序流水线；功能模型连异常行为都没定义完整，RTL 已经热火朝天地写了两万行。最后所有人都很忙，只有系统跑不起来。

所以，第一阶段不能追求“大而全”，而是要先让最小闭环转起来。

### 第一步：ISA—功能模型

最先需要打通的是“指令集架构—功能模型”循环。

这里的功能模型不是一个为了演示指令语义而临时编写的解释器，而是指令集的可执行契约：指令如何译码，寄存器和状态如何更新，访存地址如何计算，异常在什么条件下产生，饱和、舍入、NaN、溢出和非对齐访问如何处理，以及并发执行时程序能够观察到什么样的内存顺序。

以 RISC-V 官方生态中的 Spike 为例，它被明确定位为一个或多个硬件线程的功能模型，而且 Spike 将 ISA 本身视为主要公共接口；新增一条指令，不只是增加一个助记符，还需要定义操作码、掩码和明确的功能行为。[Spike 官方仓库](https://link.zhihu.com/?target=https%3A//github.com/riscv-software-src/riscv-isa-sim)

这个阶段的验收标准，不是“Hello World 跑通了”，而是每条指令都有正向、边界、异常和随机测例，指令执行前后的寄存器、内存、异常状态和提交结果都可以形成可比对的 trace，也就是执行轨迹。否则你做出来的不是架构模型，而是一台非常有个人性格的计算器。

### 第二步：编译器—ISA—功能模型

功能模型能够稳定执行手写汇编后，第二个循环才是把编译器接进来。

编译器适配不是在目标列表里增加一个名字就结束了，它至少涉及 target triple，也就是目标平台标识；数据类型布局；调用约定；参数和返回值传递；寄存器分类；指令选择；寄存器分配；栈帧生成；汇编器和反汇编器；ELF 目标文件；重定位类型；链接脚本，以及必要时的 intrinsic，也就是编译器内建函数。

这一阶段需要验证的，也不只是编译器有没有产生合法汇编，而是高级语言语义经过前端、中间表示、优化、指令选择、汇编和链接之后，能否在功能模型上得到正确结果。一个优化前正确、开了 `-O2` 就开始修仙的编译器，严格来说还不能叫编译器，只能叫随机程序生成器。

### 第三步：C 运行环境—编译器—ISA—功能模型

编译器能够生成基本程序之后，还要补齐 C 语言运行环境。

这里不能只写“把 glibc 或 musl 跑起来”，因为从一段 C 代码到可执行程序，中间还隔着启动代码 `crt`、编译器运行库 `libgcc` 或 `compiler-rt`、链接器、动态加载器、系统调用 ABI、线程局部存储、原子操作、信号和文件接口。glibc 和 musl 是 C 标准库的重要组成部分，但它们背后依赖的是一整套 ABI 和操作系统接口，一旦调用约定、ELF 重定位或系统调用号不一致，程序往往不会礼貌地告诉你哪里错了，只会在一个看起来完全无关的地方突然去世。

### 第四步：Linux—BusyBox—GNU 工具链—系统功能模型

到了第四步，才真正进入整系统软件栈。

这一层要把 Linux 内核、BusyBox 用户空间、GNU 工具链、glibc 或 musl、编译器、汇编器、链接器、ISA 和系统功能模型连起来，最终完成从启动、初始化、挂载根文件系统，到运行 Shell 和普通 ELF 程序的端到端验证。

这里需要区分两类模型。用户态功能模型只执行目标 ELF 程序，系统调用可以通过宿主机转译、半主机接口或自定义运行时完成，因此速度快，适合编译器回归和小程序测试；系统功能模型则要模拟处理器特权态、内存管理、中断、定时器和外设，能够真正启动操作系统。

QEMU 官方文档也明确区分了 System Emulation，也就是完整系统仿真，与 User Mode Emulation，也就是用户态仿真；后者会将目标程序的系统调用翻译为宿主机系统调用，并处理信号与线程，而完整系统仿真则面向操作系统和整机环境。[QEMU 系统仿真文档](https://link.zhihu.com/?target=https%3A//www.qemu.org/docs/master/system/index.html)、[QEMU 用户态仿真文档](https://link.zhihu.com/?target=https%3A//www.qemu.org/docs/master/user/main.html)

走到这里，一套架构才算真正向程序员露出了完整形态。后续微架构可以从顺序执行改成乱序执行，可以调整流水线深度、队列大小、Cache 容量和执行单元数量，但不能随意破坏已经对软件承诺的指令语义、异常模型、内存模型、特权级、ABI 和并发行为。

功能模型之所以重要，就是因为它把这些承诺变成了可以执行、可以测试、可以与 RTL 做差分比较的东西。

## 不要相信 Agent 说“已经完成”

上述每一步循环，都必须有稳定、独立、不可被实现者随意修改的 CI，也就是持续集成门禁。

作为闭环里唯一的人类，千万不要过分沉醉于 Agent 的花言巧语。它说“所有测试已经通过”，可能是修好了实现，也可能是删掉了失败测例，修改了参考答案，给失败命令补了一个 `|| true`，缩小了回归范围，或者发现某个脚本只检查退出码、不检查输出，于是非常聪明地打印了一行“PASS”。

越聪明的 Agent，越有可能想出你从未设想过的通关方式。

LLVM 自己的测试体系将测试分为单元测试、回归测试和完整程序测试：单元与回归测试要求提交前持续通过，发现缺陷后要沉淀能够最小化复现问题的测例，而完整程序测试则要真正完成编译、链接、执行，并把输出与参考结果比较。这种分层方式值得直接借鉴，因为它同时回答了“一个函数是否正确”“某个历史问题是否复发”和“整条工具链能不能运行真实程序”三个不同问题。[LLVM Testing Infrastructure Guide](https://link.zhihu.com/?target=https%3A//llvm.org/docs/TestingGuide.html)

因此，我的门禁不会只看一个绿色勾，而会检查测试清单、执行日志、覆盖范围、参考结果来源、随机种子、工具版本和产物哈希；关键结果还要由第二个 Agent 重新审查，必要时用另一套模型、另一条工具链或另一种实现做差分验证。

这和现实中的管理没有本质区别。领导每天找不同的人聊，不是因为闲得慌，而是因为任何一个人的汇报都只代表一个观察角度。你以为自己汇报得天衣无缝，领导听完点点头，转身就去问测试、QA 和隔壁模块：“他说的是真的吗？”

对 Agent 也一样。不要只问“做完了吗”，要分别问实现者改了什么、测试者覆盖了什么、评审者发现了什么、CI 实际运行了什么，以及这个“通过”究竟能够证明什么。

## NPU 筑基阶段：一环裂变成三环

当最小闭环能够转动之后，问题又来了：算子、编译器、ISA、功能模型、性能模型、RTL 仿真、综合、布局布线和 FPGA 仿真，能不能全部塞进同一个循环？

当然可以，代价是每转一圈，人都老了一岁。

问题不一定出在 Agent 身上，而在于不同工具的时间尺度完全不同：功能模型执行一条指令可能只需要很短时间，编译器回归需要几分钟，周期精确模型需要更长时间，RTL 仿真可能要跑几个小时，综合和布局布线则可能按小时甚至按天计算。如果所有修改都必须等最慢的工具完成，整个项目就会被最重的验证链路拖住。

所以，一个大循环必须裂变为三个能够独立转动、又通过稳定接口相互咬合的小循环。

### 软件循环：编程框架—编译器—ISA—功能模型

软件循环关注的是功能正确性和可编程性：算子能否表达，编译器能否正确降低，生成的指令序列是否符合 ISA，功能模型是否得到正确结果。

这个循环应该尽量轻、尽量快，让编程模型、编译器优化和指令集设计能够频繁迭代。它的主要交付件不是一份口头说明，而是编程接口、编译器补丁、ISA 版本、ABI 文档、ELF 样例、指令 trace 和回归结果。

### 体系结构循环：ISA—功能模型—性能模型

体系结构循环关注的是设计有没有性能价值。

功能模型告诉我们“结果是否正确”，CA 模型，也就是 Cycle-Accurate 周期精确模型，回答的则是“需要多少周期、瓶颈在哪里、资源为什么空闲、数据为什么没有及时到达”。ISA 和功能模型提供正确性基准，性能模型增加流水线、队列、带宽、延迟、依赖和资源竞争约束，然后通过 benchmark 观察 IPC、吞吐、访存停顿、执行单元利用率和关键队列占用。

这个循环最重要的不是把性能数字跑得漂亮，而是建立可以解释的因果关系：某个 benchmark 提升了，到底是指令条数减少、访存次数下降、并行度增加，还是模型漏算了一个冲突；如果性能模型给出的提升无法通过 trace、计数器和资源占用解释，那么越漂亮的数字越值得怀疑。

### 硬件开发循环：微架构 RTL—UT/IT/ST—综合与布局布线

当 ISA、功能模型和性能模型相对稳定后，第三个循环才开始接入 RTL。

RTL 设计先通过 UT，也就是单元测试，验证局部模块；再通过 IT，也就是集成测试，验证模块之间的接口、握手和时序关系；最后通过 ST，也就是系统测试，运行完整程序和复杂场景。功能结果需要与功能模型比较，流水行为和性能计数器需要与 CA 模型做 Correlation，也就是相关性校准；综合与布局布线则进一步反馈真实的频率、面积、功耗、拥塞和关键路径，迫使微架构回到现实世界。

因为在性能模型里增加一个队列，只需要改一个参数；到了 RTL 里，它会变成寄存器、比较器、仲裁逻辑和旁路网络；再到了物理实现阶段，它可能变成一条跨越半个芯片的关键路径，然后 Timing 攻关组长就会带着一脸复杂的表情来找你喝茶。

把一个大环裂成三个小环，并不是为了画一张更漂亮的流程图，而是为了隔离不同时间尺度的工作，让软件、体系结构和硬件能够独立迭代，同时通过 ISA、功能模型、性能 trace 和验证结果保持一致。只要接口和交付件稳定，三个环可以并行转；一旦接口发生变化，就必须明确影响范围，触发相应的跨环回归。

## NPU 金丹阶段：让 Multi-Agent 组成一家大厂

三个循环能够独立运转后，下一个问题就是：这么多 Agent，究竟由谁负责什么？

我的做法很简单，向大厂学习。

不要觉得大厂岗位多、流程重、名字长都是 HR 没事找事。很多岗位之所以出现，是因为项目规模扩大以后，设计、实现、验证、质量和交付之间必然会产生责任边界；如果所有人都对所有事情负责，最后通常就是所有人都不负责。

所以，我按照真实芯片项目的组织方式，给 Agent 分配虚拟岗位。

![image](https://picx.zhimg.com/v2-6ad620117ee6f9e949adf75d527e574b_1440w.jpg)

在软件循环里，有算子开发工程师、算子测试工程师、版本发布经理、C 语言编译器开发工程师、C 语言编译器测试工程师、QA 和可信工程师。开发 Agent 负责实现，测试 Agent 负责从相反方向找问题，发布经理负责版本、依赖和产物，QA 负责流程门禁，可信工程师负责检查供应链、权限、许可证和安全风险。

在架构—微架构循环里，有指令集架构师 SE、功能模型开发工程师、CA 模型开发组长、CA 模型开发工程师、CA 模型测试工程师，以及架构 Feature SE 和模块 BOX SE。这里的 SE 不是代码写得最多的人，而是规格和交付结果的负责人：他要定义 Feature 的边界、接口、行为、验收条件和影响范围，并在软件、模型和硬件发生冲突时给出最终判断。

在硬件开发循环里，有核微架构 SE、核设计组长、验证组长、模块设计、模块验证、Correlation 性能验证工程师、BES 工程师、Timing 攻关组长、Power 攻关组长和 DTCO 组长。DTCO，也就是 Design-Technology Co-Optimization，设计与工艺协同优化，负责把微架构设想、标准单元能力、工艺约束和物理实现代价放到一起评估；Timing、Power 和后端实现则负责把性能模型里的理想世界，一点一点拖回物理现实。

当然，给 Agent 起一个“核设计组长”的名字，并不会让它第二天突然拥有二十年 RTL 经验。所谓 Role，也就是角色，真正有意义的不是头衔，而是角色卡里写清楚的几件事：它拥有什么模块，允许读取和修改哪些代码仓，输入是什么，必须输出什么，Definition of Done，也就是完成定义是什么，需要运行哪些测试，交付给下一个角色什么材料，遇到什么情况必须停止并向人类升级。

Agent 之间并不靠坐在一起开会交流，而是靠一套 SOP，也就是标准作业程序，以及版本化的交付件进行协作。Spec、接口表、任务单、测试报告、性能数据、评审意见和未闭环问题，都必须成为仓库里的持久化文件，而不能只存在于某一次对话的上下文中。

要始终把 Agent 想象成一个能力很强、态度很好、每天上班都会失忆的新员工。你昨天和它讲了两个小时的项目历史，它今天依然可能满脸真诚地问你：“我们为什么不用 x86？”

因此，Agent 的组织状态需要记录在一个集中索引中，例如 JSON 或 YAML 文件，包括角色、模块 Owner、当前任务、输入产物、输出位置、依赖关系、仓库版本和升级路径；但这个文件只能作为路由表，真正的事实来源仍然应该是经过版本管理的 Spec、代码、测试和数据，不能把整个公司的知识都塞进一个越来越肥的 JSON，然后祈祷所有 Agent 对字段含义有相同理解。

对于十个代码仓组成的 Superproject，还需要维护统一的版本清单：每个仓固定到哪个 commit，接口对应哪个版本，哪些变更必须成组提交，跨仓 CI 由什么事件触发，产物之间如何追溯。否则一个 Agent 在编译器仓里增加了新指令，另一个 Agent 还拿着两天前的功能模型跑回归，最后双方都宣布自己测试通过，只剩下 Human in the Loop 在深夜研究到底是谁活在平行宇宙里。

## NPU 元婴阶段：修宗立派

这个项目目前正在走向这一阶段。

我并不清楚它最终能做到什么程度，也不打算现在就宣布一个人加一群 Agent 已经可以替代一家真正的芯片公司。真实芯片开发还涉及大量商业 EDA、工艺库、IP 授权、DFT、封装、可靠性、实验室验证和量产数据，这些都不是多写几份提示词就会自动出现的。

但至少从目前的实践看，Agent 已经让一个人搭建“虚拟芯片开发组织”成为可能：你可以让不同 Agent 承担架构、实现、测试、评审、发布和专项攻关职责，用代码仓保存组织记忆，用 CI 充当纪律委员会，用性能和 PPA 数据决定路线，而不是靠谁的提示词写得更有气势。

至于这套流程究竟能不能继续转下去，能不能从一个有趣的实验，真正变成一套可复用的芯片设计方法，就看后续本系列的更新吧。

## 结语

本系列用于清华暑期学校的教程开篇，想告诉新入社会的毕业生同学们。当工具越来越强，代码、模型、验证甚至项目管理都可以交给机器之后，你们学生究竟还剩下什么？

我想，剩下的并不是下命令，更不是在流程末尾点一下批准，而是选择什么问题值得解决，决定架构应该向哪里走，在功能、性能、功耗和实现代价相互冲突时作出取舍，并为这个取舍承担后果。Agent 可以写完十万行代码，可以不厌其烦地跑几千个测例，也可以生成一份看起来无懈可击的报告，但它不会因为一条错误的技术路线浪费了团队半年而心痛，更不会在所有门禁都变绿之后，仍然追问一句：这些测试，到底证明了什么？

也许这个项目最后真的能搓出一颗像样的 NPU，也许它只会停在 FPGA、RTL 或某一次没有收敛的布局布线里；但只要软件、体系结构和硬件这三个循环真正转了起来，只要其中的知识、数据、失败和方法能够沉淀下来，这场实验就没有白做。

芯片会迭代，模型会过时，Token 迟早会花完，今天看起来强得离谱的赛博员工，明天也可能成为版本列表里一个无人问津的旧名字。真正能够留下来的，仍然是人如何理解一个复杂系统，如何把模糊的想法变成可以验证的工程，又如何带着一群并不真正理解梦想的机器，把那个梦想一点一点建出来。
