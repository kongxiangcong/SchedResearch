# 浅谈昇腾虚拟指令集PTO 第二部分

- 类型：文章
- 原文：[知乎文章](https://zhuanlan.zhihu.com/p/1987661046970880273)

**PTO (Parallel Tile Operation)**是华为海思为昇腾芯片设计的一套围绕着Tile设计的虚拟指令集。今天继续为大家讲解PTO里面的奥秘。

今天基于PTO指令的python编程框架pyPTO开源了，[AtomGit | GitCode - 全球开发者的开源社区,开源代码托管平台](https://link.zhihu.com/?target=https%3A//gitcode.com/cann/pypto)欢迎试用拍砖提issue。PyPTO的最底层，用的就是PTO Virtual ISA, 俗称TileOP。

本次部分，主要给大家传递的观点**是PTO ISA，Domain Specific Accelerator DSA的福音**。

我们的达芬奇架构，是一套DSA的交响乐团。你需要一个能力强的指挥，让各个DSA加速器有节奏的运转起来，才会响起悦耳的交响曲。如果这个时候，指挥不当的话，就是一曲杂音，不堪入耳。

![image](https://pic2.zhimg.com/v2-8f56e9440e9b833de937cbc1a43c97ff_1440w.jpg)

PTO就是指挥看到的五线谱。是指挥各种乐器的和弦谱。

五线谱当然是跨平台的，我们把竖笛换成唢呐，音色可能会变，但是音调绝不会变形。

**因此，五线谱，就是音乐中的指令集。**

**这个指挥，在达芬奇架构中，就是Scalar Unit。它会为CUBE, MTE, VEC, FIXP等各种加速器，编排好合理的节奏。它给各个加速器发出的，就是一堆异步的命令。PTO指令，就是发给达芬奇核Scalar Unit的编排好的五线谱。**

![image](https://pic3.zhimg.com/v2-dc9c7a91074f6aaacfa45c281591f6a0_1440w.jpg)

为什么这样说？我举一个PTO指令的例子：

用PTO指令如何做矩阵乘？

![image](https://pic1.zhimg.com/v2-8ab7cabf5cfa6917e1193c6f7e37adf6_1440w.jpg)

PTO指令有多个抽象层级的接口，例如字节码/IR的形态，这种就是从上层框架直接传下来的接口。

```text
%t0 = tload %sv[%c0, %c0] : (!pto.memref<...>, index, index) -> !pto.tile<...>
%t1 = tload %sv[%c0, %c0] : (!pto.memref<...>, index, index) -> !pto.tile<...>
%t2 = textract %t0 : !pto.tile<...> -> !pto.tile<...>
%t3 = textract %t1 : !pto.tile<...> -> !pto.tile<...>
%acc = tmatmul %2, %3 : (!pto.tile<...>, !pto.tile<...>) -> !pto.tile<...>
```

它也有直接API调用的PTO Intrinsic形态，可以直接在CCE里面手写Intrinsic：

```text
TLOAD(aMat, aGlobal);
TLOAD(bMat, bGlobal);
TEXTRACT(aTile, 0, aMat);
TEXTRACT(bTile, 1, bMat);
TMATMUL(cTile, aTile, bTile);
TSTORE(cGlobal, cTile);
```

它整体的作用，就是将一个五维的Tensor，通过NDDMA加速器(copy_gm_to_cbuf_multi_nd2nz)，加载到L1 Buffer中。然后在L1中，拆成多个subtile, 通过MTE1加速器把左矩阵加载到L0A buffer时候转成了NZ格式(RowMajor)，然后通过MTE1把右矩阵加载到L0B buffer中，并转置了一下变成(ColMajor)(load_cbuf_to_ca_transpose). 两个操作准备好了以后，就开始矩阵乘。源源不断的喂给了一个16x16x16的Systolic Array，并在ACC Tile上进行累加，写到L0C buffer中。最后从L0C buffer中，拷贝出来，走了一个Fix Pipeline, 做了一个随路的量化，写回了五维Tensor的其中一块中。

![image](https://picx.zhimg.com/v2-4feb0d584d585ce3cb8f5d7e106f08b1_1440w.jpg)

CUBE的内部数据流

你可以看到，PTO指令的简单的几行，就隐藏了多少个底层DSA加速器。

但是，为了用好一个systolic array，我们需要源源不断的给它为数据，满足其大带宽的要求，是非常不容易的事情。相比NV的Tensor Core来说，达芬奇核用了一个标量单元SU，通过异步的DMA操作(MTE)，将CUBE的流水编排好。

如何编排好这个流水？一个CUBE运算，从左边流入到右边流出，需要8拍的时间。这个时候，我们需要向里面持续不断的塞进去8x16x16x16x2的输入进去。在塞的同时，还要确保输出Buffer C有地方可存，需要检查unit flag一样的credit, **确保输出不会被覆盖**。

因此我们围绕着CUBE实现了一套C语言。这个语言叫做CCE (Cube compute engine)。在CCE之前，还有一套古老的语言，叫做CM (C Matrix)。这些就是PTO Tile编程的最初溯源。

因此，矩阵乘的流水线上，需要TLOAD, TEXTRACT, 要源源不断的流水进，流水出。当前的MATMUL正在计算的同时，下一次TLOAD就要启动了。另外一边的TExtract就开始转置了。

这个就是我们俗称的Ping-Pong buffer。

下面我会展示一下使用手动模式下，如何用PTO 写一个矩阵乘的Ping-Pong buffer。

![image](https://pic1.zhimg.com/v2-2b13070d98cece414958408fae38a0c0_1440w.jpg)

```text
AICORE inline void ProcessKIteration(uint32_t kIter, __gm__ U *currentSrc0, __gm__ S *currentSrc1,
    Tile<Mat, U, baseM, baseK> aMatTile[2],
    Tile<Mat, S, baseK, baseN> bMatTile[2],
    TileLeft aTile[2], TileRight bTile[2],
    TileAcc &cTile)
{

    int cur = kIter % 2;
    GlobalDataSrcA gmA(currentSrc0 + kIter * baseK);
    GlobalDataSrcB gmB(currentSrc1 + kIter * baseK);

    TLOAD(aMatTile[cur], gmA);
    TLOAD(bMatTile[cur], gmB);
    TMOV(aTile[cur], aMatTile[cur]);
    TMOV(bTile[cur], bMatTile[cur]);
    if (kIter == 0) {
        TMATMUL(cTile, aTile[cur], bTile[cur]);
    } else {
        TMATMUL_ACC(cTile, cTile, aTile[cur], bTile[cur]);
    }
}

AICORE inline void runGEMMBASIC(__gm__ T *out, __gm__ U *src0, __gm__ S *src1)
{
    // get gm offset of each core
    constexpr uint32_t mIter = M / singleCoreM;
    uint32_t mIterIdx = get_block_idx() % mIter; // get current core idx
    uint32_t nIterIdx = get_block_idx() / mIter;
    uint64_t currentGmOffsetA = mIterIdx * singleCoreM * K;
    uint64_t currentGmOffsetB = nIterIdx * K * singleCoreN;
    uint64_t currentGmOffsetC = mIterIdx * singleCoreM * N + nIterIdx * singleCoreN;
    __gm__ U *currentSrc0 = src0 + currentGmOffsetA;
    __gm__ S *currentSrc1 = src1 + currentGmOffsetB;
    __gm__ T *currentDst = out + currentGmOffsetC;

    using NDValidShapeC = TileShape2D<T, baseM, baseN>;
    using NDWholeShapeC = BaseShape2D<T, M, N>;
    using GlobalDataOut = GlobalTensor<T, NDValidShapeC, NDWholeShapeC>;

    using TileMatAData = Tile<TileType::Mat, U, baseM, baseK, BLayout::ColMajor, baseM, baseK, SLayout::RowMajor>;
    using TileMatBData = Tile<TileType::Mat, S, baseK, baseN, BLayout::RowMajor, baseK, baseN, SLayout::ColMajor>;

    TileMatAData aMatTile[2];
    TileMatBData bMatTile[2];

    using LeftTile = TileLeft<U, baseM, baseK, baseM, baseK>;
    using RightTile = TileRight<S, baseK, baseN, baseK, baseN>;
    using ResTile = TileAcc<T, baseM, baseN, baseM, baseN>;

    LeftTile aTile[2];
    RightTile bTile[2];
    ResTile cTile;
    constexpr uint32_t kLoop = singleCoreK / baseK;

    for (uint32_t kIter = 0; kIter < kLoop; kIter++) {
        ProcessKIteration<T, U, S, M, K, N, baseM, baseK, baseN>(kIter, currentSrc0, currentSrc1,
            aMatTile, bMatTile, aTile, bTile, cTile);
    }
    TSTORE(dstGlobal, cTile);
}
```

在PTO的语境中，Ping-Pong buffer，就是定义了两个一模一样的Tile。可以Declare为：

Tile tuple[2];

通过一个指针，对0和1进行Flip，完成一个Ping-Pong Buffer的实现。

当前CUBE在运算Tile-0的时候，TLoad在写入Tile-1。然后以此交替。

那进阶版的SoftMax该怎么写呢？

```text
#include <pto/pto-inst.hpp>
using namespace pto;

template <typename T, int M, int N>
AICORE void RowSoftmaxOneTile(__gm__ T* out, __gm__ T* in) {
  using GT = GT2D<T, M, N>;
  using XTile = Tile<TileType::Vec, T, M, N>;
  using Col1 = Tile<TileType::Vec, T, M, 1>;

  GT gin(in), gout(out);
  XTile x(M, N), tmp(M, N);
  Col1 row_max(M, 1), row_sum(M, 1);

  TLOAD(x, gin);
  TROWMAX(row_max, x);
  TROWEXPAND(tmp, row_max);
  TSUB(x, x, tmp);
  TEXP(x, x);
  TROWSUM(row_sum, x);
  TROWEXPAND(tmp, row_sum);
  TDIV(x, x, tmp);
  TSTORE(gout, x);
}
```

上面这段 Softmax 代码是 Auto 模式的写法：看起来很顺，但现实里，真正的乐团不会这么乖。

TLOAD 刚把琴搬上台，遇到的CacheMiss，TROWMAX 就想开始演奏，结果发现琴还在门口，音符直接弹空气，于是你就听到了传说中的：“性能杂音”。于是Set/Wait Flag就派上用场了。

这时候，作为性能调优专家，你就得上场了，开启了Manual模式。当你发现，Softmax就是一个链条：

load → rowmax → expand → sub → exp → rowsum → expand → div → store

那我们是不是可以这样安排一下？

- 当 **Tile0** 在做 `TROWMAX` 的时候，**Tile1** 可以在 `TLOAD`
- 当 **Tile0** 在做 `TEXP` 的时候，**Tile1** 可以在 `TROWMAX`
- 当 **Tile0** 在 `TSTORE` 的时候，**Tile2** 已经在 `TEXP`

只要你把 Tile 做成 **Ping-Pong / Triple Buffer**，再把同步插对，整条流水就会像交响乐一样：

- 搬运组永远在搬运
- 演奏组永远在演奏
- 没有人干等
- 也没有人抢拍

因此，作为高端指挥，你应该这样排流水：

load1 → rowmax1 → expand1 → sub1 → exp1 → rowsum1 → expand1 → div1 → store1

load2 → rowmax2 → expand2 → sub2 → exp2 → rowsum2 → expand2 → div2 → store2

load3 → rowmax3 → expand3 → sub3 → exp3 → rowsum3 → expand3 → div3 → store3

为了达到这样流水线的效果，你就得加入TSYNC.wait/TSYNC.record两种PTO指令，让这三个链条错开一些，流水起来。

总结一下，PTO指令到底为高端调优程序员提供了什么功能？

PTO 的价值从来不是“又发明了几条新指令”，更不是把 TADD、TMATMUL 这种名字换个马甲就算创新。它真正解决的，是 DSA 世界里最棘手、也最容易被低估的问题：复杂流水的组织方式。这玩意儿在GPGPU就叫做warp specialization。在CPU里面就是异步多加速器执行。达芬奇核，本质上就是一个小的MCU带着一堆加速器拼接而成。

在一颗达芬奇核里，CUBE、MTE、VEC、FIXP 各自都很能打，但它们就像一支乐团里的不同声部——铜管、弦乐、打击乐、合唱团。单独拉出来都能秀一段，但要想合起来像交响乐，就必须做到三件事：谁先上、谁后上、谁等谁、谁跟谁对齐节拍。现实中，最“折磨人”的不是算子公式本身，而是这些异步单元之间的喂数、接力、避让、同步、复用缓冲区：一次矩阵乘背后要安排多段搬运、多级变换、多次累加，还得保证输出不被覆盖、依赖不被破坏、带宽不被浪费。指挥得好，整团齐鸣；指挥得差，就是一地杂音——不是算不对，而是算得慢、算得抖、算得不稳定。

PTO 的意义，就是把这套“指挥工作”从经验主义的手工排练，升级成一套可表达、可复用、可检查的语言体系：它用 Tile 作为统一的“音符/小节”，用 TLOAD/TSTORE、TMOV、CUBE/VEC/FIXP 等操作作为标准化的“演奏指令”，再用同步语义（Auto 插同步、Manual 显式插 TSYNC / Event）把“什么时候该进、什么时候该等”写进谱面里。于是，开发者不再需要直接和硬件的微小差异肉搏，而是把核心精力放在：这段音乐应该怎么编排，哪些段落要重叠，哪些段落必须保序。

这才是 PTO 的价值：不是多几条指令，而是让PTO把 DSA封装起来， 真正进入“可规模化开发”的时代。
