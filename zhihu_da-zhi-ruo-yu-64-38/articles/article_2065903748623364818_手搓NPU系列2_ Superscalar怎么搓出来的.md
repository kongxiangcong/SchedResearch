# 手搓NPU系列2: Superscalar怎么搓出来的

- 原文：[知乎文章](https://zhuanlan.zhihu.com/p/2065903748623364818)

![image](https://pic4.zhimg.com/v2-1b133f4a9c6645fbaa8413ab8dfa73f7_1440w.jpg)

提到 NPU，很多人的第一反应都是一大片气势恢宏的乘加阵列：激活数据从左边流进去，权重从上面流下来，中间密密麻麻的 PE，也就是 Processing Element，处理单元，不停执行 MAC，也就是 Multiply-Accumulate，先乘再加，最后从阵列另一端吐出一个矩阵结果。

这个印象当然不能说错，毕竟发布会上的 NPU 大多也确实长成这样，只不过它描述的是 NPU 里面最容易画、最容易计算理论峰值，也最适合在 PPT 上涂成金色的那一部分。

真正把一个神经网络模型完整跑起来，处理器还要干很多没有那么适合登上宣传海报的工作：它要计算张量地址，搬运输入、权重和中间结果，判断循环边界，处理动态形状，完成量化和反量化，识别稀疏索引，在标量、向量、矩阵和 Tile 执行单元之间建立依赖，并且在分支预测错误、地址翻译失败、缓存没有命中或者访存需要重放时，知道哪些工作可以继续保留，哪些工作必须撤销。

矩阵阵列负责“算得快”，但谁来保证它一直有正确的数据可算，往往才是更难的问题。

很多 NPU 的实际瓶颈并不是 MAC 数量不够，而是阵列造得太大，周围的控制和存储系统却跟不上。账面上每周期可以完成成千上万次乘加，真实运行时却可能在等数据、等地址、等同步、等上一块计算释放本地存储，或者等某个看起来微不足道的标量条件判断。

结果就是，计算单元一个个造得膀大腰圆，最后大部分时间坐在原地等外卖。

Superscalar NPU，也就是超标量 NPU，试图解决的正是这个问题。它不是简单地在一颗普通 CPU 旁边挂一个被动等待命令的矩阵乘单元，而是把 CPU 中已经发展成熟的超标量乱序控制、块级任务管理，以及标量、向量、矩阵和 Tile 等专用执行引擎，放进同一个执行模型中。

标量地址计算、条件判断、Load、Store 和控制指令，可以像现代 CPU 一样，在硬件中动态寻找已经具备执行条件的工作；矩阵和 Tile 操作则继续保持粗粒度，由一条命令启动一大片规则计算，避免让每一次乘加都承担完整的取指、解码、寄存器重命名、发射和提交成本。

这套架构的关键，不是把 NPU 彻底做成 CPU，而是明确区分两类工作：

**不规则的控制和访存，需要细粒度乱序；规则的大规模计算，需要粗粒度执行。**

如果不做这层区分，设计很容易滑向两个极端：要么所有工作都由编译器提前排好，硬件确实简单，但运行时只要出现一次意外延迟，整条流水就陪着停住；要么把每一个细小操作都塞进复杂乱序窗口，灵活性确实很高，但控制功耗和面积很快就会让计算阵列感受到什么叫喧宾夺主。

Superscalar NPU 要做的，就是在这两个极端之间，找到一个工程上更合理的位置。

### 一、NPU 真正缺的，往往不是更多 MAC，而是有人把事情安排明白

传统神经网络加速器最擅长的，是形状规整、依赖明确的大规模矩阵计算。

例如矩阵乘法：

[ C=A\times B ]

每一个输出元素都是输入矩阵一行与另一个矩阵一列的点积，运算规律固定，数据访问模式相对容易预测，因此非常适合放进脉动阵列或者其他专用矩阵引擎中批量执行。

所谓脉动阵列，可以把它理解成一条组织严密的流水作业线：数据按照固定节奏在处理单元之间流动，每个处理单元只负责一小部分乘加工作。它不需要每做一次乘法都回到中央调度器请示，也不需要每一个中间结果都频繁写回大型寄存器文件，因此数据复用率高，控制开销低，单位功耗下能够完成更多计算。

问题在于，真实模型并不是由一个无限大的矩阵乘组成的。

以 Transformer 为例，除了矩阵乘，还会出现 Softmax、LayerNorm、激活函数、位置编码、KV Cache 访问、张量切分与拼接、掩码处理和格式转换。到了大语言模型推理的 Decode 阶段，每一步只生成少量 Token，矩阵规模明显缩小，访存、同步和控制开销在总时间中的占比反而会上升。

模型越走向动态形状、稀疏计算、小批量推理和复杂算子融合，处理器需要处理的“杂事”就越多。

而这些杂事虽然没有矩阵乘那么壮观，却常常决定矩阵引擎能不能及时开工。

一次 Tile 计算启动之前，地址生成单元可能要先算出输入位置，Load 单元要把数据搬进本地存储，向量单元要完成数据格式转换，标量指令要判断当前 Tile 是否位于边界，上一块计算还要释放目标 SRAM Bank。只要其中一环没有完成，矩阵阵列就只能等待。

最简单的解决办法，是让编译器在程序运行以前，把这些工作全部排好，硬件按照固定顺序执行。

这种静态调度并不是错误。对于延迟稳定、形状规则的负载，静态调度甚至可能拥有更好的面积效率和能效，因为处理器不需要建设复杂的动态调度网络。

但是，静态调度有一个很苛刻的前提：编译器要比较准确地知道每项工作需要花多少时间。

问题是，访存延迟从来不是一个听话的常数。

同一条 Load 指令，有时命中一级缓存，几拍就回来；有时遇到 Cache Miss，需要访问更远的存储层次；有时要等待地址转换；有时发现前面一条 Store 正在写相同地址，需要从 Store Queue 中转发数据。

编译器可以根据平均情况安排流水，却不可能在编译时知道某一次具体访问究竟会不会命中。

如果整个程序严格按顺序推进，一条意外变慢的 Load，就可能让后面大量与它无关的工作一起停住。

这正是乱序执行能够介入的地方。

### 二、乱序执行不是把程序顺序打乱，而是把“真依赖”和“排队”分开

乱序执行经常被概括成“让后面的指令先跑”，听起来多少像处理器开始不讲规矩了。

实际上，现代乱序处理器最在乎的恰恰是规矩。它允许内部执行顺序发生变化，但要求软件最后观察到的状态，与程序按照顺序执行完全一致。

假设程序中有三条指令：

```text
A：从内存读取数据 X
B：计算 Y + Z
C：使用 X 做加法
```

其中，A 可能需要等待内存，B 与 A 完全无关，C 则真正依赖 A 的结果。

顺序处理器会等待 A 完成，然后再执行 B 和 C；乱序处理器则会发现，B 虽然写在 A 后面，却不依赖 A，因此可以先执行。C 仍然必须等待，因为真实数据依赖并不会因为处理器很积极就自动消失。

所以，乱序执行没有消灭依赖，它只是区分了两类等待：

一种是“没有数据，确实不能做”；另一种是“数据已经齐了，只是前面有人堵着”。

Superscalar，也就是超标量，表示处理器每个周期可以同时解码、调度或者执行多条指令；乱序执行，则表示处理器可以从一批在途指令中，选择已经准备好的工作先做。

这两者结合起来，使处理器不再被单条长延迟指令轻易拖住。

对 Superscalar NPU 来说，这种能力格外重要，因为 NPU 程序中经常同时存在标量计算、地址生成、Load、Store，以及发往向量、矩阵和 Tile 引擎的大粒度命令。一条 Load 在等数据时，另一条独立的地址计算可以继续，一个不相关的向量操作也可以开始，甚至另一个块的矩阵命令也可能提前进入等待队列。

只要硬件能够准确识别依赖，并保证结果最终按程序顺序生效，就没有必要让所有工作陪着最慢的那一条指令一起发呆。

但这里马上会出现一个新的问题：CPU 处理的通常是一条条普通指令，而 NPU 中的一条矩阵命令，可能代表成千上万次内部运算。难道要把这些乘加全部塞进 CPU 式的乱序窗口吗？

当然不能。

如果每一个 MAC 都要占用一个 ROB 条目，经历寄存器重命名、发射选择和顺序提交，那么处理器花在“管理计算”上的成本，很可能比计算本身还高。矩阵引擎原本就是为了摊薄控制成本而存在，不能绕了一圈，又把每一次乘加请回中央调度大厅排队盖章。

因此，Superscalar NPU 必须同时维护两种粒度的并行。

### 三、控制平面和计算平面，不是同一回事

从整体上看，一颗 Superscalar NPU 可以分成两个平面。

控制平面由取指、分支预测、解码、寄存器重命名、发射调度、ROB 和恢复系统构成，它负责回答的是：

- 接下来应该执行哪些指令；
- 哪些操作数已经准备好；
- 哪些资源目前可用；
- 哪些工作属于错误的投机路径；
- 哪些结果已经可以正式提交。

计算与数据平面则由标量 ALU、分支单元、访存单元、向量引擎、矩阵阵列、Tile 执行单元、本地 SRAM、DMA 和片上网络构成，它们负责真正完成计算和搬运。

可以把整体流程简化为：

```text
取指与分支预测
        ↓
    指令缓冲区
        ↓
解码、资源预览与原子分配
        ↓
  重命名与发射队列
        ↓
标量 / 分支 / 访存 / 向量 / 矩阵 / Tile
        ↓
   顺序提交与恢复
```

矩阵和 Tile 引擎还会通过独立的命令队列在后台推进，并把完成状态返回给块管理结构。

这个结构最重要的地方，不是流水级有多少，而是不同世界之间的边界是否清楚。

例如，一条微操作在发射队列中等待时，发射队列是它唯一的 Owner，也就是状态所有者；只有当执行单元真正接受了这条操作以后，所有权才发生转移。

如果发射队列以为执行单元已经接管，于是提前删除条目，而执行单元实际上又没有成功接收，这条指令就会凭空消失；反过来，如果两边都认为自己仍然是 Owner，同一个结果就可能写回两次。

硬件里最麻烦的问题，往往不是没人负责，而是大家都非常负责。

因此，Superscalar NPU 大量使用 Ready/Valid 握手：

- `valid` 表示上游正在提供一笔有效事务；
- `ready` 表示下游本周期有能力接收；
- 两者同时为真，事务才真正发生，也就是 `fire`。

如果 `valid` 已经拉高，而 `ready` 为低，上游必须保持数据不变，不能一边说“还没交出去”，一边把内容悄悄换掉。

这些规则听起来像接口细节，但它们实际上决定了复杂乱序系统能否在反压、取消和恢复同时发生时仍然保持一致。

### 四、IFU：高性能处理器先要解决的，不是怎么算，而是下一批指令在哪里

IFU，也就是 Instruction Fetch Unit，取指单元，是整颗处理器的供料系统。

后端可能同时拥有多条执行通道，向量、矩阵和访存引擎也可以并行工作；如果 IFU 每隔几拍才犹犹豫豫地送来一两条指令，后面再宽的执行单元也只能端着饭碗等开饭。

Superscalar NPU 的前端没有把“取得指令字节”和“预测下一条路径”混成一条大流水，而是拆成两条可以独立推进的路径：

- I-SIDE 负责地址翻译、指令缓存访问和字节拼接；
- B-SIDE 负责分支方向和目标地址预测。

两边处理的是同一笔取指事务，但面对的延迟来源完全不同。

I-SIDE 可能在等待 ITLB、I-cache 或缓存填充；B-SIDE 则在查询 BTB、方向预测器、返回地址栈和循环预测器。如果强行让两者锁步，缓存的一次反压就会拖住预测，预测表的一条长路径也可能塞进指令字节供应流水。

将两者拆开以后，缓存和预测可以分别运行，最后再根据请求身份汇合。

这听起来只是多加了一些标签，实际上是现代前端非常关键的一项设计，因为取指响应未必按顺序返回。

一笔取指事务通常需要携带：

- STID，也就是硬件流身份；
- Fetch Sequence，也就是取指序号；
- Epoch，也就是当前投机世代；
- Prediction Tag 或恢复 Checkpoint。

PC 本身不能代替这些身份。

循环的不同迭代可能拥有完全相同的 PC，一个旧请求的缓存响应也可能在很多周期以后才回来。如果处理器只看地址，不看 Sequence 和 Epoch，就可能把上一次循环迭代的响应交给当前请求。

这和快递柜的逻辑很像：收件地址相同，不代表所有包裹都是同一件；至少还得看看订单号和取件码。

### 指令地址翻译和 I-cache 为什么要并行访问

程序使用的是虚拟地址，真正访问缓存需要物理地址。

ITLB，也就是 Instruction Translation Lookaside Buffer，指令地址转换旁路缓冲区，负责把虚拟地址快速翻译成物理地址，并检查这个页面是否允许执行。

L1 I-cache 是最靠近流水线的一级指令缓存。

为了缩短取指延迟，处理器通常不会等 ITLB 完成翻译以后，再开始访问 I-cache，而是先使用虚拟地址的一部分索引读取候选缓存行，同时查询 ITLB，随后再用物理标签和权限完成最终确认。

这样可以把地址翻译和 SRAM 读取重叠起来。

代价是，“缓存看起来命中”不等于“这次取指合法”。如果 ITLB 最终发现页面不存在、权限不足，或者这笔请求已经属于旧 Epoch，那么候选缓存行即使真的包含相同字节，也不能被使用。

### 为什么前端恢复和后端恢复不能混为一谈

如果 ITLB Miss，前端通常只需要取消当前取指事务以及更年轻的前端请求，保留已经开始的 Page Walk，等地址转换完成以后，从原始 PC 重新取指。

这种 Frontend Inner Flush，不应该清空 ROB，也不应该回滚寄存器重命名，更不应该碰后端 LSU 中已经属于架构执行的状态。

而如果分支执行单元在真实操作数到达以后，发现此前预测路径错误，则需要执行后端精确恢复：ROB、BROB、Rename、IQ、LSU 和专用引擎命令都要根据统一的年龄关系选择性取消。

两者最后都表现为“重新设置 PC”，但代价完全不同。

如果把它们都叫 Flush，再接到一根“大家全部清空”的控制线上，一个普通 TLB Miss 就可能被处理成全核大扫除；机器当然很干净，性能也顺便被扫没了。

### 五、为什么分支预测也要拆成“先快后准”

B-SIDE 负责预测下一条控制流路径，它至少要回答两个问题：

当前分支会不会跳，以及如果跳转，目标地址在哪里。

不同预测结构擅长的事情不同：

BTB，也就是 Branch Target Buffer，分支目标缓冲区，负责记忆以前出现过的跳转目标；简单方向计数器学习一个分支更倾向跳还是不跳；TAGE 使用多组不同历史长度的表，捕捉更长距离的控制相关性；RAS，也就是 Return Address Stack，返回地址栈，专门预测函数返回；Loop Predictor 则擅长学习循环迭代次数。

更大的预测结构通常更准确，但访问也更慢。因此，B-SIDE 不会等所有预测器都查完以后才给答案，而是让小而快的结构先提供一条候选路径，后面的复杂预测器再不断纠正。

这有点像导航系统：先根据当前道路迅速给一个能走的方向，随后更完整的路况和路线计算回来以后，再判断是否需要改道。

后级预测器发现更好的结果时，需要比较：

```text
{是否跳转，分支地址，目标地址，控制流类型}
```

如果这个组合发生变化，就产生 Prediction Correction，撤销错误的前端请求，并从新目标继续取指。

这里最关键的设计并不是预测表有多少，而是每一级预测结果都必须带着精确身份，并且只能修改属于自己的那一笔请求。

预测历史同样不能随意更新。全局分支历史和返回地址栈需要在预测开始时保存 Checkpoint，发生修正以后回滚到对应快照，再追加真实方向。

否则多个预测级都觉得自己掌握了最新答案，每一级都热情地更新一次历史，最后预测器会非常努力地学习一段从未发生过的程序。

### 六、Instruction Buffer：把前端的“字节世界”和后端的“指令世界”隔开

I-cache 返回的是 Cache Line，也就是一整行字节，但后端需要的是一条条已经切分好的完整指令。

如果指令支持多种长度，一条指令还可能从一条 Cache Line 的末尾开始，在下一条 Cache Line 中结束。前端必须保留上一行的尾部，再借下一行的前缀完成拼接。

完成长度识别和跨行拼接以后，前端再把不同长度的原始编码，规范化成统一的内部格式，并预先识别 `BSTART` 和 `BSTOP` 等块边界。

完整 Opcode、操作数、立即数和执行单元类型仍然留到后面的解码阶段处理，避免前端的关键路径被一张巨大的解码表拖住。

Instruction Buffer，也就是指令缓冲区，位于前端和后端之间，它不是某个流水级顺手多存了几条指令，而是一座真正的隔离水库。

前端可以按 Cache Line 粒度并发取指，响应甚至可能乱序返回；Instruction Buffer 则只向后端暴露同一 STID 中连续、有效、顺序正确的指令前缀。

每个条目除了保存指令本身，还要保存 PC、指令长度、块边界、Fetch Sequence、Epoch、异常信息和完整预测记录。

这些元数据必须和指令条目绑定，而不能等到解码时，再去某个“当前预测寄存器”里临时取一份，因为到了那个时候，所谓“当前预测”很可能已经属于下一笔取指请求。

Instruction Buffer 增加了存储开销，却把变量长度、跨行拼接、Cache Line 返回顺序和后端解码彻底隔开。后端从这里开始，面对的终于不再是一堆需要猜边界的字节，而是整齐的指令。

---

### 七、指令进入乱序后端以前，不能一边分资源，一边临时反悔

指令经过解码以后，需要同时获得很多资源：

- ROB 条目；
- 物理寄存器标签；
- 发射队列位置；
- Load Queue 或 Store Queue 身份；
- 块身份 BID；
- 必要的恢复 Checkpoint。

宽超标量处理器真正困难的地方，并不是每一种资源单独怎么分，而是这些资源必须对同一组指令保持一致。

假设一组四条指令同时进入后端，ROB 认为四条都可以接收，寄存器重命名认为三条可以接收，Store Queue 却只能接受两条。如果各个模块分别根据自己的 `ready` 修改状态，后端很快就会出现 ROB 空洞、物理寄存器泄漏、半条 Store，或者多个模块对这组指令到底进入了多少条产生不同理解。

因此，Superscalar NPU 将这个过程拆成三个逻辑步骤。

D1 负责真正理解指令：识别 Opcode、输入输出、立即数、非法编码、块边界，并在必要时把一条架构指令拆成多个 Uop，也就是微操作。

D1 不修改后端状态，它只计算这组指令需要哪些资源。

D2 根据当前资源快照，形成一份 Reservation Plan，也就是预留计划。它预览 ROB 身份、BID、物理寄存器、IQ Credit 和内存顺序身份，但不真正推进任何队列指针。

D3 才是原子承诺点。它从最老指令开始，选择所有资源都能够同时满足的最大连续前缀，并在同一次 `fire` 中完成所有资源分配。

剩余指令保持不变，等待下一次尝试。

这种设计会增加 Credit 聚合和资源预览逻辑，但它消灭了更危险的复杂度：不能出现 ROB 已经分到了，物理寄存器也拿到了，最后才发现 Store Queue 没位置，于是准备下个周期再补手续。

硬件里的半笔交易，比停一个周期危险得多。

---

### 八、寄存器重命名：处理器不是寄存器不够，而是不想被名字骗了

乱序执行要成立，硬件还必须消除寄存器假依赖。

假设两条互不相关的指令先后写同一个架构寄存器，会形成 WAW，也就是 Write After Write，写后写冲突；年轻指令准备覆盖寄存器，而老指令还没有读取旧值，则会形成 WAR，也就是 Write After Read，写后读冲突。

这些冲突并不代表两条计算在数学上真的存在依赖，只是因为它们碰巧使用了同一个寄存器名字。

寄存器重命名的办法，是让不同时间产生的值使用不同物理寄存器。

例如：

```text
第一条写 R1 → 物理寄存器 P17
第二条写 R1 → 物理寄存器 P42
```

这样，两条指令虽然在软件看来都写 R1，硬件内部却不会互相覆盖。

真正的 RAW，也就是 Read After Write，读后写数据依赖，仍然通过共同的物理标签保留下来。

Superscalar NPU 中，标量 P 寄存器和块内 T/U 寄存器的生命周期并不相同。

P 寄存器表示跨块持久存在的标量架构状态，需要传统的全局映射表、空闲物理寄存器表和提交恢复机制。

T/U 则更接近 Tile 或块内临时值，它们往往只在某个块内部有效。块结束以后，这些值可以局部回收，没有必要一直占用全局物理寄存器。

因此，P 与 T/U 采用分域重命名。

P 值通过物理 PTag 在调度网络中广播；T/U 值则可以使用点对点 QTag，直接唤醒特定发射队列条目，避免在整个调度网络里进行昂贵的全局比较。

这样做增加了重命名结构的种类，但每套结构只管理真正属于自己的生命周期。

如果强行把所有寄存器塞进同一套全局映射表，设计表面上更统一，块结束时的局部回收、恢复和唤醒网络却会变得更加笨重。

这是一类很典型的架构交换：结构数量更多，但每个结构承担的责任更明确。

---

### 九、发射队列：被选中不等于已经执行

完成重命名的微操作会进入 IQ，也就是 Issue Queue，发射队列或调度队列。

每个 IQ 条目需要保存源操作数标签、目标标签、执行类型、ROB 和 BID 身份、Ready 状态，以及取消和恢复信息。

一条指令只有满足三个条件，才真正具备执行资格：

输入数据已经准备好，目标执行单元有能力接收，并且没有违反内存顺序或恢复约束。

物理 IQ 可以按照执行类型拆分，例如整数、分支、地址生成、Store 数据、系统指令和 NPU 命令分别使用不同 Bank。

拆分能够减少每个调度器需要比较的条目数量，降低 CAM 和选择网络的延迟；共享则能更好地吸收流量波动，避免一个队列堵成早高峰，旁边的队列却还在享受独栋办公区。

Superscalar NPU 使用 Resident + Inflight 的管理方式。

一条指令在 IQ 中等待时是 Resident，也就是正式居民；调度器选中它以后，只是设置 `inflight`，表示已经开始尝试发射，但所有权仍然留在 IQ。

随后，处理器还要争取寄存器文件读端口，检查旁路数据是否有效，并确认目标执行单元的入口槽位确实能够接收。

只有这些条件全部满足以后，所有权才从 IQ 转移到执行流水。

如果读端口仲裁失败，或者执行单元突然反压，只需要清除 `inflight`，让条目原地等待下一次选择，而不是先把指令从 IQ 移走，再想办法重新插回去。

这套方法尤其适合 Load 的投机消费者。

依赖 Load 的指令可以提前被选中，但在 Load 最终确认命中以前，IQ 仍然保留原始条目。如果 Load Miss，流水线中的投机副本被 Poison，也就是禁止产生副作用，IQ 中的原条目则清除 `inflight`，以后重新发射。

它不需要重新走一遍解码、重命名和 Dispatch，也不会丢失原有年龄。

代价是 IQ 条目驻留时间更长，取消和释放必须使用完整身份，而不能只看一个可能已经被复用的 Slot Number。

---

### 十、ROB 和 BROB：一套管指令顺序，一套管块生命周期

ROB，也就是 Reorder Buffer，重排序缓冲区，可以被理解为一本按照程序顺序登记的在途指令账本。

指令按顺序进入 ROB，执行单元可以乱序把它们标记为完成，但提交端只能从 ROB Head 开始，提交连续完成并且没有异常的前缀。

这套机制保证，硬件内部即使乱序执行，软件看到的结果仍然保持顺序。

它同时支持精确异常：一旦某条指令出错，处理器可以保留它之前的结果，取消该指令和所有更年轻的投机状态。

但是，普通 ROB 不适合直接管理矩阵引擎内部的每一个动作。

一条 Tile 命令可能持续几百甚至几千周期，如果对应 ROB 条目一直等到整个引擎任务结束才释放，有限的 ROB 很快就会被长延迟任务堵住。

反过来，如果命令一发出去就立即认为完成，那么发生预测错误或者异常时，处理器又说不清楚已经发给异构引擎的工作到底属于哪条路径。

BROB，也就是 Block Reorder Buffer，块重排序缓冲区，解决的正是这个问题。

普通 ROB 管理的是指令顺序，BROB 管理的是动态块生命周期。

一个块可以包含标量地址计算、数据搬运、向量操作，以及发往矩阵或 Tile 引擎的命令。标量部分结束，并不一定代表块完成；如果该块启动了异构引擎，还需要等待相应 Engine Completion。

块完成条件可以表示为：

```text
block_complete =
    scalar_done &&
    (needs_engine ? engine_done : true)
```

每个块由 `(STID, BID)` 共同识别。

BID 只是编号，本身不能直接用于判断年龄，因为 BROB 往往是环形结构，编号回绕以后，较大的 BID 不一定更年轻。真正的年龄还要结合 Head、Tail、Wrap 和 Generation。

因此，恢复时不能简单写成：

```text
bid > flush_bid
```

然后把所有数值较大的块删除。

正确做法是由 BROB 根据当前活动区间生成精确的年轻块集合，再让 ROB、Rename、IQ、LSU 和专用引擎共同消费同一份 Kill Set。

ROB 和 BROB 不是两套重复的提交系统，而是在不同粒度上维护同一个执行世界：

ROB 管“小账”，记录每条普通指令有没有完成；BROB 管“项目账”，记录整个动态块以及它启动的异构工作有没有真正结束。

### 十一、Load 投机：先假设会命中，但必须准备好把消费者叫回来

访存是乱序执行中最难处理的部分，因为 Load 的延迟在发射时通常无法确定。

一条 Load 可能命中 L1 Cache，也可能发生 TLB Miss、Cache Miss、等待 Store 转发、遭遇内存顺序冲突，或者需要 Replay。

最保守的做法，是等 Load 数据确定返回以后，再唤醒依赖它的消费者。

这种设计很安全，但 Load-Use 延迟较长，即使 Load 实际命中一级缓存，消费者也要等到结果正式返回以后才开始调度。

更激进的设计会先假设 Load 命中，并提前唤醒消费者。

在一条具体的执行路径中，可以表现为：

- Load 刚发出时先产生 Speculative Wakeup；
- Cache 数据返回时通过 Bypass 直接送给消费者；
- 再晚一拍确认这次访问究竟是 Hit、Miss、Fault 还是 Replay。

也就是说，消费者可以先走到等待数据的位置，数据一回来就直接使用，不必等结果先写回寄存器文件、下一拍再重新读取。

如果 Load 果然命中，依赖链会明显缩短。

如果 Load 没有命中，处理器则必须取消投机唤醒，把已经提前进入流水的消费者标记为无效，并让 IQ 中仍然保留的原始条目以后重新发射。

这项机制最关键的并不是敢不敢猜，而是猜错以后能不能准确撤回。

同一个 Load Tracking Slot 会被循环复用，因此每次访问都需要分配一个 Load Generation，也就是世代号。数据返回、取消和重放不仅要匹配 Slot，还要匹配 Producer Identity 和 Generation。

例如：

```text
{STID, producer_key, load_generation}
```

只有这几个字段全部匹配，返回数据才真正属于当前这次访问。

否则，上一次 Cache Miss 的迟到响应，可能碰巧遇到同一个 Slot 中的新 Load，并把旧数据热情地交给新指令。处理器表面上继续运行，错误则会在几十万条指令以后，以一种让整个团队开始检查宇宙射线的方式出现。

Load 投机不是免费的性能。

如果缓存命中率高，Load-Use 依赖密集，提前唤醒非常有价值；如果 Miss 频繁，消费者数量又多，反复 Poison 和 Repick 会吞噬发射带宽，并占用更多 IQ 条目。

因此，这项机制是否划算，取决于缓存命中率、内存依赖预测、Store Forwarding 能力和 Replay 网络容量，而不是因为规格里写了“支持 Speculative Wakeup”，性能就会自动从纸面上长出来。

---

### 十二、IEX：不同执行单元可以各自推进，但完成只能有一个定义

IEX，也就是 Instruction Execution，执行系统，真正负责把微操作变成结果。

其中：

- ALU 处理整数算术和逻辑；
- BRU 处理分支和控制流校验；
- AGU 生成访存地址；
- STD 准备 Store 数据；
- FSU 或 System Pipeline 处理浮点、长延迟算术和系统操作；
- Vector、Matrix 和 Tile 引擎接收粗粒度 NPU 命令。

这些执行单元的延迟和吞吐完全不同，因此不能把它们画成一条所有指令依次经过的大流水。

为了描述不同延迟，执行系统可以同时使用两套时间坐标。

E1、E2、E3 表示指令离开发射阶段以后，经过了多少个绝对执行周期；W1、W2、W3 则表示真实数据结果处于第几个 Producer-Relative Age，也就是相对于结果生产者的数据年龄。

一条短延迟 ALU 指令可能在 E1/W1 就产生结果；一条长延迟乘法的 W1 可能出现在更晚的 E Stage；Load 的 W1 则要等到 Cache 数据真正返回。

分支可以很早确定方向，但如果它不产生寄存器数据，就没有必要为了图画得对称，硬给它造一个不存在的 W Stage。

E 坐标让恢复系统知道一条操作在流水中走了多远，W 坐标则让依赖调度器知道真实数据什么时候出现。两者分开以后，不同执行单元不需要被一个含糊的“固定延迟”强行套住。

### AGU 和 STD 为什么要分开

Store 同时需要地址和数据。

地址可能很早准备好，Store 数据却来自另一条长延迟指令；也可能数据已经准备好，地址还在等待寄存器。

因此，一条逻辑 Store 在后端可以拆成 AGU Child 和 STD Child，分别处理地址和数据，但两者共享同一个 ROB 身份、BID 和内存顺序身份，最后在 Store Queue 中汇合。

这样，地址生成和数据准备可以分别调度，不必互相等待。

但从架构上看，它们仍然是一条 Store，不能因为拆成两个物理 Child，就产生两份独立副作用。

这正是微操作拆分中必须保留 Parent Identity 的原因。

### 分支发现错误以后，为什么不能立即随意修改 PC

BRU 可以很早发现预测错误，但早期发现错误和正式改变架构执行方向，并不是同一件事。

错误信息可以先形成 Correction Metadata，帮助处理器尽快停止继续沿错误路径扩张；真正的架构级 Redirect，则需要和 ROB、BROB、块边界以及精确恢复状态统一以后，再向前端发布。

这种做法看起来比“分支一错立刻跳转”复杂，却避免了执行单元越过提交系统，提前修改整个机器的架构方向。

尤其在 Superscalar NPU 中，一个错误路径可能已经启动了矩阵、向量和 DMA 工作，恢复不能只改 PC，还要知道哪些块命令仍在队列，哪些已经被引擎接受，哪些已经产生内部结果。

---

### 十三、完成不是一根 Valid 信号，而是一笔原子事务

一条指令产生结果时，往往需要同时更新多个地方：

- 写入物理寄存器；
- 唤醒依赖它的消费者；
- 标记 ROB 条目完成；
- 更新块状态；
- 记录 Trace；
- 产生异常或者恢复信息。

如果这些副作用可以分开进行，就可能出现非常危险的中间状态。

例如，ROB 已经被标记为 Completed，但寄存器写端口因为反压没有接受结果。提交系统可能认为指令已经完成，消费者却仍然读不到数据。

因此，执行结果需要被归一成 Terminal Transaction，也就是终端事务。

只有所有 Mandatory Sink 都能够接收时，这笔事务才真正 `terminalFire`。如果其中任何一个端口反压，Producer 必须保留完整结果，其他模块也不能提前修改状态。

这条规则增加了 Ready 汇聚和结果缓存，却让“完成”重新拥有一个唯一、可证明的定义。

对于系统指令、原子操作、MMIO 和外部内存写入，规则更加严格：可以提前计算地址，可以提前检查条件，但在获得 Precise Permit 以前，不能真正改变外部世界。

因为普通寄存器写错了还可以通过 Flush 撤回，已经发送到外设的一次操作，通常不会因为处理器说“刚才那条路径其实是我猜的”，就很配合地假装什么都没有发生。

---

### 十四、NPU 引擎：命令发出去，不等于工作已经完成

向量、矩阵和 Tile 引擎通常通过块命令队列接收工作。

命令队列负责吸收引擎反压，BROB 负责块生命周期，具体引擎负责内部数据流和局部完成，这三个角色不能互相替代。

命令进入队列，只说明控制核已经把任务放进等待区；引擎接受命令，说明工作正式开始；引擎返回 Completion，才说明本地计算结束。

恢复系统必须区分命令处在哪个阶段：

1. 仍在队列中；
2. 已被引擎接受；
3. 已经产生内部结果；
4. 已经产生不可逆外部副作用。

越靠后的状态越难取消。

因此，每一条块命令至少需要携带 STID、BID、目标引擎、操作类型、数据位置和完成回报路径。

命令队列用这些身份管理等待任务，引擎使用同样的身份返回 Completion，BROB 根据 BID 更新块状态，恢复系统则根据统一的 Kill Set 判断哪些工作应该保留。

只要其中一个模块决定根据自己的理解重新计算块年龄，系统就会出现多个版本的“年轻任务名单”。

现实管理里，多份名单最多意味着多开几次会；在芯片里，多份名单意味着某些任务被取消两次，某些任务一次也没有取消。

---

### 十五、真正决定 NPU 效率的，仍然是数据复用

专用 NPU 引擎能够高效运行，核心原因并不是乘法器有多神奇，而是数据能够在片上被重复使用。

如果权重、激活和部分和每做一次乘加都要访问外部内存，带宽和能耗会迅速失控。对于现代芯片，从远处搬运一个数据所消耗的能量，往往远高于完成一次简单算术。

因此，矩阵和 Tile 引擎通常配套本地 SRAM 或 Scratchpad。

Scratchpad 可以理解为显式管理的片上暂存区。与 Cache 主要依赖硬件自动替换不同，Scratchpad 中的数据位置和生命周期，通常由编译器、DMA 或本地控制器明确安排。

数据通过 DMA，也就是 Direct Memory Access，直接内存访问引擎，批量搬入本地存储，再通过 NoC，也就是 Network on Chip，片上网络，送往不同计算阵列。

不同 Dataflow 会选择让不同数据尽量驻留，例如：

- Weight-Stationary，让权重驻留；
- Output-Stationary，让部分和驻留；
- Input-Stationary，让输入驻留。

哪一种更合适，取决于算子形状、本地存储容量、阵列规模和片上带宽。

Superscalar NPU 的乱序控制不能替代这些机制。

乱序解决的是任务之间如何重叠、动态延迟如何隐藏、依赖如何管理；真正决定阵列能否被喂饱的，仍然是数据布局、本地存储、DMA、NoC 和编译器调度。

如果数据复用不好，乱序后端只会更加积极地发现“大家都在等内存”；如果 Scratchpad 容量不足，再聪明的调度器也不能把不存在的数据变出来。

因此，Superscalar NPU 的性能来自多个层次共同作用：

编译器暴露块和依赖，指令集表达控制语义，乱序后端动态寻找可执行工作，Scratchpad 和 DMA 提供数据，向量与矩阵阵列完成高密度计算。

其中任何一层明显掉队，其他部分都很难单独补救。

### 十六、这套设计真正获得了什么，又把复杂度搬到了哪里

Superscalar NPU 的价值并不在于流水级名字更多，而在于几个边界被划分得足够明确。

| 设计选择 | 获得的收益 | 付出的代价 |
| --- | --- | --- |
| 取指和预测双流水 | Cache、TLB 与预测器可以独立反压，早期预测降低空泡 | 需要维护 Sequence、Epoch、Checkpoint 和精确响应匹配 |
| Instruction Buffer 隔离前后端 | 变长指令和跨行拼接止于前端，后端只处理固定宽度指令 | 每个条目需要保存较多预测与恢复元数据 |
| 资源预览与原子分配 | 避免 ROB 空洞、半条 Store 和物理标签泄漏 | Credit 聚合与原子承诺成为复杂控制路径 |
| P 与 T/U 分域重命名 | 持久标量值和块内临时值按真实生命周期管理 | 需要多套映射、释放和恢复机制 |
| ROB 与 BROB 两层顺序 | 普通指令精确提交，长延迟异构工作按块管理 | 恢复必须统一解析块年龄和 Kill Set |
| Resident IQ 与 Inflight | Load Replay 不必重新解码和重命名，指令年龄不丢失 | IQ 条目驻留更久，释放和取消必须带精确身份 |
| Load 投机唤醒 | 缩短 Cache Hit 情况下的 Load-Use 延迟 | Miss 时需要 Generation、Poison 和 Repick |
| 终端原子发布 | ROB、寄存器、Wakeup 和 Trace 对完成状态保持一致 | 多个结果端口之间会产生反压耦合 |

这套微架构真正的主线，并不是“追求所有东西都并行”，而是：

**投机可以足够激进，但所有权转移必须足够保守。**

前端可以不断修正预测，Load 可以在数据回来以前提前唤醒消费者，执行单元可以乱序完成；但只要涉及资源分配、IQ 释放、ROB 完成、块恢复和外部副作用，硬件就必须使用精确身份、保留式握手和唯一 Owner。

这种设计不会让控制逻辑变少，却能让复杂度沿模块边界被验证，而不是散落在顶层若干彼此猜测的组合选择中。

### 十七、Superscalar NPU 到底适合什么工作负载

Superscalar NPU 并不是“功能更多，所以一定更先进”，也不是所有 NPU 都必须采用的唯一道路。

它是否值得，取决于工作负载是否真正拥有可以被动态调度利用的并行性。

如果任务几乎完全由大规模、规则、静态矩阵运算组成，编译器可以稳定安排数据搬运和计算，那么更简单的命令处理器可能拥有更好的面积效率和能效。

如果程序包含大量动态控制、小批量计算、不规则访存、多种执行引擎协同，以及难以静态预测的缓存和同步延迟，超标量乱序控制就更有价值。

这套架构还依赖几个前提：

程序中必须存在足够的独立标量工作，块命令必须能够覆盖足够大的计算量，编译器要正确形成块并暴露依赖，本地存储和片上网络要喂得饱计算阵列，而 ROB、IQ、寄存器文件和旁路网络带来的收益，也必须覆盖它们消耗的面积、功耗与时序成本。

Tile 粒度尤其关键。

Tile 太小，一次 Load、Compute、Reduce 和 Store 会被切成大量细碎命令，为了覆盖同样多的数据，处理器需要更大的 ROB、IQ、寄存器文件和取指带宽。

Tile 变大以后，一条命令可以覆盖更多计算，同样数量的 ROB 条目能够支撑更多数据在途，控制开销被摊薄；但 Tile 太大，又会增加本地存储压力，降低细粒度并行，并让边界和尾部处理更加困难。

因此，Tile 大小不只是计算阵列参数，它同时决定了控制粒度、乱序窗口覆盖范围、数据复用效率和 Scratchpad 需求。

Superscalar NPU 更适合的，是那些“像程序一样复杂的 AI 工作负载”，而不只是“像公式一样规整的矩阵乘法”。

### 结语

一颗 NPU 为什么还要像 CPU 一样乱序执行？

因为真实的 AI 程序并不只有整齐的矩阵乘法，它还包含地址、分支、访存、同步、动态形状，以及不同执行引擎之间的大量协作；当这些工作开始决定整体性能时，只扩大矩阵阵列已经不够，控制平面也必须升级。

Superscalar NPU 的思路，并不是让每一次乘加都进入复杂乱序流水，而是把控制和计算分层：普通指令在乱序后端中寻找细粒度并行，向量、矩阵和 Tile 引擎以块为单位展开大规模计算，ROB 维护指令顺序，BROB 维护块生命周期，最后所有投机都回到同一套精确提交和恢复规则。

IFU 解决的是怎样尽早找到正确的指令，所以它把字节供应和控制流预测拆开；乱序后端解决的是哪些指令现在真的可以执行，所以它用寄存器重命名、发射队列和原子资源分配，把模糊的等待变成硬件能够观察的状态；执行系统解决的是不同类型的工作怎样产生一致结果，所以它允许 ALU、LSU 和 NPU 引擎分别推进，再通过终端事务和统一恢复链完成收口。

这套设计减少的，是局部访存、控制和资源冲突带来的无谓等待；它增加的，则是取指、重命名、调度、事务身份和恢复系统的复杂度。

因此，它从来不是一项免费的升级。

矩阵阵列决定一颗 NPU 的理论峰值有多高，存储系统决定多少峰值能够被真正喂出来，编译器决定并行性有没有被暴露，而乱序控制决定，当现实没有严格按照编译器的计划运行时，处理器能不能临场调整，把当前真正能做的事情先做掉。

说到底，堆出一大片乘加阵列并不是最难的，难的是让它们一直有活干，干的还是正确的活；更难的是偶尔走错路以后，处理器不仅能停下来，还能准确记得自己究竟是从哪一步开始错的。
