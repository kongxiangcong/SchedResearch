# 改弦更张之二: 基于Tile寄存器的CPU

- 类型：文章
- 原文：[知乎文章](https://zhuanlan.zhihu.com/p/2040513796893103375)

如果从零开始，重新设计一颗面向 AI 的处理器，它一定还会长得像 GPU 吗？

我的答案是：未必。

它更可能是一种新的 CPU，一种基于 **Tile 寄存器** 的乱序 CPU。

![image](https://pic3.zhimg.com/v2-baada3031582543d1b09482dc85baf80_1440w.jpg)

只是这颗 CPU 的“寄存器”不再是 64 bit，也不再是 128 bit、512 bit 的向量寄存器，而是一整块 Tile；它的重命名，不再只是标量寄存器重命名，而是 Tile 重命名；它的 Issue Queue，不再只发射一条加法、一条乘法、一条 load，而是发射一个向量块、一个矩阵块、一个搬运块；它的 ALU 不再只是加减乘除，而是 矩阵乘单元，DMA和Tile ALU；它的 LSU，也不再只是从 cache 里抠几个字节，而是能理解二维块、分型布局、bank 交织和矩阵搬运的 Tile LSU。

![image](https://pic2.zhimg.com/v2-be1f7c7f34e18c615efebf21f826d00f_1440w.jpg)

你说它还是 CPU 吗？

当然是。只是它的每个器官，都长大了一圈。过去 CPU 是“小刀割肉”，一条指令做一点事；Tile CPU 是“开山劈岭”，一条指令搬一块山、一刀切一片云。形态还是 CPU 的形态：有取指、有解码、有重命名、有乱序窗口、有精确异常、有页表、有状态恢复；但粒度已经不是传统 CPU 的粒度，而是 AI 时代真正需要的计算粒度。

冯思远曾经说过一句很有意思的话：Tile 编程不是某一个人发明的，它是 AI 计算发展到一定阶段之后自然涌现出来的编程范式。

这话很对。

Tiling 这个词并不新。早年的 polyhedral 编译、stencil 计算、循环优化，都在讲 tiling。ResNet 时代，卷积成为主菜，大家也讲 tiling，但那时候的 tiling 更多还是编译器和缓存之间的小算盘：怎么把循环切小一点，怎么把 cache 命中率做高一点，怎么少搬一点数据。

到了大模型时代，Tile 不再只是优化技巧，而开始变成一种架构语义。因为模型的主战场已经变了：矩阵乘、Attention、MoE、稀疏路由、量化、反量化、归约、重排、转置、融合，一切都围绕“块”发生。软件已经在用 Tile 思考，硬件却还在用标量指令、warp、barrier、DMA、flag 去拼。这就像大家已经在修高铁站了，你还拿马车驿站的制度管理客流，当然天天堵。

所以真正的问题不是“要不要 Tile”，而是：

## **矩阵乘涌现出来的Tile 应不应该成为硬件的一等公民？**

我的答案是：应该。而且，应该把它放进 CPU 的体系里。

CPU 是人类掌握过的最复杂、也最会“吃复杂度”的电路之一。投机执行、分支预测、乱序调度、寄存器重命名、Load/Store 消歧、页表、精确异常、状态回滚、RAS、容错，这些东西不是一夜之间长出来的，而是五十多年体系结构演进一点点啃出来的硬骨头。

早期的 superscalar CPU，并没有今天意义上的完整 Reorder Buffer （ROB）。后来大家发现，没有 ROB，就很难做精确异常；没有精确异常，操作系统、调试器、虚拟内存、容错恢复都会变成灾难。于是 ROB 出现了。早期处理器对 Load/Store 的投机也远没有今天这么大胆，后来各种 Memory Disambiguation、Load Queue、Store Queue、Replay、Violation Detection 慢慢成熟，CPU 才能在“看起来不能乱”的内存世界里大胆乱序。

CPU 的伟大，不在于它每一拍能做多少乘法，而在于它能把一堆本来应该由程序员操心的事情，吞进硬件里，变成一种稳定的抽象。程序员写的是同一份二进制，微架构升级之后，性能自然变好。这个世界上最贵的软件生态，就是这么养出来的。

说白了，CPU 做了一件很奢侈的事：它用硬件复杂度，换软件自由度。

传统 CPU 的问题在于，它的指令太小了。

ROB 再怎么做，也不可能无限大。256 entry、512 entry 已经很豪华，想做到 1K entry，频率、功耗、面积、唤醒选择复杂度都会一起来敲门。Tomasulo 这套东西本质上很贵，Issue Queue 的 wakeup-select、依赖矩阵、旁路网络、物理寄存器文件端口，哪个都不是省油的灯。硬件界没有免费的午餐，最多是有人替你买单。

但 AI 给了 CPU 一条新路：**不一定要把 ROB 做得更大，可以把指令做得更大**。

这就是**块指令**的意义。

如果一条指令不再是一条 add，而是一个 Tile 上的 TADD；不再是一条 load，而是一个二维块的 TLOAD；不再是一条 FMA，而是一个矩阵 Tile 的 MMA；那么一个 256-entry 的 ROB，看到的仍然是 256 条指令，但实际覆盖的计算量已经完全不是一个量级。

假设我们有 64 个 Tile 寄存器，T0 到 T63，每个 Tile 寄存器最小粒度 4KB。那一条：

`TADD T2, T1, T0`

就不是“加两个数”，而是对两个 Tile 做一整块向量计算。它在 ISA 上是一条指令，在硬件上是一段规整的数据流，在软件上是一个可调度、可重命名、可依赖分析的块操作。

这时，一个 256-entry ROB 的含义变了。它不再是 256 条小指令的窗口，而是 256 个 Tile 操作的窗口。窗口的逻辑深度没变，但计算覆盖面积暴涨。过去 CPU 的乱序窗口像一张办公桌，现在它还是一张办公桌，只是桌上每份文件都变成了一箱档案。

这就是 Tile CPU 的核心直觉：**不盲目扩大乱序机器，而是扩大乱序机器所管理的基本对象。**

这件事对 AI 处理器尤其重要。今天昇腾、GPU、TPU 各有各的问题。

![image](https://pic2.zhimg.com/v2-decfe095cc29c02f77b9abfcbf5f8905_1440w.jpg)

昇腾的问题之一，是 CUBE 和 VEC 的执行粒度差异太大，矩阵和向量像两套系统，各写各的算子，各管各的 buffer，各等各的 flag。矩阵一边是 CUBE，向量一边是 VEC，中间靠 UB、L1、DMA、set/wait、ping-pong buffer 勉强粘起来。写算子的人像调度春运，既要看车次，又要看站台，还要担心乘客下没下车、门关没关、信号灯有没有插错。一个 flag 插错，程序不是慢一点，而是直接死给你看。

GPU 为了维护 CUDA 生态，把很多矩阵计算包装在 warp 和 thread 的语义里。几个 warp 凑在一起，128 个线程合力干一个矩阵活。这样当然能跑，也能跑得很快，但问题是控制复杂度并没有消失，只是换了个名字：warp specialization、mbarrier、shared memory staging、producer-consumer warp、async copy、shuffle、predicate、reconvergence。听起来很高级，本质上就是让一个 SM 人格分裂：一部分人搬砖，一部分人和泥，一部分人砌墙，一部分人盯进度，还要靠 mbarrier 开晨会。

## Tile CPU 的思路是：统一Tumasulo调度粒度。

CUBE 和 VEC 应该共享同一套 Tile 寄存器。矩阵计算产生的结果，不应该先绕到某个 buffer，再由向量单元费劲搬出来；向量计算处理后的结果，也不应该再倒腾半天才能喂给矩阵单元。它们应该像传统 CPU 里的整数单元和浮点单元一样，共用一套架构状态，或者至少共享一套统一管理的物理寄存器资源。CUBE 是一条 Tile 指令，VEC 也是一条 Tile 指令，搬运是 Tile 指令，转置是 Tile 指令，量化也是 Tile 指令。区别只是执行单元不同，而不是编程世界分裂。

![image](https://pic4.zhimg.com/v2-d15abe860bb0d9647808657a2f732bd7_1440w.jpg)

这样调度器看到的世界就干净了。

ROB 里有标量块，有向量块，有矩阵块，有 Tile Load，有 Tile Store。重命名负责消除假依赖，Issue Queue 负责等待真依赖，执行单元按资源和 ready 状态发射。谁先 ready 谁先走，谁有依赖谁等着。过去程序员手写 set/wait 的地方，现在交给硬件；过去编译器艰难插 flag 的地方，现在变成乱序调度的老本行；过去 ping-pong buffer 要小心翼翼排班，现在变成 Tile 寄存器分配、循环展开和 code motion 的问题。

这就是 CPU 方法论的魅力：把“人肉流水线”变成“硬件可以管理的乱序调度”。

当然，块指令不一定全是 Tile。标量控制也可以被封装成粗粒度块。比如一段循环控制、一段地址生成、一段 mask 计算，也可以作为块级调度对象。真正的关键不在于所有东西都变成矩阵，而在于所有东西都进入同一个可管理的调度体系。AI 处理器最怕的不是有多种执行单元，而是每个执行单元都自带一套祖传状态机，彼此之间靠暗号通信。

## 那 Tile Size 应该多大？

这不是拍脑袋的问题。

Tile 太小，硬件管理开销摊不薄，还是像传统向量机一样吃端口、吃 issue、吃调度。Tile 太大，寄存器文件、读写口、bank conflict、跨单元搬运、异常处理又会变成噩梦。一个合理的方向，是把最小 Tile 粒度设在几 KB 量级，比如 4KB。这个大小足够承载典型 AI 块计算，又不会大到完全无法做寄存器化管理。

4KB 的 Tile，大约可以容纳 1024 个 FP32，2048 个 FP16/BF16，或者更多低精度数据。它既能表示一个小矩阵块，也能表示一段向量块，还能通过 layout 描述变成不同执行单元眼里的不同形状。对于 CUBE，它可能是某种 fractal layout；对于 VEC，它可能是线性向量；对于 Tile LSU，它可能是二维地址空间中的一个矩形；对于量化单元，它可能还带着 scale、zero point 或 MX 格式的局部元数据。

这里最重要的一点，是 layout 必须成为一等公民。

Tile 不是一坨无名内存。它必须知道自己是 ND、NZ、ZN，还是某种 CUBE-friendly 的分型布局；必须知道 bank 如何交织；必须知道哪些维度有效，哪些是 padding；必须知道尾块如何 mask；必须知道数据类型是 BF16、FP16、FP8、INT8、MXFP4 还是更邪门的 4bit 格式。否则所谓 Tile 寄存器只是大号 SRAM，不是架构抽象。

## 世界上大厂都不是傻子，为啥别人不做

纸面上看，画 64 个 Tile 寄存器很容易。画一个 Tile ALU，也不难。写一句“共享 Tile Register File”，更是轻松愉快。难的是每一个细节都会要命。

Tile Load 和标量 Load 是什么关系？是否共享页表？是否共享一致性域？标量 store 和 Tile load 地址重叠怎么办？Tile load 跨页了怎么办？一整个 Tile 里某个 element 触发 page fault 怎么办？异常是整体上报，还是局部上报？如果 Tile Store 写了一半出错，状态怎么恢复？cache snoop 打进来时，Tile 里的数据算 cache line 吗？设备内存能不能投机？不可缓存内存能不能乱序？一个二维 Tile Load 不对齐，是拆成多笔请求，还是强制对齐？拆成多笔请求以后，外部可见顺序如何定义？

这些问题，没有一个是“加个模块”就能糊弄过去的。

首先，你必须全权控制指令集的定义权。

然后还要号召微架构、内存模型、操作系统、编译器的专家们一起坐下来才能啃的骨头。

当然七嘴八舌讨论起来就没完没了，和上班拉屎一样烧钱

1024 个 4bit 数据组成的 Tile，怎么转置？怎么从 32×128bit 变成适合 CUBE 的布局？MX scale 放哪里？每 32 个元素一个 scale，还是每 64 个元素一个 scale？scale 和 payload 是绑在一起走，还是分开走？矩阵算完以后，怎么高效量化回 BF16 给 VEC 做 softmax、exp、norm？尾轴很短时 reduce 怎么做？不规则稀疏场景下，gather/scatter 怎么保持带宽？histogram、topk、routing、prefix sum 这些东西，是继续靠算子哥用 shuffle 和 atomic 玩杂技，还是硬件给出更自然的块级语义？

GPGPU 面对这些场景，当然也能做。办法就是全世界一起优化：atomic 不行就 warp-level primitive，shuffle 不行就 shared memory，shared memory 不行就分层 reduce，分层 reduce 不行就换算法。最后算子哥修成武林高手，能在寄存器、shared memory、L2、tensor core、warp scheduler 之间飞檐走壁。问题是，一个生态能靠武林高手撑起来，不代表新架构还应该把普通程序员都逼成武林高手。

## Tile CPU 的目标，是让做CPU的多吃一点复杂度，让软件算法哥少一点玄学。

当然这个蛋糕的划分，还是很多人反对的。软件容易了，我咋去写算子了呢？CPU的也专家们在迟疑，是否能做出来。

Intel 其实已经迈出过半步。AMX 有 Tile 寄存器，也能做矩阵块计算。但 AMX 更像是在传统标量 CPU 旁边加了一个矩阵加速角。它没有真正把 Tile 纳入完整的乱序数据流，也没有让 Tile LSU、Tile Rename、Tile Issue、Tile Memory Model 成为核心抽象。它还舍不得离开传统 CPU 的舒适区，所以最后变成了一个很好用的扩展，而不是一种新处理器形态。

真正的 Tile CPU，要更激进。

它不是“CPU + 一个矩阵插件”，而是把标量、向量、矩阵统一纳入块级乱序执行。CPU 负责控制，Vector 负责灵活，Cube 负责重火力，Tile Register 负责把它们粘成一个体系。它不是拼积木，而是重新定义积木的接口。

当然，这件事也不浪漫。Tile 寄存器文件的读写口怎么做？Crossbar 怎么避免炸面积？bank 怎么分？多执行单元同时读写怎么仲裁？Tile rename 表怎么设计？物理 Tile 寄存器容量怎么控制？大 Tile 和小 Tile 是否共池？是否允许动态 Tile size？是否支持部分写？是否支持 layout 原地转换？TLOAD/TSTORE 和标量 Load/Store 的顺序点怎么定义？ROB 只提交 Tile 指令，还是要追踪内部 micro-op？精确异常落在哪一级？

这些问题一个比一个细，一个比一个硬。真正做芯片的人都知道，最难的不是写“支持灵活 Tile 计算”，最难的是时钟一敲，所有东西都必须在面积、功耗、频率和验证复杂度之间活下来。不要一遇到带宽问题就喊 3D，不要一看到 crossbar 就想堆硅。很多事情最后拼的还是基本功：banking、pipeline、bypass、queue、credit、scoreboard、replay、flush、exception、verification。

架构可以飞，电路得落地；诗可以上天，版图还得闭时序。

因为这不是改一条指令，也不是加一个矩阵单元，而是动指令集的根。动指令集，就等于动操作系统、编译器、运行时、算子库、调试工具、性能模型和程序员心智。

这里面任何一个环节没想清楚，都会变成未来十年的债，背上历史的骂名，**架垢师**。

但反过来说，也正因为它难，它才值得做。

今天 AI 模型的变化太快了。今天是 Attention，明天是 MoE，后天可能是新的记忆机制、新的路由结构、新的稀疏模式、新的长上下文压缩方式。你不知道下一篇论文会从哪里杀出来，也不知道下一个爆款模型会把哪个不起眼的算子推到舞台中央。训练和推理的难点，从来不只是矩阵乘法，而是模型结构永远在动，软件栈永远在追，通信模式永远在变。

如果硬件只擅长一种固定姿势，那它会在第一波浪潮里很漂亮，也会在第二波浪潮里很狼狈。

中国自己的 AI 处理器路线，完全可以走一条“CPU + Vector + Cube”的新路。CPU 不是传统小 CPU，而是块级乱序的控制核心；Vector 不是零散补丁，而是灵活处理非矩阵算子的主力；Cube 不是孤岛火炮，而是 Tile 数据流中的重火力单元。三者统一在 Tile 寄存器、Tile 调度、Tile 内存模型之下。

它不把复杂度甩给程序员，不把同步写成玄学，不把 buffer 管理变成宗教仪式，不让每个算子都靠手工 set/wait 保平安。它把过去 CPU 五十年最宝贵的东西——乱序、重命名、精确状态、内存语义、软硬件边界——搬到 AI 计算的块级世界里。

我之前问过体系结构大佬Yale Patt，其实CPU 生态当年就是这么来的。非冯诺伊曼架构挑战冯诺伊曼已经几十年历史了。到现在都没成功。在不断卷的竞争中，CPU不断吸收各种架构的精髓，例如数据流，例如systolic，例如transputer，例如belt machine。现在吃下GPU，也不迟。替软件吃下乱序，吃下预测，吃下异常，吃下页表，吃下寄存器重命名，最后才换来了软件的自由生长。

今天 AI 处理器如果还想进入下一个阶段，也许也需要一次类似的“复杂度内吞”。

哎，说来说去，问题其实很简单。

设计一款新型的处理器，把标量，向量，张量统一起来，啥都可以算不就行啦，算力可以大，带宽可以吃满，啥都可以高效跑起来，可以放在任何介质上。So Easy
