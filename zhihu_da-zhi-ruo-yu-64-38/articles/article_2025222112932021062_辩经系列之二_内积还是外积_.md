# 辩经系列之二：内积还是外积？

- 类型：文章
- 原文：[知乎文章](https://zhuanlan.zhihu.com/p/2025222112932021062)

2026 年，低精度矩阵乘的江湖，早已不复太平。

![image](https://pica.zhimg.com/v2-733684e755b5231072282b25d09ef164_1440w.jpg)

表面看去，不过是几家芯片厂商、几本指令手册、几套编译器后端，在机房、会议室、论文页边上你来我往；可若真把耳朵贴近那些风扇长鸣的机柜，贴近一颗颗张量单元昼夜不息的心口，便会听见一股极低沉、极持久的暗流，正在无数系统之下缓缓冲撞。那暗流说来说去，只围着一句话打转：

**矩阵乘，究竟该以内积Inner Product立身，还是以外积Outer Product布阵？**

这话初听平常，细想却极不平常。因为它问的，原不是一条指令该怎么写、一个算子该怎么排，甚至也不是某一代硬件的成败得失。它问的，是今日这场算力大潮里，矩阵乘这门天下第一显学，究竟该以什么样的骨架立住，才能既吞得下海量数据，又守得住数值精度，还不至于把软件写成一地鸡毛。

江湖上论此事的人很多，很多人装作谜语人，例如韭菜架构师的[也说矩阵外积和内积，不打哑谜](https://zhuanlan.zhihu.com/p/29297535012)。知乎论坛上，真正说到筋骨上的却不多。你若不把各家摆开，一家一家地看，便极容易被那些中性而堂皇的接口蒙住双眼，以为大家都在做同一件事。其实不是。江湖中最会骗人的，从来不是谎话，而是半句真话。

矩阵之道发展至今，早已不是一条独木桥。有人尚内积，谓点点归元，积小成大，最合低精度数值之正脉；有人崇外积，谓一势横推，能挟一列一行之力而震一片矩阵，最宜布大阵、开大江；也有人不肯明言本门心法，只在门外挂一块“矩阵乘加”的匾额，把真正的招式藏在深院回廊之后，任你从外面看，只觉云山雾罩，摸不准它究竟是拳是掌，是刀是剑。

## 一、同一座山，内积是东坡，外积是西岭

矩阵乘写在纸上，不过两种看法。

一种是课本里的老写法： ![C_{ij}=\sum_k A_{ik}B_{kj}](https://www.zhihu.com/equation?tex=C_%7Bij%7D%3D%5Csum_k+A_%7Bik%7DB_%7Bkj%7D) 又或者写成：

![C \mathrel{+}= A_{:,k}B_{k,:}](https://www.zhihu.com/equation?tex=C+%5Cmathrel%7B%2B%7D%3D+A_%7B%3A%2Ck%7DB_%7Bk%2C%3A%7D)若只站在线性代数的山脚下看，这两种写法并无高下，不过是同一座山从东西两面去望：东坡有东坡的层层石级，西岭有西岭的云气回环，山还是那座山，峰还是那道峰。可一旦把这两条路搬进硬件里，味道便立时变了。数学只管“你总归能上山”，硬件却要追问：**你挑的是哪条山路，路上要过几道险滩，扛多少行李，走几步便要喘一口气。**

```text
矩阵内积
for i in 0 .. M-1:
  for j in 0 .. N-1:
    acc = 0
    for k in 0 .. K-1:
      acc += A[i, k] * B[k, j]
    C[i, j] = acc
```

内积一路，眼睛是盯着**单个输出元素**的。它关心的是：这一项结果，究竟如何沿着 ![K](https://www.zhihu.com/equation?tex=K) 维，把一行与一列的乘积逐项归并，最后熬成一个数。它像一位老账房，桌上只摆一本总账，外头送来一张张票据，他便一张一张核对，一笔一笔并进去。每一步都不大，每一步却都朝着同一个结果收束。也正因如此，内积一路天然更容易长成 **dot-product** 或小型 **sum-of-products** 单元：它不求排山倒海，求的是步步归元，招招收口。

```text
矩阵外积
initialize C to zero
for k in 0 .. K-1:
  a_col = A[:, k]
  b_row = B[k, :]
  for i in 0 .. M-1:
    for j in 0 .. N-1:
      C[i, j] += a_col[i] * b_row[j]
```

外积一路，则不是先盯着某一个结果，而是先看**一列 AAA** 和 **一行 BBB**。它更关心的是：若一次送进这样一组输入，能同时掀动多少输出元素。于是它天然更适合长成 **rank-1 / rank-k update**，适合铺成 **systolic array**，也适合 **block outer-product** 这样的大开大阖的数据流。它不像账房，更像水师：一股水推过去，不只润一垄田，而是沿着渠系同时浇开一片地。([Why Systolic Architectures?](https://link.zhihu.com/?target=https%3A//www.eecs.harvard.edu/~htk/publication/1982-kung-why-systolic-architecture.pdf%3Futm_source%3Dchatgpt.com), [TPU 论文](https://link.zhihu.com/?target=https%3A//arxiv.org/abs/1704.04760%3Futm_source%3Dchatgpt.com))

可若读者此时心里一热，便断言“外积必胜，内积不过小家子气”，那便又着了相。因为到了今天，江湖上还有第三种路数，最会藏锋，也最容易叫人看走眼：

```cpp-objdump
Tile矩阵乘
for each output tile (tm, tn):
  load C_tile
  for tk in K tiles:
    A_tile = load A[tm, tk]
    B_tile = load B[tk, tn]
    C_tile = MMA(A_tile, B_tile, C_tile)
  store C_tile
```

这便是 **tile 级矩阵乘加**。它既不把自己明明白白写成内积，也不肯把自己赤裸裸写成外积，而是把输出切成一块一块 tile，先把 `C_tile` 载入，再不断取 `A_tile`、`B_tile` 来做矩阵乘加，直到整块 tile 累加完毕。门面上看，它是一块中性的 **MMA** 牌匾；骨子里究竟更偏内积还是更偏外积，却要看它的数据流和局部归约如何组织。它像个万花筒，远看只是一只小小镜筒，平平无奇；可你若凑近了，转一转，再往里看，便会发现其中另有层层世界，花影千重，虚实交错。你以为它只是一块 tile，谁知放大了以后，里头仍是成千上万的小江湖。

## 二、内积和外积在低精度拉开了差距

内积与外积，若只写在纸上，本是等价的。可一旦进了硬件，尤其是一旦进了**低精度**，事情便不再这样平和。因为这时矩阵乘里最要紧的，已经不只是“乘法怎么算”，而是**高精度累加器何时出场、多久出场一次**。说得更直白些，内积和外积真正的分野，不是公式写法，而是你这一刀究竟切在了哪里：

- 若切在**累加状态**上，让一大片部分和长期悬在场上，等着输入一轮轮去拍它，这一路便更近外积；
- 若切在**局部归并**上，先把若干乘积在近处熬成一团，再去碰高精度总账，这一路便更近内积。

低精度时，这一刀就格外要命。单个乘积固然已经很小，可一串一串乘积叠加起来，数值范围却会极快抬高。定点数里，若每个乘积都逼近上界，那么把 ![K](https://www.zhihu.com/equation?tex=K) 个这样的乘积累起来，累加器大致还要再长出 ![\log_2 K](https://www.zhihu.com/equation?tex=%5Clog_2+K) 位，才不至于中途溢出。浮点则更麻烦：它不只是尾数相加，还牵着**指数对齐、规格化、舍入**这些老臣一齐出场。于是便出现一种很有讽刺意味的景象：乘法器已经瘦身成功，轻巧如燕；可那条负责更新 **psum** 的高精度路径，却依旧衣冠整肃，步履沉重，每次出面都价码不菲。(["https://nhigham.com/wp-content/uploads/2023/10/high93s.pdf">Higham, The Accuracy of Floating Point Summation](https://zhuanlan.zhihu.com/p/2025222112932021062/%3Ci))

所以，低精度时代真正贵的，往往不是“乘”，而是“加”。
外积一路，最擅长布阵，最擅长复用；可它也最容易把大块累加状态早早摆到台前，叫高精度 accumulator 一次次出来理账。内积一路，未必最会铺大阵，却更自然地把“先局部归并，再碰高精度总账”的次序守住。

这，才是内积与外积在低精度时代真正分出胜负的地方。

## 三、外积的数据流，未必就是外积的命数

江湖上许多人一见“外积”二字，便以为凡是走外积数据流的，骨子里便必然是同一路数。其实未必。**外积数据流**，与**纯外积串行累加**，看似只差几个字，实则相去甚远。前者说的是阵怎么摆、水怎么走、输入与输出 tile 如何复用；后者说的，却是数值上最小更新单元究竟长什么模样，部分和又是如何一笔一笔被改写的。一个说的是阵法，一个说的是内功；一个关乎铺排，一个关乎收势。

若外积只停留在“数据怎么走”这一层，它原是有大长处的。它最会借势，最会复用，最会让一列 ![A](https://www.zhihu.com/equation?tex=A) 与一行 ![B](https://www.zhihu.com/equation?tex=B) 一经相逢，便去震动一整片输出，像潮头推岸，一浪下来，不只湿一角，而是整片滩涂同时受力。这种阵法在大规模矩阵机器里，自有其滔滔之势。可若这一路数再往里剥一层，剥到最小更新单元那里，若你发现它其实是 ![\hat{c}_{t+1}=fl(\hat{c}_t+p_t), \qquad p_t=a_tb_t,](https://www.zhihu.com/equation?tex=%5Chat%7Bc%7D_%7Bt%2B1%7D%3Dfl%28%5Chat%7Bc%7D_t%2Bp_t%29%2C+%5Cqquad+p_t%3Da_tb_t%2C) 那事情便立刻变了味。

因为这一式子，表面看只是“当前累计值再加一个新乘积”，像是再自然不过的一笔；可在数值分析那本老账簿里，它有一个很响、也很沉的名字：**递归求和**。说得不客气些，若真让外积一路在低精度里走到这一步，它便不再只是“外积善于布阵”的那点风流，而是重新掉回了最老、也最笨的那口井里。每来一个新乘积，便立刻拿去碰当前累计值；当前累计值的指数，每一步都要站出来发号施令；新来的乘积，也每一步都要依着它的量级去对齐、规格化、舍入。若 ![\hat{c}_t](https://www.zhihu.com/equation?tex=%5Chat%7Bc%7D_t) 已经很大，而 ![p_t](https://www.zhihu.com/equation?tex=p_t) 又太小，那 ![p_t](https://www.zhihu.com/equation?tex=p_t) 的低位便会在对齐时被一点点挤出门外，像细雨打进江潮，声息未闻，便已消散。此即所谓 **swamping**。它不喧哗，不张扬，然而最伤人。像江湖里有些阴柔掌力，表面不见血，不见骨，过得片刻，人才知经脉已伤。

这一层，Higham 在 *[The Accuracy of Floating Point Summation](https://link.zhihu.com/?target=https%3A//nhigham.com/wp-content/uploads/2023/10/high93s.pdf)* 里，其实早已讲透。递归求和的误差，并不是均匀地撒在每一步上，而是会被各步 partial sum 的大小加权；越往后加，旧部分和越大，新乘积便越容易受它支配，误差也便不再只是“由输入精度决定”，而是会随着累加深度一层层往上滚。把这句话翻译回硬件，便是**只要高精度 accumulator 在 product 级频繁介入，它的指数便会在每一步都支配新乘积的命运。**

到这里，外积的问题，便不在“外积”二字，而在于它把纯串行高频累加那套旧伤，重新招回了身上。阵法再大，若每一步都惊动高精度总账，终究还是气散而不聚，势大而难收。反过来，若肯先把乘积按小组收一收，局面便立刻不同。譬如先得

![g_0=fl(p_0+p_1+p_2+p_3), \qquad g_1=fl(p_4+p_5+p_6+p_7) ](https://www.zhihu.com/equation?tex=g_0%3Dfl%28p_0%2Bp_1%2Bp_2%2Bp_3%29%2C+%5Cqquad+g_1%3Dfl%28p_4%2Bp_5%2Bp_6%2Bp_7%29+)

再令

![\hat{c}\leftarrow fl(\hat{c}+g_0), \qquad \hat{c}\leftarrow fl(\hat{c}+g_1)](https://www.zhihu.com/equation?tex=%5Chat%7Bc%7D%5Cleftarrow+fl%28%5Chat%7Bc%7D%2Bg_0%29%2C+%5Cqquad+%5Chat%7Bc%7D%5Cleftarrow+fl%28%5Chat%7Bc%7D%2Bg_1%29)

那便不是让旧部分和对**每一个**乘积都横加干预，而只是让它在每一组归并之后，才出来主一次事。它不再是“逐项支配”，而是“按组支配”。这差别看似只多了一个“组”字，实则如同把散兵游勇收成方阵，把乱箭齐发改成分段放射。Higham 也正说到这一层：成对归约、成组归约，其误差增长更接近 ![\log_2 n](https://www.zhihu.com/equation?tex=%5Clog_2+n) 的量级，而不是 ![n](https://www.zhihu.com/equation?tex=n) 的量级。也就是说，哪怕硬件里的 group reduction 未必真是一棵完美平衡树，它只要肯先在局部把风浪压一压，再让高精度 accumulator 出面理账，伤势便会小许多，气血也不至于散得那般快。

好比江湖上一位成名已久的宗师，并不肯为每一个来犯的喽啰都亲自出手，而是先让门下弟子在前院消化一轮，真正需要压场的时候，他才缓缓出面，衣袖一拂，便把残局收了。高精度路径之贵，也正在于此：它不怕出手，怕的是**出手太频，太碎，太早**。

也正因如此，内积一路才更像修炼**任督二脉**，先把真气在体内一层层理顺、汇聚、归元，待火候到了，再送入丹田，一次定局。所谓 **fused dot-product**，它的高明从来不只是“多做几次乘法”而已，而是在于先把若干乘积裹成一团较宽的 sum-of-products，让局部的气血先在体内走顺，再只让高精度部分和介入一次。[Lutz 等人的 FP8-DOT4 工作](https://link.zhihu.com/?target=https%3A//www.ac.uma.es/arith2024/papers/Fused%2520FP8%25204-Way%2520Dot%2520Product%2520with%2520Scaling%2520and%2520FP32%2520Accumulation.pdf) 之所以值得反复提起，正因为它点破了这层窗户纸：关键并不在“四路”本身，而在于“这四路点积在进入 FP32 累加之前，不先被舍入”。说得更直白些，它修的正是那条最笨的旧路，不是让 accumulator 每来一个乘积就下场一次，而是让它等一小团乘积先在局部归并、站稳脚跟，再来接手。

## 四、训练精度之殇，在于矩阵累加位宽

矩阵乘这门功夫，江湖上人人看得见的是乘法器：位宽降了，格式新了，吞吐涨了，仿佛刀更轻、马更快、行军更省粮。可真正决定训练成败的，往往不是这些摆在门面上的热闹，而是那条藏在暗处、负责把一笔笔乘积并成总账的累加经脉。模型训练之殇，不常死于乘得不够快，反倒常死于加得不够稳**。** 这一层，低精度时代尤其如此。因为位宽可以降，乘法可以省，可部分和终究要往一处收；一旦收势失了法度，前面省下来的那点便宜，后面常常要成倍吐回去。([Sakr et al., ICLR 2019](https://link.zhihu.com/?target=https%3A//openreview.net/forum%3Fid%3DBklMjsRqY7%26utm_source%3Dchatgpt.com), [Blumenfeld et al., ICLR 2024](https://link.zhihu.com/?target=https%3A//openreview.net/forum%3Fid%3DoOwDQl8haC%26noteId%3DFf9ejNpWVC%26utm_source%3Dchatgpt.com))

早在低比特训练的研究里，便有人把这层窗户纸捅破了。[《Accumulation Bit-Width Scaling For Ultra-Low Precision Training Of Deep Networks》](https://link.zhihu.com/?target=https%3A//openreview.net/forum%3Fid%3DBklMjsRqY7%26utm_source%3Dchatgpt.com) 说得很明白：训练里即便权重、激活、梯度都敢往低精度压，**部分和累加**却往往仍要保留更宽位宽，否则训练质量会明显下滑；他们不仅给出分析框架，还在 ResNet、AlexNet 等模型上验证：累加位宽若压得过头，网络收敛就会受损。低精度训练真正卡住人的，不是乘法器还能不能更小，而是**部分和一旦变窄，信息损失会不会沿训练过程一路滚大**。这就像行军打仗，前锋的刀枪固然可以换轻装，可中军粮道若被你硬生生削短一截，前线越猛，后方越容易断炊。

[《Towards Cheaper Inference in Deep Networks with Lower Bit-Width Accumulators》](https://link.zhihu.com/?target=https%3A//openreview.net/forum%3Fid%3DoOwDQl8haC%26noteId%3DFf9ejNpWVC%26utm_source%3Dchatgpt.com) 虽然主谈推理，却把一句狠话摆得很正：在许多低精度研究里，**高精度累加已经逐渐成了主要瓶颈**；之所以迟迟不敢把 accumulator 一路压下去，不是众人愚钝，而是因为一旦压得太狠，精度便真会掉，且掉得不讲情面。作者之所以要专门研究 12-bit accumulator 能否撑住，恰恰反过来证明一件事：**累加位宽不是边角料，而是系统命门。**

[DeepSeek-V3 Technical Report](https://link.zhihu.com/?target=https%3A//huggingface.co/papers/2412.19437%3Futm_source%3Dchatgpt.com) 把 FP8 训练高高举起，工程上也确实把这条路走通了；但围绕其报告内容，社区很快就追问到一个极细、也极要命的问题：**Hopper Tensor Core 的 FP8 累加精度，究竟保留到什么程度？** 在公开 issue 里，提问者直接引用报告中的说法，追问“为何文中会提到有效 mantissa 很受限制，而实验里结果又看上去没那么差”。([DeepSeek-V3 报告页](https://link.zhihu.com/?target=https%3A//huggingface.co/papers/2412.19437%3Futm_source%3Dchatgpt.com), [DeepSeek-V3 issue #197](https://link.zhihu.com/?target=https%3A//github.com/deepseek-ai/DeepSeek-V3/issues/197%3Futm_source%3Dchatgpt.com)) 这件事本身就极有意味：若累加精度真只是小事，何至于大模型工程做到这一步，还要专门为 Tensor Core 的中间精度较真？正因为训练是长河，不是短打；一次矩阵乘里的微小误差，也许当场不炸，可千万步、万亿 token 地滚过去，便可能在某个夜深人静处，露出真容。

真到大模型训练的深水区，大家都在想方设法替低精度乘法补课，免得它把累加经脉拖垮？尺度要分块，动态范围要调教，局部误差要设法拦腰截住——说到底，还是在替那条累加路径擦屁股。门面上看，是 FP8 训练大获成功；骨子里看，却是所有人都明白：**低精度乘法可以放，累加精度却不可轻慢。**当然我们也欢迎新的算法能够在累加精度上做更多的创新，这样我们的CUBE累加就不要这么宽了。内积的累加，都是远远超过32bit的，42bit算是正常，69bit算是极致。

## 五、ARM SME之坑

这个世界上也就只有华子能够拿出来两种矩阵引擎，鲲鹏SME，昇腾CUBE。也就是因为同时做了两个的那个男人，才知道阴和阳的两面。

**ARM SME**不打机锋，也不藏话头，开宗明义便说自己擅长的是**向量外积累加到矩阵状态**。Arm 自家的介绍里，明明白白把 SME 的要点写成“**two vectors 的 outer product**”与“**matrix tile storage**”；又专门立了一套新的架构状态 **ZA**，让外积的结果不是飘在半空里，而是堂而皇之地落在一片二维矩阵阵列之上。这一路的心法，说穿了并不复杂：不是盯着一个结果元素，沿着K维慢慢熬；而是取两股向量之势，让它们一经相逢，便去撼动整片 tile。看上去极有气象，像大江行地，一浪既来，不只湿一角，而是整片滩涂一齐受力。

可问题恰恰也出在这里。**外积这一门，最擅长的是布阵，不擅长的是收功。** 声势越大，越要问一句：这一片被同时更新的矩阵状态，数值上究竟由谁兜底？Arm 自己给出的答案，其实已经把这层尴尬写在明处了。对于 `FMOPA`、`BFMOPA` 这类 widening 指令，架构上并不是让低精度结果就地在低精度里翻滚，而是**强行把它们累加到 32-bit 的 ZA tile 上**。也就是说，输入可以是 FP16、BF16，门面上看仍是“外积并累加”的大阵；可真正作为架构状态站在堂上的，却是 **ZA.S 这类 FP32 累加阵列**。([Arm SME 指令说明 Part 2](https://link.zhihu.com/?target=https%3A//developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/arm-scalable-matrix-extension-introduction-p2), [FMOPA 伪代码说明](https://link.zhihu.com/?target=https%3A//arm.jonpalmisc.com/latest_aarch64/fmopa_za32_pp_zz), [BFMOPA 伪代码说明](https://link.zhihu.com/?target=https%3A//arm.jonpalmisc.com/latest_aarch64/bfmopa_za32_pp_zz)) 这件事本身就很说明问题：**SME 口头上高举外积大旗，架构上却又不敢让外积结果在低精度里裸奔到底。** 为什么？因为它自己也知道，低精度乘法器便宜，不代表低精度累加就可以胡来；向量叉乘到一整片矩阵状态，看起来痛快，可真要把这片状态长期留作架构之物，便不得不抬到更高精度去养着。

SME 的路数，出手时讲究排山倒海，掌风过处，四壁皆震；可掌势越大，内力反噬也越重，于是到头来，不得不在丹田里另蓄一口更厚的真气替它压阵。SME 的 **ZA** 正是这口“真气”：看似是外积门法的自然延伸，实则也是外积门法不得不背上的负担。 ZA 累加阵列的布局并不轻巧，让它不得不用寄存器去搭建，SRAM就不要想了。Richard G把它定义成一块**按 SVL 字节数平方扩张的二维方阵状态**，既可以看作 tile，又可以切成行列 slice；为了便于硬件访问，不同 tile slice 之间还要做交织布局。你若只看宣传，会觉得这是一片恢弘的矩阵国土；可若站在架构师的角度往里看，便会生出另一层感受：外积并不是只换来“更自然的数据流”，之前矩阵累加的超过32bit的精度问题，到底要不要暴露到状态上？

架构可见的结果都已经被迫抬到 32 bit 了，内部若真想把外积的数值路径收拾得更像样，就几乎必然还得靠更宽的临时累加位宽去垫后**。** 这个累加宽度，便是内部不可见的架构状态。外积一旦真做成架构第一公民，低精度下它就很难只靠一个“32-bit 累加阵列”的门面把事情圆过去。

但是，即使做成了更宽的累加精度，为了克服swamping效应，**向量差乘每次累加需要对齐、规格化、舍入的精度需求是远远大于内积的**。这也就是解释了矩阵乘内积下，累加可以做到38bit-42bit就基本满足精度要求了。但是外积需要69bit的累加精度，才能做到和内积相同的精度！这个69bit还要乘以累加阵列的FLOPS。

SME现在的实现是CUBE的1/4的算力。如果做到和CUBE相同的算力，那么SME的面积会远远大于CUBE的面积。这也就是为什么，韭菜架构师说的名言：“这个公司设计指令集的人 1）既不写 RTL，也不写算法 kernel；2）是 ARM 派来的间谍”了。

## 六、内积之巅，昇腾CUBE

论内积门派，也就是Intel AMX，NV Tensor Core 和昇腾的CUBE。这些内积的矩阵单元，在 ISA 层亮出的，是堂堂正正的点积归约：两块 tile 相对，沿局部 ![K](https://www.zhihu.com/equation?tex=K) 维生成若干乘积，再把它们并入目标 tile accumulator。这样的写法，一望便知是“内积派”的嫡传。

先说 Intel AMX。它确实是把“tile 级别的秩序”做出来了：tile load、tile store、tile matmul，摆得颇有章法，看上去像是把矩阵运算从标量世界里请进了正殿。用AMX写程序的确是很爽。可它最大的硬伤，也恰恰在这里。AMX 这套内积功夫，本该配大开大阖的粮道，可它偏偏寄身在 CPU 那套旧朝廷里，要去挤 CPU 的 memory model，要去同标量 LSU 抢路。内积本来就吃输入带宽，偏偏又不肯另立新渠，还要与标量访存共用旧桥旧道。你叫一位练重剑的高手，日日走独木桥、钻小巷子，能施展开多少本事？所以 AMX 的毛病，不是内积不对，而是**内积虽正，所托非人**。路子是正路，地基却还是 CPU 那一套老地基。能在这样的地面上写出惊世骇俗的性能，本来就不是容易的事。

再看 NVIDIA Tensor Core。它的有趣之处，在于它虽属内积系谱，却又不像 AMX 那样老老实实把“点积”二字挂在门口。它更像一个城府极深的高手，表面上只给你一块矩阵乘加的牌匾，背地里却代代改法，年年变招。Volta 初出江湖时，Tensor Core 还是初代神兵，主打混合精度矩阵乘加，意在把 AI 训练的矩阵大算一举抬起来；到了 Turing，它又明显偏向推理，开始把 FP16、INT8、INT4 一类多精度能力收进囊中；Ampere 再往前，既引入 TF32，又纳入 FP64，摆明了不只盯着 AI，还要把 HPC 一并揽入帐下；到了 Hopper，Transformer Engine 更是与 Tensor Core 紧紧绑在一起，整个重心都压向大模型训练；再到 Blackwell，这套路数已不再只是“矩阵乘更快”这么简单，而是把**低精度格式、缩放策略、Transformer Engine** 打成了一整套。也就是说，Tensor Core 从来不是“一颗老芯片换个工艺接着卖”的故事，而是一路在改战法、一路在调经脉。

但若真要说到“内积之巅”，还是得看昇腾的 CUBE。因为 CUBE 身上，有一种别家少见的明快：它不像 AMX 那样寄身旧制度，也不像 Tensor Core 那样处处折中、层层藏锋。它从骨架上就是一颗内积核，而且这骨架长得极漂亮。它把低精度乘法做成了三维展开，轻盈得像树梢新叶，一层一层舒展开去；可真到累加树干那里，却又肯逐级做粗、逐级加厚，直到最底下那一截，粗壮得足以扛住极高的 FP4 算力。于是你会看到这样一种很有意思的景象：枝叶可以轻，树干却必须壮；乘法可以细薄如纸，累加却要厚重如梁。也正因如此，到了最新的 Ascend 950 PR，FP4 算力竟可高至 1732 TFLOPS。这个数字本身固然耀眼，但更值得看的不是它有多高，而是它背后那套内积式结构逻辑：**前端轻盈，后端厚重；前端是叶，后端是木；前端求展开，后端求承重。** 这才是内积之所以适合低精度的一层真义。

内积还有一个外积一路最难受、最不愿正面承认的好处：**算力配比可调。** FP16、FP8、FP4 之间，你可以做成 1:2:4，也可以做成 1:4:8，甚至继续往下扩。为什么能这样？因为内积一路最核心的资源消耗，落在局部归约与累加路径上，而前端数据格式一旦变窄，带来的更多是 L0A、L0B 一侧的带宽与容量伸缩。这种伸缩，对 CUBE 来说，往往只是“矩阵两边的供料口稍微改改宽度”的事情；可若你换到那种“用向量喂矩阵”的外积架构上去想，事情便立刻变得头疼。说得再直白一点：若你非要拿 SME 那一套来吃这些变化，问题就来了——向量长度要不要跟着加宽？若不加宽，是不是要多轮填充？若多轮填充，访存、时序、接口复杂度谁来买单？这类问题，越想越烦，越算越乱。因为外积那一路，本就最吃“阵法整齐”，而一旦数据格式频繁变窄、变轻，原本整齐的向量喂数节奏便容易被打散。对 CUBE 来说，这些却简单得多。因为它本来就是按内积的路数立起来的：前端乘法阵列怎么铺，后端累加树怎么长，左右两边的供料口怎么扩，逻辑上都是一条气脉，不必像外积一路那样，先去纠结“这一行向量够不够宽、那一列数据要不要补齐、这口粮是一次喂完还是分三次喂”。

然后我们在扯到GPGPU架构上，warp specialization要是能给tensor core喂数据，需要多少个warp呢？不同的数据格式是不是用的warp个数不同？

这种增加，如果类比到那种从向量给矩阵喂数据的架构来说（说的就是SME），就是极为头疼的事情。SVE是不是为了SME，需要把VL的宽度变宽呢？还是需要多次向量填充数据呢？怎么想都是难搞的事情。外头总爱说 GPU 生态好、编程成熟，可一到真要给 Tensor Core 喂数据的时候，旧朝的体面便也未必还能尽数维持。到了 Hopper 这一代，NVIDIA 已把 Tensor Core 的大块矩阵运算抬到 **warpgroup** 粒度来做：所谓一个 warpgroup，便是 **四个 warp，合一百二十八线程**，专门去发 `wgmma` 这等更大的矩阵乘法指令。换句话说，**单只一个 warp 已不够撑场面，得四个 warp 抱成一团，才够把 Tensor Core 那张胃口喂开。** 这已说明一件事：若真要让矩阵乘发挥威力，GPU 也早不是“一个 warp 干完一切”的老光景了。([What is a Warpgroup?](https://link.zhihu.com/?target=https%3A//modal.com/gpu-glossary/device-software/warpgroup%3Futm_source%3Dchatgpt.com), [NVIDIA Hopper 架构简介](https://link.zhihu.com/?target=https%3A//www.nvidia.com/en-us/data-center/technologies/hopper-architecture/%3Futm_source%3Dchatgpt.com))

更麻烦的是，不同数据格式下，这笔账往往还不一样。Hopper 与 Blackwell 的 Tensor Core 支持的精度族谱越来越杂：FP16、BF16、TF32、FP8，再到 Blackwell 的 FP4、微缩放格式，位宽一变，tile 形状、输入搬运量、shared memory 压力、寄存器占用、甚至 Transformer Engine 配合方式都跟着变。NVIDIA 官方自己也在讲：Hopper 重点把 FP8 和 Transformer Engine 绑在一起，Blackwell 又进一步把 FP4 与第二代 Transformer Engine 绑在一起，说明不同精度本来就对应不同的主战场和不同的实现重心。于是从工程实践看，喂 Tensor Core 需要多少 warp，本就不该期待“所有格式一个答案”——FP16、FP8、FP4 下，数据量、搬运节奏、局部缩放元数据、共享内存压力皆不同，warp 分工当然也会跟着变。

## **七、未来路在何方**

今日之大模型，仍旧深深受累于累加精度。乘法可以越来越轻，格式可以越来越花，FP16、BF16、FP8、FP4，名目一层叠一层；可到了最后，那些部分和、那些总账本、那些高精度 accumulator，仍像老衙门里的印信与账册，谁也不敢轻慢，谁也不敢轻易裁撤。于是整个世界都活在一种奇异的两难之中：一边拼命夸低精度的轻巧迅捷，一边又不得不在暗处悄悄加宽累加路径、抬高中间精度、补上局部归约，唯恐哪一步走岔了，模型便不收敛，训练便走火入魔。这不是某一家芯片的羞处，而是这个时代共同的窘境。它说明了一件极朴素、也极残酷的事：**我们还没有真正发明一种算法，能让累加精度从硬约束变成软约束；我们还没有走到那个“模型自己知道哪里该粗、哪里该细，哪里该升精、哪里该降精”的时辰。**

也许，未来的路，终究不只在硬件。真正能指引下一代演进的，恐怕还是算法本身。等到哪一天，大模型不再把高精度累加视作命根，不再处处依赖一条粗重到吓人的总账路径；等到哪一天，算法能自己感知误差、自己调节精度、自己在局部归约与全局收敛之间找到动态平衡，那时内积与外积今日这些争论，才可能真正被超越。到了那一步，矩阵乘单元也许不必再为“到底留 32 bit、42 bit，还是 69 bit”这等事情夜夜惊心；高精度不必再像朝廷钦差一般凡事亲临，低精度也不必再像江湖草莽一般时时担心自己压不住场。若真有那一日，硬件才算从“替算法擦屁股”的苦差事里解脱出来，算法也才算真正反过来给了硬件新的天命。

可在那一天到来之前，仍要认清眼前的形势。**按照目前的算法格局来看，内积独立的矩阵乘单元，仍旧更像 the chosen one。** 不是因为它名字古老，也不是因为它听上去更正宗，而是因为在低精度这块险地里，它更容易守住一条最重要的规矩：先在局部把气机理顺，把乘积归并成势，再去碰那本高精度总账。它不像纯外积那般，把部分和早早悬在台前，任由每一笔新乘积都来惊动老臣；它更像练内功，讲究任督二脉贯通，讲究真气在体内先走一个周天，到了火候，才送入丹田，一锤定音。今天的模型训练，今天的数值边界，今天的收敛现实，都还在替它说话。
