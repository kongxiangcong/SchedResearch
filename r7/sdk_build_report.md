# R7 local XRT C++ client SDK assembly

The installed Phoenix runtime can be used by a newly compiled, project-local C++
client. This step assembled a header/import-library subset and qualified host
metadata parsing. It did not build an AIE kernel, open the device, run copy/GEMM,
or qualify performance counters. Device execution evidence belongs to the main
R7 experiment, separately from this report.

## Frozen inputs and assembly

- Public header revision: `42cba83aee86b253c49eccd484646e91d062468d`, XRT 2.17.0.
  Reused the already captured [exact source archive](https://codeload.github.com/Xilinx/XRT/tar.gz/42cba83aee86b253c49eccd484646e91d062468d),
  SHA256 `971e612a83c0d8c848ab1f5a78e03db53f5a1568bb96b1553150f387c78a1d3d`.
- `sdk/assemble_sdk.py` recursively selected 25 verbatim public headers for
  device/kernel/BO/hw-context/xclbin use. Quoted includes resolve completely.
  Each header has its exact upstream URL, source path, size and hash in
  `sdk/source_manifest.json`. System/STL headers come from the installed MSVC/Windows SDK.
- Upstream `version.h` is generated by CMake. `sdk/include/version.h` is explicitly
  a local generated subset of the ABI macros, using major 2/minor 17/default
  patch 0 from frozen `src/CMakeLists.txt` and macro formulas from frozen
  `src/CMake/config/version.h.in`. Both originals are saved under
  `sdk/generation_sources`. ABI checking remains enabled. This file does not
  invent installed DLL build dates/branches and is not a verbatim upstream file.
- `C:/Windows/System32/AMD/xrt_coreutil.dll` hash was checked against the prior PE
  inventory before assembly:
  `0ad76915287e229c61845279e4c089607254197b61f92f7fca411a7935aa4e94`.
  Its 426 actual named exports became `sdk/lib/xrt_coreutil.def`, then the local
  import library. No implementation or driver DLL was copied or modified.
- Used installed Visual Studio BuildTools 2022 v17.14.22, MSVC tools directory
  `14.44.35207`, x64 target/host. `VsDevCmd.bat` only sets the build child process
  environment. No global environment, compiler installation or driver upgrade.

## Reproduction and build outputs

From repository root, using PowerShell:

```powershell
python -X utf8 -B r7/sdk/assemble_sdk.py
& r7/sdk/build.cmd
python -X utf8 -B r7/sdk/qualify_metadata.py
python -X utf8 -B r7/sdk/build_qualification.py
& r7/sdk/verify_fixture.exe 'D:/dsh-proj/SchedResarch/r7/sources/kernel_access/int8_fixture'
```

Compiler flags are `/std:c++17 /Zc:__cplusplus /O2 /MD /EHsc`; include root is
`r7/sdk/include`, import library is `r7/sdk/lib/xrt_coreutil.lib`.
`/Zc:__cplusplus` is necessary because these upstream headers select `std::any`
using `__cplusplus`; `/std:c++17` alone on MSVC selected a missing Boost header.
The initial DEF quoted each symbol, which MSVC preserved in the import name;
assembly was corrected to use unquoted actual symbols. These were local build
failures, not device incompatibility or runtime numerical failures.

`sdk/build.cmd` produces `sdk/xclbin_metadata.exe`. The later build script
`sdk/build_qualification.py` builds `r7/bin/copy_probe.exe`,
`r7/bin/compute_probe.exe`, and `sdk/verify_fixture.exe`, captures each source's
bytes before compilation, checks they remain unchanged during compilation,
and records source/executable hashes in `sdk/build_receipt.json`. Exact source
snapshots and build logs sit beside the scripts. All three final builds exited
0. No device probe was executed by this SDK task. Build receipts are historical
and must not be silently associated with a subsequently edited source file.

## Actual loaded-DLL metadata checks

The metadata executable parses a file with `xrt::xclbin`; its source creates no
`xrt::device`, context, BO or run. Every final invocation explicitly reports the
module path returned by `GetModuleFileNameA(GetModuleHandleA("xrt_coreutil.dll"))`.
All 16 returned the installed `C:/Windows/System32/AMD/xrt_coreutil.dll` and the
hash above. The child process PATH is prepended with that AMD directory only.

All 15 installed `.xclbin` files plus the frozen RyzenAI-SW `gemm_4x4.xclbin`
were successfully parsed (exit 0). Complete UUIDs, kernel names, argument index/
type/size/offset and memory connectivity indices are in `sdk/metadata/*.txt`;
`sdk/metadata_receipt.json` records file hashes and results. These memory indices
are xclbin connectivity metadata, not a measured physical allocation map or a
device-context `kernel.group_id()` qualification.

`validate_phx.xclbin` exports `DPU_PDI_0` through `DPU_PDI_7`; the GEMM binaries
export `DPU`. Both ABIs have opcode `uint64_t`, input/parameter/output/intermediate
buffer pointers, instruction pointer, instruction count `uint32_t`, and mc
pointer. The host memory index is 0 and instruction SRAM index is 1 in these
metadata. The declared memory size does not establish resident capacity available
to the complete research workload.

Four installed xclbins contain the named `XDP_KERNEL`:

| File | XDP_KERNEL present |
|---|---|
| `1x4_3.5.0.0-1505.xclbin` | yes |
| `1x4_3.5.0.0-1562.xclbin` | yes |
| `4x4_3.5.0.0-1506.xclbin` | yes |
| `4x4_3.5.0.0-1561.xclbin` | yes |

The installed `validate_phx.xclbin`, all installed GEMM xclbins, and downloaded
`gemm_4x4.xclbin` do not contain `XDP_KERNEL`. A name's presence does not qualify
the profiler's instruction ABI, firmware compatibility, counter routing, event
semantics, measurement overhead or safe device execution.

## Independent CPU fixture check

`sdk/verify_fixture.exe` includes the frozen original AMD `super_instr.h` and
`wgt_matrix.h`. It reproduced the Python fixture's 200-byte instruction struct
exactly (`MLKernelParams=40`, `GemmInstr=60`, `GemmSeq=200`), reproduced all
4,194,304 packed weight bytes, then independently accumulated all 2,048 INT8 GEMM
outputs using INT64 sums and compared them exactly to the stored INT32 oracle.
It exited 0. `sdk/fixture_verification_output.txt` and
`sdk/fixture_verification_receipt.json` retain the output and input hashes.

This is source-layout and CPU-oracle evidence, not evidence that the device
executes the fixture correctly. It does not make the old Python development SDK
complete, demonstrate BF16 support, compile new AIE instructions, or qualify any
architecture performance/negative result. The next decision is a bounded device
launch with the fixed source-backed contract and explicit comparison, handled
by the main R7 work.

`sdk/artifact_manifest.json` hashes the SDK report and all SDK artifacts, excluding
the manifest itself. R1–R6 and root files were not modified by this subtask.
